## 1 · How practitioners actually build these systems, step by step

### 1.1 Agentic research and planning architectures

**The vocabulary.** Anthropic separates *workflows*, "systems where LLMs and tools are orchestrated through predefined code paths", from *agents*, "systems where LLMs dynamically direct their own processes and tool usage" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Its named patterns, in order of increasing autonomy:

| pattern | what it is | use when (source's words) |
|---|---|---|
| prompt chaining | fixed sequence of calls, with programmatic "gates" between steps | "the task can be easily and cleanly decomposed into fixed subtasks" |
| routing | classify the input, send it to a specialised handler | "distinct categories that are better handled separately, and where classification can be handled accurately" |
| parallelization | *sectioning* (independent subtasks) or *voting* (same task several times) | subtasks parallelize, or "multiple perspectives or attempts are needed" |
| orchestrator-workers | a central model decides the subtasks at run time, delegates, synthesizes | "you can't predict the subtasks needed" (example given: information gathering across many sources) |
| evaluator-optimizer | one model drafts, another critiques, loop | "clear evaluation criteria" and refinement "provides measurable value" |
| autonomous agent | loop with tools, ground truth from the environment each step, stopping conditions, human checkpoints | "open-ended problems where it's difficult or impossible to predict the required number of steps" |

The same source's governing advice: start simple and add agentic structure "only when simpler solutions fall short"; give the agent ground truth from tools at each step; include "stopping conditions (such as a maximum number of iterations)" and pause "for human feedback at checkpoints or when encountering blockers"; and invest in the agent-computer interface (tool descriptions, poka-yoke arguments) as much as in the prompt ("we actually spent more time optimizing our tools than the overall prompt").

**ReAct (reason + act).** The base loop of almost every research agent: interleave a reasoning trace with a tool action and its observation. Reasoning "help[s] the model induce, track, and update action plans as well as handle exceptions", actions "interface with external sources"; grounding each step in a lookup reduced the "hallucination and error propagation prevalent in chain-of-thought reasoning", and the trajectories are human-readable ([ReAct, arXiv 2210.03629](https://arxiv.org/abs/2210.03629)).

**Plan-and-execute.** A *planner* writes a multi-step plan; an *executor* runs each step with tools; a *re-planner* is called after execution to "decide whether to finish with a response or whether to generate a follow-up plan". Variants: ReWOO lets later steps reference earlier outputs as variables (`#E2`) so the plan runs without consulting the planner each step; LLMCompiler compiles the plan into a task DAG and a "task fetching unit schedules tasks once their dependencies are met", in parallel. Claimed gains over ReAct: speed, cost (small models for steps), and better overall results from explicit up-front thinking ([LangChain, Planning agents](https://www.langchain.com/blog/planning-agents)).

**As-needed (hierarchical) decomposition.** ADaPT does not commit to a full plan up front: it "plans and decomposes complex sub-tasks as-needed, i.e., when the LLM is unable to execute them", recursively; +28% to +33% success on three benchmarks over fixed planning ([ADaPT, arXiv 2311.05772](https://arxiv.org/abs/2311.05772)). The point for us: decomposition depth should follow difficulty met, not be fixed at intake.

**Reflection and episodic memory.** Reflexion has the agent write a verbal reflection on each failure into an "episodic memory buffer" read on the next attempt ([arXiv 2303.11366](https://arxiv.org/abs/2303.11366)). This is learning between attempts without retraining.

**Deep research systems in production (three vendors).**

*Anthropic Research* ([How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)):
1. A **LeadResearcher** analyses the query, writes a strategy and **saves its plan to Memory** ("if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan").
2. It spawns **subagents** in parallel, each with a task description that states objective, output format, tool guidance and boundaries (vague delegation produced duplicated or missed work).
3. **Effort scaling** is written into the prompt: a simple fact-finding query gets one agent and 3–10 tool calls; complex research gets 10+ subagents with divided responsibilities.
4. Search strategy: "Start with short, broad queries, evaluate what's available, then progressively narrow focus."
5. Subagents return condensed findings; outputs can go to an **artifact store** rather than through the lead ("prevents information loss during multi-stage processing").
6. A separate **CitationAgent** processes the documents and the report to attach sources to claims.
7. Lessons: errors compound in stateful agents, so build to **resume from checkpoints**; full **production tracing**; "rainbow deployments" so running agents are not broken by an update. Multi-agent beat single-agent by 90.2% on its internal eval, but used ~15x the tokens of a chat; "token usage alone explains 80% of the variance" in performance.

*Google Gemini Deep Research* ([API docs](https://ai.google.dev/gemini-api/docs/deep-research); [engineering talk digest, ZenML](https://www.zenml.io/llmops-database/building-gemini-deep-research-an-agentic-research-assistant-with-custom-tuned-models)):
1. The agent first returns a **research plan the user can edit** ("editable chain of thought"; `collaborative_planning=True` returns a plan instead of executing; the user iterates, then approves). The origin: "when asking an intern to do research, they would naturally ask clarifying questions first."
2. Execution is **asynchronous and durable**: runs take minutes, `background=true`, poll or stream; individual call failures retry "without losing overall progress"; the run graph is dynamic, decided by the model at run time, so static workflow engines did not fit.
3. Memory: recent research stays in full context for follow-up questions; older research moves to retrieval.
4. Users accepted longer runs and valued seeing many sources visited.

*OpenAI deep research* ([system card, Feb 2025](https://cdn.openai.com/deep-research-system-card.pdf)): trained by RL on browsing tasks graded against ground truth or rubrics; searches, reads text, images and PDFs, runs Python, "pivoting as needed in reaction to information it encounters". Stated limits: it "can sometimes hallucinate facts ... or make incorrect inferences", "may struggle with distinguishing authoritative information from rumors", and is weak at "confidence calibration" (from the launch page as quoted in search results; the launch page itself returned 403). Two named risks bear directly on us: **prompt injection** from browsed pages (mitigated in part by not letting the agent "navigate to or construct arbitrary URLs"), and **aggregation of personal information** about individuals ("in combination they may provide an unexpectedly comprehensive view about their life"), mitigated by policy, a blocklist and evaluation.

**STORM (structured pre-writing).** Before writing, STORM discovers *perspectives* on the topic, simulates conversations in which writers holding each perspective question a source-grounded expert, then builds an *outline*; this improved organisation by 25% and coverage by 10% over a retrieval baseline as judged by Wikipedia editors. Its stated residual failures: "source bias transfer" and "over-association of unrelated facts" ([STORM, arXiv 2402.14207](https://arxiv.org/abs/2402.14207)). The perspective step is a method for generating competing lines of inquiry.

### 1.2 Memory, scratchpads and long-horizon work

Anthropic's context-engineering guidance ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)):
- **Context rot**: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; context is an "attention budget".
- **Just-in-time retrieval**: keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load the content when needed; **progressive disclosure** (sizes, names, timestamps guide what to open next).
- Three long-horizon techniques: **compaction** (summarise and restart; risk: losing "subtle but critical context"), **structured note-taking** (the agent maintains an external notes file; the Pokémon example keeps tallies and maps across thousands of steps), and **sub-agents** that return 1,000–2,000-token summaries.

Anthropic's harness for multi-session agents ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)): an *initializer* session writes a **progress file** and a **structured list of every objective, each marked failing until verified**; each later session reads them, works on **one item at a time**, verifies end to end, commits, and updates the log. Named failure modes it fixes: "declaring victory prematurely", trying to do everything at once, and marking work done that does not work end to end.

MemGPT treats context as an OS treats RAM: tiers of memory and explicit moves between them, applied to documents larger than the window and to multi-session continuity ([arXiv 2310.08560](https://arxiv.org/abs/2310.08560)).

### 1.3 Document understanding

**Industrial intelligent document processing (IDP) runs a pipeline: classify, then route, then extract, then review.** Microsoft Document Intelligence pairs a **custom classification model** ("identify the document type before invoking the extraction model"; it also *splits* a multi-document file into typed page ranges) with per-type extraction models composed behind one endpoint. Two model kinds: **template** models for a fixed visual layout (a test: blank out the user-entered data; if the blank forms look identical, it is one template) and **neural** models for "the same information, but different page structures". "You only need five examples of the same form or document type to get started"; the advice is to split visually distinct variants into separate models ([Custom document models](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-model)).

Google Document AI's custom extractor has a three-rung ladder: a **foundation model, zero-shot**, usable "after labeling a single document"; **auto-labeling** (the model proposes labels, a person verifies them); and **fine-tuned custom models** needing "at least 10 training instances and 10 test instances of each field". For the generative path the schema is the prompt: field names "are semantically critical", and good property descriptions give "location information and text patterns of the property values, which help disambiguate" ([Custom extractor mechanisms](https://docs.cloud.google.com/document-ai/docs/ce-mechanisms)). This is few-shot learning of a new document type in production form: a schema with descriptions, one or a few examples, people verifying.

**Layout-aware parsing.** Open tools reconstruct a document's structure before any reading: Docling runs layout analysis (DocLayNet model) and table-structure recognition (TableFormer), recovers reading order, and emits a structured `DoclingDocument` exportable to Markdown/JSON ([Docling, arXiv 2408.09869](https://arxiv.org/abs/2408.09869)). Losing structure is a known cause of failure: PDFTriage shows that RAG systems which flatten PDFs into text fail on questions that refer to pages, sections and tables; giving the model the document's structural metadata plus `fetch_pages`, `fetch_sections`, `fetch_table` tools fixed many of these ([PDFTriage, arXiv 2309.08872](https://arxiv.org/abs/2309.08872)).

**Reading by structure first, then targeted extraction.** Three research systems formalise what Bob described:
- *PDFTriage* (above): read the outline, then fetch the parts the question needs.
- *ReadAgent*: paginate a long document into episodes, compress each into a **gist**, then reason over the gists and **look up** original pages when detail is needed; 3.5–20x effective context, better on QuALITY, NarrativeQA, QMSum ([arXiv 2402.09727](https://arxiv.org/abs/2402.09727)).
- *RAPTOR*: recursively cluster and summarise into a tree, then retrieve at whichever level of abstraction the question needs; +20 points on QuALITY with GPT-4 ([arXiv 2401.18059](https://arxiv.org/abs/2401.18059)).

**Question-guided extraction over long or many documents.** DocETL observes that a single LLM call over a long document misses instances (its example: not finding every force-majeure or indemnification clause) and rewrites the task into split → map → resolve → reduce pipelines with agent-guided validation, 25–80% more accurate than engineered baselines ([DocETL, arXiv 2410.12189](https://arxiv.org/abs/2410.12189)). **Schema discovery** for unfamiliar semi-structured collections: Evaporate first identifies the attributes the documents contain, then extracts them either directly by LLM or by LLM-written extraction code, aggregated by weak supervision; 110x fewer tokens than direct extraction at better quality ([Evaporate, arXiv 2304.09433](https://arxiv.org/abs/2304.09433)).

**Prompting for long documents** (Anthropic, [prompting best practices §Long context prompting](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)): put long documents at the top and the question at the end ("can improve response quality by up to 30 percent ... especially with complex, multidocument inputs"); wrap each document with `<source>` and other metadata; **quote first, then answer** ("ask Claude to quote relevant parts of the documents first"). Position matters: performance "significantly degrades when models must access relevant information in the middle of long contexts" ([Lost in the Middle, arXiv 2307.03172](https://arxiv.org/abs/2307.03172)).

**Retrieval over a collection.** Chunks lose their context ("revenue grew 3%" of whom?); prepending a short generated context to each chunk before embedding and BM25 cut retrieval failures 49%, and 67% with reranking; and below about 200,000 tokens, Anthropic advises skipping retrieval and putting the whole corpus in the prompt with caching ([Contextual retrieval](https://www.anthropic.com/news/contextual-retrieval)). For questions about a whole collection ("what are the themes?"), GraphRAG builds an entity graph and community summaries and beats plain RAG on comprehensiveness and diversity ([arXiv 2404.16130](https://arxiv.org/abs/2404.16130)).

### 1.4 Human-in-the-loop review and acceptance

Industrial practice routes **low-confidence predictions, plus a random sample of the rest, to people**: Amazon A2I's two activation conditions are a confidence threshold and random sampling for audit, and reviewed outputs feed retraining ([A2I docs](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-use-augmented-ai-a2i-human-review-loops.html); note the service is closed to new customers). Microsoft: "For scenarios where accuracy is critical, confidence can be used to determine whether to automatically accept the prediction or flag it for human review"; confidence exists at several levels (document type, field, word/OCR, table/row/cell) and must be read together, since OCR confidence and field confidence are independent; a low *document-type* confidence means the document differs from what the model knows ([Accuracy and confidence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/accuracy-confidence)). Google's auto-labeling puts people in the loop as verifiers of machine proposals that then become training data ([ce-mechanisms](https://docs.cloud.google.com/document-ai/docs/ce-mechanisms)).

Two warnings from the human side:
- **LLM confidence is not calibrated by default.** Verbalised confidence is systematically overconfident; agreement across multiple samples helps; all methods struggle on specialised knowledge ([arXiv 2306.13063](https://arxiv.org/abs/2306.13063)). OpenAI says the same of deep research (above).
- **Reviewers over-rely.** NIST names *automation bias*, "excessive deference to automated systems", and notes it "can exacerbate other risks of GAI, such as risks of confabulation"; it also warns that GAI may produce "confabulated logic or citations that purport to justify or explain the system's answer" ([NIST AI 600-1 §2.2, §2.7](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)). Experiments (N=731) show explanations reduce overreliance only when they **lower the reviewer's cost of verifying** the AI's answer; complex explanations do not ([Vasconcelos et al., arXiv 2212.06823](https://arxiv.org/abs/2212.06823)).

### 1.5 Citation grounding and hallucination control

Measured state: generative search engines had full citation support for only **51.5%** of sentences, and only **74.5%** of citations supported their sentence, while appearing fluent and informative ([Liu et al., arXiv 2304.09848](https://arxiv.org/abs/2304.09848)). On ALCE, "even the best models lack complete citation support 50% of the time" on ELI5 ([arXiv 2305.14627](https://arxiv.org/abs/2305.14627)). A 2026 trajectory-level study finds no deep research system robust: some are "confident fabricators", others create an "illusion of grounding" by misattribution (>0.20); **over 57% of source errors in proprietary agents arise early (in planning) and cascade**; agents show an "anchor effect" on early retrievals and a homogeneity bias; and they silently drop user-specified restrictions ([PIES, arXiv 2601.22984](https://arxiv.org/html/2601.22984v1), first 100k characters read).

The techniques practitioners use:
| technique | how | source |
|---|---|---|
| permission to not know | instruct the model it may say the document lacks the information | [Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations) |
| quote first | for >20k-token documents, extract verbatim quotes, then reason only from them | same; long-context tips |
| cite then retract | after drafting, find a supporting quote for each claim; "If it can't find a quote, it must retract the claim" | same |
| restrict to supplied documents | forbid general knowledge for factual claims | same |
| API-level citations | the model cites spans of supplied documents; `cited_text` is extracted by the API so "citations are guaranteed to contain valid pointers to the provided documents"; granularity is sentences (text, PDF) or your own blocks (custom content); scanned PDFs without text and images are not citable; incompatible with strict structured output | [Citations](https://platform.claude.com/docs/en/build-with-claude/citations) |
| independent verification | Chain-of-Verification: draft; plan verification questions; answer them *independently of the draft*; revise | [arXiv 2309.11495](https://arxiv.org/abs/2309.11495) |
| best-of-N consistency | run several times; disagreement flags likely hallucination | Reduce hallucinations; arXiv 2306.13063 |
| dedicated citation pass | a separate agent attaches sources after the research | Anthropic multi-agent research |
| system-level limits | no arbitrary URL construction; blocklists; refusals for private-person dossiers | OpenAI system card |

Definitions to adopt: **attribution** is whether a statement is supported by an identified source, judged by a person in two stages, first whether the statement is interpretable, then whether the source supports it (AIS, [arXiv 2112.12870](https://arxiv.org/abs/2112.12870)); **atomic-fact precision**: split output into atomic facts and count the share supported (FActScore; ChatGPT 58% on biographies; an automated estimator within 2% of humans; [arXiv 2305.14251](https://arxiv.org/abs/2305.14251)).

### 1.6 Evaluation of such systems

Anthropic's agent-eval practice ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)):
1. Start with **20–50 tasks drawn from real failures** (the research team started with "about 20 queries representing real usage"); effect sizes are large early.
2. Keep **transcripts** and **read them**; grade the **outcome** (the state of the world), not the exact path.
3. Combine **code graders**, **model graders** (a rubric; for research: factual accuracy, citation accuracy, completeness, source quality, tool efficiency; "a single LLM call ... outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent") and **human** review, which "catches what automation misses" (the team found agents preferring SEO content farms over authoritative sources that way).
4. Separate **capability** evals (low pass rate, room to climb) from **regression** evals (~100%); measure **pass^k** (all of k runs succeed) where consistency matters.
5. For research agents specifically: ground truth shifts, experts disagree; use groundedness, coverage and source-quality checks, and **calibrate LLM rubrics against expert human judgment** frequently.

LLM judges agree with people >80% but carry **position, verbosity and self-enhancement biases** ([MT-Bench, arXiv 2306.05685](https://arxiv.org/abs/2306.05685)). Evaluation criteria **drift**: "users need criteria to grade outputs, but grading outputs helps users define criteria", so criteria must be revisited after people grade real outputs ([EvalGen, arXiv 2404.12272](https://arxiv.org/abs/2404.12272)). Public benchmarks: DeepResearch Bench (100 expert tasks; RACE for report quality, FACT for citation accuracy and effective-citation count; [arXiv 2506.11763](https://arxiv.org/abs/2506.11763)); OpenAI evaluated factuality with PersonQA and found its test set itself out of date in places (system card §3.3.6), a reminder that reference answers age.
