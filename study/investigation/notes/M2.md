### 3.1 `ai-runs` (layer 6) — the run as a durable, bounded object

**Purpose.** "The AI run: a durable, bounded, attributed object a member opens over a question or a project, under which the assistant finds, pursues, extracts and checks ... nothing here accepts, attests, concludes or captures" (ai-runs §Purpose).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `open` (`op=airunopen`) | run id, context (`inquiry` or `project`), mode, two principals (plane credential, paying Claude account), skill version, bias manifest, standard pair, bounds, state → run row + bound rows + lens at open | R9, R10, R40 | built (R40 tested T11) |
| mode `plan` open | `plan` id, project context, a member behind the caller, `fetches`=`subsessions`=0 | R46, R47 | specified (K660); the gate code exists, but `plan` is not deployed (see run-rules) |
| `tick` (`op=airuntick`) | consumption map, log entries, `state` (≤ 262,144 B) → log appended via observation-log's one writer (`authority_kind: run`, `actor_class: machine`), lease extended, run ended if a bound is exhausted | R11, R12, R45 | built |
| `close` / the one exit | bound or ending → terminal log entry with rolled-up search state (`PRESENT` > `partial` > `LOOKED_INDETERMINATE` > `LOOKED_ABSENT` > `NEVER_LOOKED`) | R13, R14, R31 | built |
| reaper; wake/resume | lease 3,600,000 ms; a run with completed capture requests is woken and re-dispatched to `agent-worker` only under the instance `ai` credential | R15–R18, R41 | built |
| `read` (`op=airun`), `log` (`op=airunlog`), `listInContext` (`op=airuns`) | run → session (budget, condition, bias lens block, bar, resumable `state` — "never a transcript, DEC-61") | R19–R24 | built |
| `spawnPayload` (`op=airunspawn`) | `search` half has **no lens field**; `compose` half adds it | R23, R34 | built |
| surfacing step | an assistant may create an inquiry only under a running run with a `surfaces` bound | R25–R27 | built |
| `runFor`, `boundOf`, `consumeBound` | for producing modules; never ends a run itself | R28, R29 | built |
| usage and ceiling | per-call `usage` → `ai_usage` per member/day/mode (admin-only export, no content); member-set daily ceiling, admin may set a lower copy-wide one; `op=aiusage` | R48–R53 | specified (T33-50) |

**What it gives an investigation engine.** A durable container for a bounded piece of AI work with recorded conditions (principals, skill version, lens, bar), a budget, an append-only search log (the observation log), resumability (`state`, lease, wake on capture completion) and one exit. Its **context is one inquiry or one project** (R9; `run-rules` R7, `RUN_CONTEXTS`); there is no notion of an investigation larger than a project, nor of objectives within it. The run's `state` is opaque scratch (≤ 256 KiB, R45), not a plan record. *(inference)* An investigation's "planner" could hold its working plan in `state` today, but nothing makes that plan visible to members as a record.

**Limits.** No member-facing "accept" here: acceptance lives with the producing modules' targets (basis-versions, action-plans). Runs start only at a member's act (`run-rules` R18; R46 for `plan`: "nothing schedules, wakes or starts a new one by itself"), except the woken resume (R16–R18), which continues an existing run.

### 3.2 `run-rules` (layer 6) — pure vocabulary, deployment order

**Purpose.** "The AI run's rules without a store: the bounds, endings and statuses ... the one deployment order of the run's modes, and the rows of every refusal" (run-rules §Purpose).

Services: `RUN_BOUNDS` = `fetches, subsessions, wallclock, runtime, mints, surfaces, proposals, lease` (R1, R13); `checkConsume` (R3: `lease`, `mints`, `surfaces`, `proposals` are plane-counted); `projectGate` (R6, DEC-63: a project run needs a participant); `runPrincipalGate` (R5); `checkSkillVersion` (R8); `DEPLOYMENT_SEQUENCE.order` = `check, investigate, extract, plan` (R9, R14); mode `ask` deployed apart (R16); `ASK_BOUNDS` `turns, bytes, wall_ms, reads` (R17); `startAllowed` — "An AI run or ask starts only at a member's act, with one exception: the AI half of a member-authored standing question" (R18); `verification_recorded` and `deployable` — each later mode deploys only after a member-recorded live verification of every earlier one (R19); ceiling refusal rows (R20).

**Built vs specified.** R1–R15 built (R13–R15 tested, RUN-RULES #5, T24). R16–R20 are marked specified (T33-49), but the code at the pin already holds them: `bio-plane/src/run-rules/deployment.mjs` defines `ASK_MODE` (`deployed: false`), `RUN_MODES`, `DEPLOYED_MODES`, `VERIFICATION_RECORDED`, `checkVerification`, `deployable` (lines ~148–240, checked). **What is deployed (code-checked):** `DEPLOYMENT_SEQUENCE.verification_recorded` is `null` and `deploys_apart.plan.deployed` is `false`, `ASK_MODE.deployed` is `false`, so `DEPLOYED_MODES` = `["check"]` only. `investigate`, `extract`, `plan` and `ask` are all undeployed in the record's gate; `agent-harness/src/harness.mjs` `MODES` agrees (`check: deployed: true`, the others `false`, lines 197–224).

**Consequence for an investigation engine.** The only mode that may run is `check` (re-check a question's basis against the record). A fresh investigative mode exists as a name and a gate, and its enablement is a chain: `check` verified live by a member → `investigate` may be deployed by a reviewed edit (R19, `enables_how` in deployment.mjs).

### 3.3 `run-productions` (layer 6) — the run's only writes to the record

**Purpose.** "What an AI run produces, and the only way it produces it. The investigative session's one write is a suggestion: a version of a question's basis in state `suggested` ... never accepted, hidden, rejected or made current here" (run-productions §Purpose).

| service | what | Rn | state |
|---|---|---|---|
| `suggest` (`op=suggest`) | one basis version in state `suggested` on the run's question; kinds `basis-version`, `sharpen-question`, `new-inquiry`, `level-empty`, `new-edition`; ≤ 120 legs, every leg a `document` leg naming the capture read | R1–R9 | built except R9 (each leg names `extent_capture`, D-595) |
| pre-write checks | no member-only field (`state`, `affirmed` …); no boilerplate; legs reachable; the strength pair computes; branches independent; differs in substance from held versions | R3 | built |
| memo of refusals | a byte-identical resubmit answers the stored refusal (`repeated: true`) | R2 | built |
| `extractPropose` (`op=extractpropose`) | mode `extract`: proposed readings of a held document's passages, each labelled machine work, minted as content rows within the `mints` bound; `earned` grade B or C computed, "never offered"; "proposals, not extraction coverage" | R10–R13 | built (R13 specified), but **unreachable**: `extract` is not deployed |
| narrow candidate source | proposals with a position, for `basis-versions`' `narrowCandidates` | R14 | specified (K31) |

**What a run may write (summary of the fence).** A suggestion (basis version, `suggested`), a log entry (tick), a capture request, its close; in `extract` mode, proposed readings; in `plan` mode, `optionpropose` (agent-worker R53). It writes nothing a member's act owns: `SUGGEST_UNWRITABLE_STATE` (C-27.13) covers `state`, `hidden`, `affirmed_parts`, `affirmed` and grounds "composed ... by a machine unless it declares exactly one part, DEC-65" (R3). A machine author's grounds are "asserted by no one (`SUFFICIENCY_UNCLAIMED`)" (R4). "Nothing is accepted, hidden, rejected or made current; nothing is captured or requested; no notification is sent" (R4).

**How a member accepts.** Not here: a suggested version is accepted (made current, affirmed) by a member's act in `basis-versions` (outside M2's scope; see M-unit for evidence modules). *(inference)* An investigation engine's findings would enter the record as suggested versions on inquiries, and members accept them where they accept any version.

| attribution | "the daemon captured this, at the investigative session's request (run <run>), under <plane>, paid by <claude>" | R10, R33 | built |

| one fetch per version | conditional fetch against a held capture | R39 | specified (K103) |
| source refusal reasons | `login`, `paywall`, `user-agent`, `other` | R40 | specified |

| sweep-scoped requests | a request may name a ratified sweep | R45 | specified |

| reads | `captureRequests`, `completed`, `leads`, `rendersHeld`, `waits`/`markWoken` (the run wake), `requestById` | R23–R29, R43 | built except R27 |

**For an investigation.** This is the engine's only route to new documents from the web: a run names an address it judged worth having; the daemon fetches with provenance; the run is woken when its requests complete (ai-runs R16). Leads for other questions (`lead_inquiry`) exist. **Limits:** the run must already know the address (no search engine or portal navigation service in scope); paywalls and logins are refusals with reasons, retryable with member-supplied credentials (specified); records requests (FOIA/CPRA) are absent from this module.

### 3.5 `agent-worker` (layer 6) — the fleet member that performs a run

**Purpose.** "The fleet member that performs an AI run for the plane ... It walks a deterministic control-flow table ...: the model decides what to search for and what reports mean, inside a step, and never when the loop stops. It writes nothing itself ... It never attests, concludes, accepts or publishes" (agent-worker §Purpose).

| service | what | Rn | state |
|---|---|---|---|
| `POST /run` | `{run_id, store, credential (aik-…), account, turns?, judgements?, max_steps?}`; reads the run's mode/budget/context from the record, its log for resume | R1–R12 | built (R6, R10 amended T33-57: member's own account only) |
| fan-out | per pass, four sub-sessions in order `meaning`, `content`, `document`, `internet`, each with a frozen spawn contract whose `scope` is `["meaningrows"]` and no lens field; internet level = `op=capturerequest` per judged address | R17, R18 | built |
| collect | reports held to the report contract; each cited address (≤ 20) re-read through `op=meaningrows`; holdings counted by `op=search` + `op=versionchain` | R19, R21 | built |
| compose / dedup / submit / adjust | `level-empty` candidates per `LOOKED_ABSENT` level; dedup against `op=basisversions`; `op=suggest` one at a time; resend only if bytes differ | R22–R25 | built |
| log after every step | `op=airuntick` with spend and a log entry when the step looked | R26, R49 | built |
| mode `plan` | reads plan, earlier plans of the project, findings, determinations, standards, consequences, available actions, deadlines, venues, legal organisations; proposes options strongest-first through `op=optionpropose`; no web | R51–R53 | specified (K660); code present (`PLAN_FLOW`, `performPlanStep`), mode undeployed |
| `POST /ask` | a member's read-only question, answered under a short-lived grant, composed by `agent-model` turns, passed through `answers`' `checkAnswer` before returning | R54–R58 | specified (T33-57); code present (`agent-worker/src/ask.mjs`, 299 lines), mode `ask` undeployed |
| `PLANE_OPS` | exactly `whoami, airun, airunlog, airunspawn, meaningrows, basisversions, search, versionchain, affordances` (reads) and `airuntick, suggest, capturerequest, airunclose` (writes) — "none of them returns document bytes" | R37 | built |

**Model turns (code-checked).** The requirement file says model turns do not run (status: "Not yet met: R40, R41 (model turns and sub-sessions do not run; D-218, D-611)"), but at the pin `agent-worker/src/index.mjs` (1,636 lines) calls `agent-model`'s `converse` at each judged row (`plan`, `compose`, `dedup`, `adjust`) when an account reference arrived (lines ~470–495), and reports `turns_run` and `judgement_source` (`model` or `body`) (lines ~1523–1535). So model-driven runs are **built in code (T33 L6), not yet verified live**: no `verification_recorded` is held, and `wrangler.jsonc` binds `PLANE` and a `RUNNER` Durable Object (`AgentRunner`, script `agent-runner`) — the subscription path's container. Whether it is deployed to Cloudflare is not visible in the tree *(inference: the release T33-D1 deploys the runner; `agent-runner` requirements say "its live start and reliability are measured after the release at T33's close")*.

**How the run reads a document (code-checked).** It does not open a document. The sub-session's only plane tool is `meaningrows` ("query the record at meaning grain through the plane (op=meaningrows)", `agent-model/src/model.mjs` `subsessionTools`, `limit` ≤ 50), with `rows` any arm `retrieval` serves (its R10: `leg`, and `passage` among others; `retrieval` R14 describes the `passage` arm with a content-axis coverage tally), so a sub-session may read **passages extraction has already made** and legs members have cited, never a document's bytes, layout or table of contents. Its answer is a `report` of at most 500 characters with ≤ 20 citations by address (`agent-harness` R5). `PLANE_OPS` "none of them returns document bytes" (R37); the parent re-reads cited addresses through the `leg` arm (`MEANING_ARM = "leg"`, `agent-worker/src/ops.mjs` line 53; R19). The rule behind it: "a sub-session that returns documents rather than reports has defeated the architecture" (index.mjs header; INVESTIGATIVE-SESSION §14b.1). The `ask` path reaches more reads (`ASK_OPS`: `explore`, `timeline`, `eventsfor`, `moneyof`, `holderat`, `lines`, `duties`, `meaningrows`, `search` and others, `ops.mjs` lines 60–65), but still no document text beyond extracted rows. *(inference)* Bob's "study the document ... the TOC of an RFP ... explore deeper and deeper" has no service in a run's reach: there is no op that reads a held document's structure, no purpose-aware reading, and the only machine reading of a document (`extractPropose`, mode `extract`) proposes passage readings and is undeployed.

**How it plans (code-checked).** The `plan` row is one judgement per pass, `judge_plan`, whose schema is `targets: [{level, url, target}]` plus look fields (`agent-model/src/model.mjs` `judgeTools`). Its facts are the pass number, the limit, the mode, the target and its basis, the levels (`rowFacts`). The pass limit is 3 (`agent-harness` R3; the plane publishes no `max_passes`, agent-worker Suggestions). No objective, hypothesis, lead list or plan record persists across passes beyond `state`. *(inference)* This is search planning within one question, not investigation planning.

### 3.6 `agent-harness` (layer 6) — the pure tables

**Purpose.** "The deterministic control-flow tables an AI run walks, and the contracts of what a sub-session is sent and may return, as pure functions" (agent-harness §Purpose).

Services: `CONTROL_FLOW` rows `gate-mode, resume, plan, fanout, collect, compose, dedup, submit, adjust, next-pass, close`, no edge `compose → submit` (R1); `gate-mode` first, only `check` deployed (R2); `stopBecause` on `fetches`, `subsessions`, `wallclock`, then the pass limit (3) (R3); judgements may set only `targets, reports, candidates, queue, adjusted, submission, level, observed, governed, condition` — anything naming `pass, maxPasses, step, budget, mode, bound, run, store, target` is `JUDGEMENT_OVERREACH` (R4); the report contract (R5); `PLAN_FLOW` for mode `plan` (R6); one sub-session per level (R7); pure (R8). All marked specified (T33-54, a copy job); at the pin the files exist (`agent-harness/src/harness.mjs` 1,267 lines, `subsession.mjs` 590) and `agent-worker/src/index.mjs` imports from them (checked). **Built in code**, met-marks pending.

**For an engine.** The pattern "the table decides control, the model judges inside a step" (INVESTIGATIVE-SESSION §14b.4) is the doctrine any planner must respect: a model-written plan cannot set the pass count, budget, mode or step. An investigation planner that chooses what to do next would either be a new table (as `PLAN_FLOW` was added for action plans) or would propose, not decide *(inference)*.

### 3.7 `agent-model` (layer 6) — how a turn reaches Claude

**Purpose.** "Given one member's own account reference, it sends a conversation's turns either to the Messages API (an API key) or to Claude Code running unmodified in the `agent-runner` container (a Claude subscription), returns each turn's outcome and its `usage`" (agent-model §Purpose).

Services: `MODEL_FOR_MODE` (R1; code: every mode `claude-opus-5`, "provisional ... until M-Q9 measures the cheapest", `agent-model/src/model.mjs` lines 29–36); `modelCall` routes by account kind, never retries a 429 (R2, R3); `cache_control` on system prompt, tools and resident pack layer (R4); `usage` on every outcome, `null` never 0 (R5); `converse` ends on the final tool, `stopped: turns|bytes` (segment bound), `exhausted` after `maxTurns` (12 default), or a silent/refused turn (R6); tools on the subscription path are only those named, relayed back to the Worker (R7); the secret kept nowhere (R8); no credential from `env` (R9). All specified (T33-55); code present (`model.mjs` 282, `apikey.mjs` 76, `subscription.mjs` 183, `outcome.mjs` 35 lines).

**Cost bounds visible here.** Segment bound on turns (`MAX_TURNS_PER_SEGMENT`, default 120, agent-worker R7) and bytes; per-conversation `maxTurns` 12. Cost is paid by **the member's own account** (K1502): "There is no project or instance level" (agent-worker R6, R32).

### 3.8 `agent-runner` (layer 6) — the subscription container

**Purpose.** "The container in which a member's Claude subscription runs a model conversation for the plane's fleet: Claude Code, unmodified, with every built-in tool, settings source and disk persistence off, so the model sees only the tools the Worker relays" (agent-runner §Purpose). R1–R11: one Agent SDK query per WebSocket connection, `tools: []`, no settings, no persistence; credential only in that query's environment; tools are relays; only egress `api.anthropic.com` ("the closed book, K1474 (i); the injection fence", R10). All specified (T33-56); code present (`agent-runner/src/` entry, runner, ws, manifest; Dockerfile). Live start "measured after the release at T33's close (M-Q1, M-Q2; T33-D1)" (Status).

**For an engine.** The model has no web or file tool of its own; every read goes through the Worker's relayed tools and thus through the plane's ops. This is the injection fence: an investigation that reads hostile documents (contractor filings, PDFs) is protected because the model cannot act except through plane ops the table allows *(inference from R3, R10)*.


### 3.9 `skills` (layer 6) — the doctrine pack a run works under

**Purpose.** "The instructions an AI run works under: the doctrine pack ... a resident layer every run holds from its first token (the objective, the machine/member boundary, the four-level rule, the absence vocabulary) and progressively disclosed layers ... It holds no gate: every fence it names is code elsewhere, and a model that ignored every word of it would get past nothing (§14b.4)" (skills §Purpose).

| service | what | Rn | state |
|---|---|---|---|
| `renderPack(published)` | from `op=affordances`' no-target answer: resident `objective`, `boundary` (machine fences, member-only acts), `four_level` (levels, search-completeness rule, answer shape `level, state, searched, not_searched`), `absence`; disclosed layers | R1–R6 | built |
| judgement doctrine | `DEFERRED_ROWS` / `JUDGED_ROWS` (§14b.4's two columns); `CLAUSES` each enforced by a C-number or stating why not; `controlFlowAuthority(text)` detects a pass budget or stopping rule in any doctrine text | R14–R16 | built |
| `PROHIBITIONS` | five: "no generated justification; no single confidence score; no connection-density ranking; machine-proposed connections never presented as connections; nothing is boilerplate" | R17 | built |
| `absenceByLevel()` | per level what absence means (meaning "nothing derived", content "nothing extracted", document "no document", internet "nobody looked"), the next level to ask | R19 | built |
| `packVersion` | identity digest recorded on the run (ai-runs R10) | R11 | built |
| disclosed layers | `contradiction` (R27, absent until its prompt is measured), `action_planning` (R28, R29), `filing_drafting` (R30), `edition_statement` (R31), `wizard_authoring` (R32), `legal_lookup` (R33: "search the four levels, request captures of what is missing, propose standards with captured text ... publish what it could not mechanise"; deployable only with `investigate`), `ask` (R34: closed book, at most one clarifying question), `suggestions` (R35: only where the member's own switch is on) | R27–R35 | R27–R32 specified in file; R33–R35 built in code at the pin (T33-52 job COMPLETE, `build/jobs/T33/skills.md`) |

**For an engine.** The pack is the place where "how to read a document of this kind" or "how to investigate a procurement" doctrine would live as a disclosed layer, versioned and recorded on each run. Today no layer covers document reading by purpose or investigation planning; the nearest are `legal_lookup` (find the governing law) and `action_planning` (propose options for an action plan). A layer must quote canon verbatim (R21: "Every authored sentence is found, through the normaliser, in the document its source names, and that document is canon"), so a reading or planning skill needs canon text first *(inference from R21)*.

### 3.11 `calibration` (layer 4) — fidelity of derivation engines

**Purpose.** "Holds the calibrations of derivation engines: dated, identified fidelity measurements of a named engine and version ... It holds no engine, no probe corpus and no measured number of its own; it runs no probe, re-grades nothing" (calibration §Purpose). Services: `checkCalibration`, `compare` (a lost bound is `worse`, which alone raises an obligation), `nextProbeDue` (30-day cadence, signals only bring a probe forward), `calibrationRecord` (`op=calibrate`), `liveCalibration({engine, version})` for `extraction`, `worseSupersessions`, listeners (R1–R19). Built (R4, R5, R8, R10–R12, R16 tested; R20 specified). Invariant: "No machine mints a grade: a calibration re-grades nothing in either direction" (R13, DEC-4).

**For an engine.** This is where an AI reader's fidelity would be measured if a model became a derivation engine (an engine with a version, a probe set, a cap). A model reading a document is a "derivation"; its readings would carry a cap only from a calibration, never from self-assessment *(inference from R13 and Content Framework §14.2 as cited)*. No model engine is registered today; `run-productions` R11 computes an `earned` grade B or C for a proposed reading from "what the reference names, never offered", not from a calibration.

**For an engine.** The observation log is a ready-made **search log** for an investigation: every look by a run, a member (through a lead), a sweep or a capture is a row with its level, authority and outcome, and an absence is recorded rather than lost. The lead is the nearest existing construct to an investigator's "tip": "something a member was told, which is somewhere to look and never evidence" (Purpose; R25). **Limits:** a member's own searching writes nothing (R24: "a member's own searching, viewing or reading writes nothing"); leads are visible only to the author and projects it was shared to (R15); a lead has no link to an inquiry or a plan beyond sharing to a project. Rows hold no notion of *why* a look was made beyond the authority (run id, lead id, objective).

### 3.13 `bias` (layer 5) — declared lenses and their debt

**Purpose.** "Declared bias is how a group says, in the record and in public, the lens it reads evidence through ... Bias is disclosed and never blocks work" (bias §Purpose). Services: `checkBiasSet` (three statement kinds `scrutiny`, `inference`, `pattern`; never a verdict on a source, R5; never a bar, R6), adoption by a member with a reason (R11, R12), `biasManifest` (the effective lens and its `statements_sha`, R13–R18), `biasInhale` (reads an outside policy into a proposal, "The method writes nothing, ever", R19–R21), the **bias debt** over work products (a run whose lens has since moved owes a re-look, disclosed, never blocking; R33–R44). Built except R24–R26, R40 (a question's findings as work products), R41, R46, R47.

**For an engine.** The run records the lens in force at its open (ai-runs R10) but the search half never receives it (ai-runs R34: "bias shapes weighing, never searching"). A long investigation would accrue bias debt when the group's lens changes mid-way, disclosed to the run's principal and project owners (R34). This is the existing mechanism for "the investigation's conclusions were formed under lens X".

### 3.14 `wizard-scripts` (layer 11) — authored guided flows

**For an engine.** A wizard is a fixed, authored path through acts; it is the product's existing "guided procedure" construct. An investigation's member-facing steps that recur (e.g. filing a records request, capturing a page in one's own browser) could be wizard scripts; the assistant may propose one on the fly but a member approves *(inference from R5, R12)*. It is not a planner: it holds no state of a case or objective.

### 3.15 `affordances` (layer 11; its assistant parts)

**Purpose.** "The plane-sourced act pre-flight (DEC-8): for one object as it stands and one caller as they are, which acts exist ... It publishes what the acting modules enforce and computes no refusal of its own" (affordances §Purpose).

Assistant parts:

**For an engine.** The rung and friction model is how a member-accept step would be presented: a machine-proposed item is accepted by a member's act on a rung, with a reason where `reasoned`. Opening an AI run on an objective is already a `reasoned` act whose reason is shown beside budget and scope (R31).
