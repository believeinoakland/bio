Unit M1, phase 1 (PROTOCOL §R). Scope: build/requirements/<m>.md for 19 modules (inquiry … tasks), verified against code where a claim matters. Product tree: `STUDY/../..` at SOURCES-PIN.


**How to read this note.** §1 takes each module in turn: its purpose as it bears on investigation, the services an investigation engine would use (name, inputs → outputs, Rn), built vs specified, and limits, each verified against its code where it matters (the file checked is named). §2 is the doctrine these requirements bind. §3 reads the nineteen modules against the study's questions (intake, planning, reading, holding, explanations, evidence, time, money, people, procurement, member-in-the-loop, AI runs, cost). §4 lists gaps and tensions. ## 1 · The modules

### 1.1 inquiry (layer 6) — the question as the one recursive object

**Purpose.** "An inquiry is the one recursive object of case-making: a question, which gathers evidence and other inquiries as the legs of its basis, and may reach a conclusion" (`build/requirements/inquiry.md` §Purpose). It holds the lifecycle, legs and their grading, ground partitions (DEC-32), exclusions, supersession, division, contradiction-inquiry vocabulary and (since T33) dated waits. It holds no basis version, conclusion or strength (those are `basis-versions`' and `strength`'s).

**What an investigation engine would use.**

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| State machine | `open`/`surfaced` → `deferred`/`dismissed`/`concluded`/`divided`; `divided` terminal; `published` read only | R1 | built |
| Leg grammar | leg `{target, role supports/cuts_against, grade A–D, grade_axis capture/connection/testimony, grade_source, note, ground, content_id/extent}`; ungraded leg is undetermined and inert (DEC-18) | R4–R9 | built (via `inquiry-grammar`) |
| New leg kinds | a held standard (`STD-`), a calculation (`CALC-`), a duty occurrence (`occurrence:<DUT>/<key>`), an imported finding of another group's case | R4, R11 | built (T33-45; `inquiry-grammar/grammar.mjs:617`) |
| Promotion check + projection | every revision judged (`BASIS_REFUSED`, `SELF_BASIS`, `BASIS_CYCLE`, `CANDIDATE_ALREADY_TAKEN_UP`…); projects `inquiry_basis`, exclusions, superseded-by, subject entity | R11, R12 | built |
| `dispose({handle,to,reason,…})` | defer/dismiss a selection of inquiries; refused if cited (`CITED`) or drawn on by >1 project (R39) | R20–R22, R39 | built |
| `divide({target, reason, children, …})` | splits a question into ≥2 children with every leg apportioned, incl. those that cut against; member only (`MACHINE_CANNOT_DIVIDE`) | R23–R26 | built |
| `ground({target, grounds, …})` | partitions legs into labelled grounds (DEC-32), member only | R27–R28 | built |
| `exclusionsNaming`, `stateHistory` | who excluded/reopened what | R18, R19 | built |
| `staled(notice)` → `onRaised` | when a capture is re-read and rows go stale, each citing inquiry is told once (re-evaluation raised) | R41, R42 | built |
| Contradiction vocabularies | coordinates, plurality differences, resolution kinds (DISSOLVED / CORRECTED / GENUINE), norm canons | R46–R48 | built |
| `inquiryFindings` as `bias` work products | a finding made under a project lens carries a debt when the lens changes | R53 | built per header (T22) |
| Dated waits | a `recheck_triggers[]` entry with a `date` → `datedWaits({member, asOf})` (`waiting`/`due`/`looked`/`ended`), `waitLook`, scheduler hooks `datedWaitsDue/Wake/Tick` | R54–R57 | built (code at `inquiry/index.mjs:944–1021`); header says "not yet met (T33-45)" at fold time |

**Limits.** No plan, objective or sub-task construct: a question has legs, children (by division) and recheck triggers, nothing that says "what to find next". `surfaced_by` is `agent` or `human`; a machine may surface a question but never divide, ground or author a leg role (R30). R31 (an opinion element is never a leg) is *(not yet met: MK-5)*. Dated waits are told only to their setter (R55), so a group investigation's deadlines are personal, not shared (*inference*).

### 1.2 inquiry-grammar (layer 6) — the pure grammar of an inquiry document

**Purpose.** The entry requirements of each state (C-2.8), the leg grammar, the recheck coverage (C-15.1), the lead checker (C-54.1); pure, reads no record (`inquiry-grammar.md` §Purpose, R9).

| service | what | Rn | state |
|---|---|---|---|
| Entry requirements | `concluded` needs a conclusion, ≥1 leg and a **falsifier** stated or its absence recorded with who/when (REC-117); `deferred`/`dismissed` need a reason | R1 | built |
| Division block | every leg has a home among children | R2 | built |
| Recheck coverage | every inquiry, every state, carries ≥1 `recheck_triggers` `{text, description, date?}`; date a real calendar date | R3 | built |
| Lead checker | a lead id (`observation-log`'s `LEAD_ID_RE`) is never a leg: `LEAD_NOT_EVIDENCE` | R5 | built |
| Imported finding ref | `imported:<import>/<finding>` with `target_edition`, no grade (the edition's grades stand) | R11 | built |
| Standard / calculation / occurrence legs | `STD-` graded on the capture axis only; `CALC-` and occurrence legs state no grade (derived by `strength`) | R13–R15 | built (`STANDARD_LEG_AXIS` at `inquiry-grammar/checks.mjs:95`) |

**Bearing.** The **falsifier** requirement and mandatory **recheck triggers** are investigative discipline already in the grammar: every conclusion must say what would overturn it, and every question says what should make someone look again. These are the substrate's nearest thing to "what would change our mind" planning.

### 1.3 leg-earning (layer 6) — what the record earns for a leg

**Purpose.** "What the record can earn for a leg of an inquiry's basis, and which questions rest on a given target" (`leg-earning.md` §Purpose). Split from `inquiry` (K617), met in T33 (K1612).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `earned(subjectEntity, targetIds, contentIds?)` | per target: connection grade (strongest A–C entity resolution of its captures to the subject), capture ceiling (bounded by machine-transcription quality; undetermined if unmeasured), testimony D for a member's observation; each with `why` | R1 | built (`leg-earning/index.mjs:413`) |
| `legCapped(stated, earned)` | null if within earned, else the cap and why | R2 | built |
| `earnedBasis({id, targets, viewer})` | the inquiry's legs as a viewer may see them, each with content row and which capture (`pinned`/`only_capture`/`undetermined`); ≤200 targets | R3 | built (`op=earnedbasis`) |
| `basisFor`, `restingOn`, `restsOnLive`, `cyclePath`, `projectsDrawingOn` | the dependency graph both ways; projects drawing on a question (≤32) | R4–R7 | built |

**Bearing.** This is the grade ceiling an engine must respect: a member may not state a grade above what the record earns (DEC-18, DEC-24 via R10). `restingOn` is the "what depends on this document" query a case file needs when a document is corrected.

### 1.4 hypotheses (layer 6) — hunches held apart from evidence

**Purpose.** "A member's hunches and hypotheses, held as labelled rows of the working inquiry (K1467): never facts, never legs, never moving a grade or a finding" (`hypotheses.md` §Purpose). Met in T33 (K1607).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `hold({inquiry, kind, statement, about, by})` | one `HYP-` of kind `cause`/`identity`/`relation`/`flow`/`other`, about named nodes (two for relation/cause/identity) | R1 | built |
| `revise`, `withdraw` | append-only history with who/when/why | R2 | built |
| `hypothesesOf`, `read` | labelled "hypothesis", never graded | R3 | built |
| `neighbours` (connection owner `hunch`) | in `explore`, a hypothesis is a hop **only inside its own inquiry's scope**; any chain through it is a lead | R4 | built (`hypotheses/index.mjs:80,131`) |
| Leg check | refuses a leg on a `HYP-` (`HYPOTHESIS_NOT_A_LEG`, C-134.10) or on a derived connection whose chain carries a hunch/declared hop (`LEAD_NOT_A_LEG`, C-134.11), or that cannot be re-derived (C-134.12) | R5, R6 | built (`hypotheses/index.mjs:336–364`) |

**Limits that matter.** `MACHINE_CANNOT_HYPOTHESISE`: "only a member holds a hypothesis" (R1, K1473). An AI planner may therefore *not* record its own competing explanations here; it can only offer a "Noticed" item a member may take up as a hypothesis (Suggestions, K1473). There is no field for a hypothesis's predicted observations, test, or status beyond `withdrawn`: it is a labelled statement, not an explanation-under-test (*inference*). `cause` hypotheses never become event relations (R9; DEC-84 (10)).

**Purpose.** "the plane pairs assertions worth comparing, deterministically, for a viewer…; a run's machine judgement over a formed pair enters the record only as a labelled, append-only proposal. It never judges, grades, edits or closes either side" (`contradiction.md` §Purpose). Plus PRESENT/RESOLVE and the DEC-85 half-seen conflict between projects.

| `propose({run, proposals,…})` | a run's labels (`world`, `record`, `precision`, `unrelated`, `undetermined`) under a pinned prompt digest (R2) become append-only candidates | R13–R16 | built |
| Weight | `record` on K1–K4 = **duty** (never dismissed, leaves only by resolution); `world`/`undetermined` = **lead**; precision/unrelated not shown | R24 | built; **K5 and K6 are withheld as `not_shown`** until their gate arm is measured (`contradiction/derive.mjs:14–35`, `K5_GATE_MEASURED = false`, `K6_GATE_MEASURED = false`) |
| `candidatesFor({on…})`, `tensionsOn`, `contextFacts` | candidates on an inquiry/content/entity/project; marks per referent (`in_tension`, `softened`, `stale`, `qualified`, …); record facts bearing on each coordinate | R25–R28 | built |
| `unresolvedRecordOn({finding, sha})` | duties a published case must disclose, one level deep | R29 | built |
| Member acts: `dismiss`, `clarify` (`differs`/`one_wrong`/`no_difference`), `takeUp`, `resolve` | resolution kinds dissolved / corrected / genuine; acceptance basis recorded (accepted a recommendation vs unaided) | R30–R36 | built |
| `recommend` | the machine's one act: names only coordinates in which sides may differ, never which side is wrong | R37 | built |
| Measures | `acceptanceRates` (review due at ≥95% acceptance over ≥30), `dismissalMeasure` | R39, R40 | built |
| DEC-85 notices / opt-in / reveal / respond | conflicts across projects told on one's own side only | R49–R55 | built |
| Connection owner "in tension with" | a candidate is a hop in `explore`, lowest grade, a chain through it is a lead | R58 | built (T33-48) |

**Bearing.** This is the substrate's most complete "competing accounts" machinery, but it is between **assertions already in the record** (claims, legs, extents, stances, money facts), not between **explanations** of what is going on. "The contractor is late because of change orders" vs "because the district delayed approvals" is not a contradiction candidate unless two recorded claims conflict. K6 (two amounts for one transfer) is the money key a procurement investigation needs, built but not yet shown (gate unmeasured).

### 1.6 strength (layer 6) — what a claim is worth, derived

**Purpose.** "Strength is what a claim is worth, derived and never stated: a **pair** of independent measurements, the weakest capture among the documents a conclusion reaches and the weakest connection among the edges it rests on (DEC-21), with testimony beside them, never composed into one value (DEC-44)" (`strength.md` §Purpose).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `strengthOf(id)` / `inquiryStrength({id, viewer})` | per axis (capture, connection, testimony): `graded`/`unrated`/`undetermined`, the weakest member named, `not_load_bearing`, recursion through inquiry legs to depth 6; grounds AND within, OR across (DEC-32) | R1–R6 | built |
| Hunch legs | inert in every pair, counted as `hunches_left_out` (`strength/index.mjs:225,609`) | R5 | built |
| `versionStrength({id, version, project, states})` | the pair over one basis version; what-ifs over other state sets labelled as such (DEC-40); a single composed figure is refused (C-30.7) | R7–R10 | built |
| `partitionIndependence` / independence | for two or more grounds, shared origins: same document, capture or captured address; since T33 one issuing source, shared person, shared event, shared ledger table, `acts_for`/`within` tie (`strength/origins.mjs:10–177`) | R11, R12 | built |
| `candidatePair({inquiry, legs})` | the pair over a hypothetical leg set, writes nothing — what a planner would use to ask "how strong would this be if…" | R26, R27 | built (`index.mjs:1084`) though the header lists R26–R27 as *(not yet met)* at drafting time |
| Anonymous testimony | group/project-level testimony counts only beside an independent corroborating leg | R29, R30, R34 | built (`testimonyCorroboration`, `index.mjs:1111`) |
| Grading method version + `recomputePair` | `GRADING_METHOD_VERSION = "bio-grading/2"` (`method.mjs:18`); a reader recomputes a grade from the case file | R31, R32, R35 | built |
| Calculation / standard / occurrence legs | a calculation's grade is its weakest input capture; an occurrence's the weakest of its source text and trigger-date attestation; its state (`met`, `overdue`) stated beside, never moving the grade | R36–R38 | built |
| The bar | a project's declared `required_strength`, beside the pair, never a gate | R14–R16, R21 | built |

**Bearing.** An engine can ask, before proposing a step, what a proposed basis would be worth (`candidatePair`) and whether two sources are really independent (R12 — the "two documents from the same office" trap investigators name). It cannot obtain a single confidence number (R10, R18), and "Grade A on the capture axis" is never given to a rendering (R19).

### 1.7 citation (layer 6) — "this is why I think that"

**Purpose.** "Citing is one act in the record's own terms, 'this is why I think that': material, or a question, becomes part of what a case or a question rests on" (`citation.md` §Purpose). On a project a `cites` edge; on an inquiry a leg.

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `cite({project, handle, role, extent, note, author})` | a `retrieval` selection becomes legs (role required, never defaulted) with the connection grade filled only where earned; a document leg is pinned to its capture | R1–R3, R8 | built |
| `sever` / `reinstate` | status changes on a project's edges, with reason, never deletion | R4 | built |
| `retiredNotCitable(id)` | the one "may this be cited now" predicate | R5 | built |

**Bearing.** This is the act by which a document *enters* an investigation's support: a selection from search (`retrieval` R19–R20) is cited with a role. The citation lives only in the citing document's bytes (R6). There is no "add to case file without asserting it supports or cuts against" — a document is either cited as a leg (with a role) or not; holding a document as *relevant, not yet read* is a gap here (*inference*; see §4).

### 1.8 basis-versions (layer 6) — alternative accounts, frozen, chosen by members

**Purpose.** "An inquiry's basis holds several **versions**, each a complete, named, described alternative account of the support for its claim, frozen once written (INVESTIGATIVE-SESSION §6)… Every act is a member's; a machine proposes a version and holds no act that moves one" (`basis-versions.md` §Purpose).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| Version grammar | name, description, claim, relationship AND/OR, `derived_from` tree, legs, grounds; frozen (`VERSION_FROZEN`) | R1–R7, R29 | built |
| `basisVersions({id, project})` | all versions with legs, grades as bounded, who moved each and why; a project's CURRENT and stance | R8–R11 | built |
| Six acts (`versionAccept`, `Reject`, `Consider`, `Revert`, `Current`, `Hide`) | member-only (`MACHINE_CANNOT_MOVE_VERSION`); states suggested → considering → accepted/rejected | R12–R15 | built |
| `conclude` / `withdrawConclusion` | a project's conclusion = adopting its CURRENT version's claim, with falsifier or recorded override; no-project conclusion moves the question to `concluded` | R16–R23 | built (`index.mjs:965`) |
| `narrowCandidates` / `narrow` | machine-proposed narrower parts of a cited document (reference places, extract-run passages), labelled machine work; `narrow` writes a new `suggested` version | R24–R27 | built |
| `appendVersion({target, version, grounds, legs, author, run, kind})` | **the machine's door**: appends a `suggested` version (used by `run-productions`' `op=suggest`, `run-productions/index.mjs:495`, and by `reevaluation`, `reevaluation/index.mjs:2502`) | R28, R30 | built |
| `projectsDrawingOn`, `projectQuestions` | which projects draw on a question; a project's questions with `legs` and `stance` | R37, R41 | built (`index.mjs:570,608`) |
| `testimonyReach` | member observations reached through any basis, depth 64 | R39 | built |

**Bearing.** Versions are the substrate's built mechanism for **alternative accounts** of a single claim's support and the clearest existing instance of *machine proposes, member accepts*: an AI run appends a `suggested` version; only a member accepts, rejects or makes it CURRENT (R30). A version is an alternative *basis for a claim*, not an alternative *explanation of events*; a set of rival explanations of "why is the school late" would be several inquiries (or several claims), not versions of one (*inference*).

### 1.10 answers (layer 6) — the assistant's closed-book answer contract

**Purpose.** "The plane's half of the assistant: what an ask may read, what an answer must look like, and the checks every answer passes before a member sees it… The model only understands the member's words, writes queries, quotes and translates; it never answers from its own knowledge" (`answers.md` §Purpose). New in T33 (T33-53).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `ASK_SCOPE`, `askAdmits(op)` | the one closed list of plane reads an ask may make: search, look states, law, profiles, entities, people, lines, duties/occurrences, timeline, events, money (`moneyOf`, `committedAgainstPaid`), calculations, `explore`; no source ops, no member history | R1, R2 | built (`answers/scope.mjs:12`) |
| Answer shape | `{question_as_read, clarifying (null or exactly one question), summary, sentences [{text, kind quote/list/figure/absence/rule/explain, support}], holdings [{address, quote}], looks [{level, state}], query, next_acts, label "machine work"}` | R3 | built |
| `checkAnswer(answer, {readLog})` | withholds (never rewrites) each sentence that quotes what was not read (`ANSWER_CITES_UNREAD`), states an unsourced figure, a rule not from the plane, or an absence without a level | R4, R5 | built (`answers/check.mjs:199`) |
| Rule services `ruleAnswer({service, args})` | law (standard, in force), profiles, `deadlinecompute`, organisations/people, `evaluate` a recipe; each labelled `legal_information` / `procedural_fact` / `computed_fact` | R6–R12 | built, **switched off by setting** (`RULE_SERVICES_SETTING`, `answers/index.mjs:182`, refusal `RULE_SERVICES_OFF`) |
| Standing questions | a member's saved query re-run daily/weekly/monthly to an end date, no model call; "something new" = a new id or an occurrence changing state; AI half answers only with the copy's and member's switches on (off until a 150-question bar is met) | R15–R21 | built; AI half switched off (`answers/standing.mjs:173`) |
| Tallies | counts only; an ask keeps nothing else (K1450) | R13, R14 | built |

**Bearing.** This is the nearest existing thing to "the assistant reads the case and answers the member", and it fixes the shape any investigation answer should take: one clarifying question at most (R3 — a direct analogue of Bob's "maybe asks a few follow on questions", but limited to one per turn), every quote bound to a read, every figure to a calculation or money fact, every absence to a level. Its limits: an ask is **read-only and keeps nothing** (R14), makes **no capture request and no fetch** (R21), and standing questions run no model by default. An engine that "starts digging" by fetching RFPs and bids is outside `answers`' scope by design; it would need `ai-runs`/`capture-requests` (not in M1's scope) under a member's act.

### 1.11 intent (layer 7) — aspirations, goals, objectives, gaps, the discovery loop

**Purpose.** "Intent holds what the group is trying to achieve and turns it into checkable work (Content Framework §12)… Progress on an objective is computed from the record and never reported; its gaps are the work list. Unasked-for findings arrive as proposals, and only a member's act adopts one, opens a question from it, or sets it aside with a recorded reason (the discovery loop)" (`intent.md` §Purpose).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| Objective text | a project must state an `objective` | R1 | built |
| `setCondition({project, condition, reason})` | a satisfaction condition `{progression, entity, relation, filter, required {grade, stages}, satisfied {share}}` | R2 | built |
| `progress({project})` | matched / meeting / short / undetermined instances, `satisfied` true/false/null — derived, never stored | R3–R5 | built (`intent/index.mjs:453`) |
| `gaps({project})` | one gap per short instance (a missing stage names the records request; a short grade names the link to strengthen), each a **proposal** to `queue` as `objective-gap` | R6 | built (`:484`) |
| `watchSet`, `servesOf` | what `monitoring` watches; what a subject serves, for `scheduler` ordering only | R7, R28 | built |
| Goals, aspirations, dead ends | `declareGoal`, `linkObjective`, `closeGoal`; `declareAspiration`, `departFrom`, `recordDeadEnd({note})` (never removed), `retireAspiration({taught})`; `pursuitOf` (goals, objectives, triaged proposals, capture requests and their outcomes, dead ends) | R8–R14 | built |
| Discovery loop: `registerSource`, `proposals`, `triage({act adopt/question/defer/dismiss})` | a machine may only `question` (open an inquiry at `surfaced`); every other act is a member's | R15, R16 | built (`:1083,1099`) |
| `ageSurfaced` | a machine-surfaced question no member acted on within 30 days is deferred with a stated reason | R17, R27 | built (`:1196`) |
| `workObjective({project, reason, author})` | **a member opens an AI run with the objective and its current gaps as its instructions** | R18 | built (`:1297`) |
| `amount` filter over money facts | condition filter on summed money facts in exact decimals | R31 | **specified** *(not yet met: T33-58)*; no `money` reference in `intent/` at the pin |

**Bearing.** Intent is the substrate's built planning layer, and its shape is close to what an investigation needs: an objective with a computable satisfaction condition, a derived gap list as the work list, a pursuit record that keeps dead ends and triaged proposals, and `workObjective` — a member-authorised AI run whose instructions are the objective and its gaps. Its limits for investigation: a condition is expressed over a **progression's instances** (`progressions`: staged processes such as a records request or a permit), so "what is going on with the school rebuild?" cannot be expressed as a condition unless the investigation is modelled as progression instances (R4: "an objective the shape cannot express keeps its text with progress stated as not computable"). Objectives belong to **projects**, not inquiries. Aspirations "set priority and never filter evidence" (R21) — a doctrine any planner must keep.

### 1.12 project-stage (layer 8) — how far a project has come, derived

**Purpose.** "A project's stage, what each stage has earned and still needs, and its work products' readiness, derived at the read from the questions the project draws on and what it has published (State Rules §4.3; K356). It writes nothing and owns no table" (`project-stage.md` §Purpose).

| service | what | Rn | state |
|---|---|---|---|
| `projectStage({project, viewer})` | `forming` → `investigating` (a held question has a leg) → `matured` (the project concluded a held question, or owns a ratified case edition) → `closed` (owner's act with `resolved`/`superseded`/`abandoned`); `undetermined` with `at_least` past 2,000 questions | R1, R2 | built (`project-stage/index.mjs`, 383 lines) |
| Work products | each case: `draft` → `internally_checked` / `externally_compliant` (never inferred) → `distributed` | R3 | built |

**Bearing.** An investigation's "where are we" at the coarsest grain already exists and is derived, never set (R5). It is very coarse: four stages, driven by legs and conclusions, with no notion of open leads, outstanding records requests or objectives (those live in `intent` and `queue`).

### 1.13 explore (layer 5) — the one bounded, as-of walk across relationships

**Bearing.** This is the substrate's built "follow the connections" tool, designed with Bob's own seven-hop chain (donor → committee → councilmember → vote → award → contract → vendor) as its volume test (Suggestions, M-X1a). For a procurement investigation, `chain`, `flowsFrom` and `timelineOver` over the district, contractor and project entities are directly usable. It writes nothing and ranks nothing (R9, R3; D68, D91), so it cannot itself be the "case file" or say which path matters; R16 forbids words such as "conflict", "suspicious", "knows".

### 1.15 retrieval (layer 5) — search, selections, and "what nobody has looked at"

**Purpose.** "Retrieval runs the query language over the record and says what it could not see… holds a member's selections and says whether a selected set moved; answers one capture's content-axis state; and reads the frontier: per level, what was looked for, what came of it, and which subjects nobody has looked at… It mints nothing: a hit is an address" (`retrieval.md` §Purpose).

| service | inputs → outputs | Rn | state |
|---|---|---|---|
| `search({q, viewer, mode, facets, widen})` | page / ids / count with provenance columns and snippet, never a score; facet counts; an empty AND offers its OR reading | R6–R9 | built (`retrieval/index.mjs:658`) |
| `meaningRows({q, rows})` | rows of one arm (`leg`, `resolves`, `concerns`, `content`, `passage`) with the **four-level absence statement** (internet / document / content / meaning) and, for passages, how many captures were never read | R10–R15, R54 | built (`:735`) |
| Selections `selectionCreate` / `selectionResolve(weight)` | a server-side set (≤10,000 ids, 300 s lease) that an act refers to by handle; drift reported; `refuse` weight refuses a moved set (`SET_MOVED`) | R18–R22, R59 | built |
| `contentAxis({captureSha})` | whether a capture has been extracted and indexed, kept as two axes | R23–R27 | built |
| `frontier({level})` | per level (`document`, `content`, `meaning`, `internet`): what was looked for, its state, when last verified, and **`never_looked`** subjects (addresses linked but never fetched; captures never read; references never matched; leads never followed), each with the causes not ruled out | R35–R50 | built (`:1405`) |
| `listBundles`, `buildIndex`, gated `image`/`file` | the roster and gated whole-bundle reads | R63–R66 | built |

**Bearing.** The frontier is the substrate's built answer to "what have we not yet looked at?", which an investigation planner needs at every step: the addresses a captured RFP links to but nobody fetched (document level, `never_looked`), captured documents nobody has read (content level), names nobody has matched to an entity (meaning level), leads nobody has followed (internet level, R47–R48). It is a list, not a plan: it does not say *why* a subject matters to a given question (*inference*). Selections are the handle by which a set of search hits is cited or disposed of (`citation` R1, `inquiry` R20).

### 1.16 reevaluation (layer 7) — when what a finding rests on changes

**Bearing.** This is the iterative half of "an investigation is an ongoing, iterative process": when a newer status report is captured, a bid document is superseded, a cited case is corrected or a contradiction marks a side stale, the findings resting on it are told, by derivation, and only a member moves anything (R19). The cause the school-rebuild case most needs — a schedule **event's date moved** (R34) — is the one not yet built. The obligation is per *finding/dependent*; there is no "what changed in my investigation since I last looked" digest across a whole inquiry tree beyond what `queue` assembles (*inference*).
