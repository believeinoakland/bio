## M-164 · 2026-09-25 · D-465 — what D-447's viewer-visible relevance costs a search, at a real instance's size

**Verdict: no fix is owed at the size any instance this project can reach has today.** At the live instance's size (31
indexed documents) D-447's `visibleBm25` adds 3–7 ms to a search in which EVERY document matches, and 36–67 ms if every
one of those 31 documents were 20,000 words long. A live search of the real record that matches all 31 documents takes
~20 ms more than one that matches none, on a ~135 ms network floor. The 210 ms figure is real, but only at 2,000
matching documents, and D-447's worker's own M-122 says so. Which of those holds for a future instance depends on its size,
and the scaling is recorded below so the figure can be taken again with the kept instrument, not recalled.

### NEGATIVE CONTROL: declared, and what came back

**Declared by the row:** the measurement at 2,000 documents reproduces M-122's 210 ms figure within a stated tolerance,
before any fix. I stated no tolerance before the first run, so the comparison below was made after it. That is recorded here, not smoothed over.

- **The ABSOLUTE figure did NOT reproduce:** 142.2 ms at 60 words (−32%) and 180.2 ms at 200 words (−14%), against
  210.1. The pre-D-447 baseline did not reproduce either: 20.8 / 30.3 ms against M-122's 73.9. M-122's corpus text and
  document length are not recorded, and its bench was not kept. The 200-word run shows the figure moves with document length, so
  an absolute match was never available without M-122's fixture. The machine may also differ, and that is UNDETERMINED.
- **The ADDED cost DID reproduce:** +121.4 ms (60 words) and +149.9 ms (200 words) against M-122's +136.2 ms, within
  ±11%. The added cost is the quantity this row is about.
- **The instrument discriminates the subject:** reverting `query.mjs` alone (one variable, the same tree otherwise)
  moves `q=culvert` at 2,000 from 142.2 to 20.8 ms and makes three-term cost flat in term count (22.5 against 296.3).
  An instrument that could not see D-447 could not print that difference.

### Why no fix is owed, and what the fix would cost if one becomes owed

At 31 documents the worst case (every document matching) adds 2–7 ms at 60 words and 7–14 ms at 2,000 words. That is
under the spread of a single live request (133–151 ms for the zero-match floor). It would take roughly 250 matching
documents of fixture length for the three-term case to add ~37 ms, and ~2,000 to add ~270 ms. The row's order (SCHEDULER #17)
is *fix only if it matters at real size*, and at real size it does not.

The fix the row names is an `fts5vocab` `instance` table. SQLite's documentation claims it yields one row per token occurrence (term,
doc, col, offset). That is the vendor's claim, NOT measured here, and it is also NOT measured whether workerd's SQLite
builds `fts5vocab`. It would count single TOKENS. `visibleBm25` counts the phrase instances `highlight()` marks
for each FTS5 atom, and those include phrases (adjacent offsets) and prefix atoms (a term range). A byte-identical
order would therefore need a phrase join and a prefix range per atom, not a single lookup. That is a larger change than the row
describes, and it is recorded here so that whoever builds it measures it against this table first.
