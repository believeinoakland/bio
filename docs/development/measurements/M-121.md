### Instrument

`tools/measure-drive-export.mjs`, landed with this entry.

- **Fetching.** Each fetch is `POST op=acquire` with `store=scratch` named on every call (CLAUDE.md §5, D-325), on
  **biosmoke7 serving 0.78.0**. So the fetch goes through the **plane's own egress** and its Drive arm. The plane
  composed the export address itself (D-112); the instrument composed nothing.
- **Reading back.** The bytes are read back with `op=capture`. Each read-back is **checked against the sha256 the
  acquire returned**; a mismatch is refused as `READBACK_DIGEST_MISMATCH`, and none occurred.
- **Reading the text.** The text is read by the **plane's own** `odtEntry` and `odsEntry` (`bio-plane/src/odf.mjs`).
  "Stable" therefore means stable as the product reads it, never as a second extractor would.
- **Comparing.** Takes are compared by sha256 of the extracted text. The `content.xml` and whole-package digests are
  kept only to say whether D-351 reproduced.
- **Refusals.** A body that is not the asked-for ODF package is **refused by name** and never scored:
  `SHELL_TEXT_HTML`, `NOT_AN_ODF_PACKAGE`, `NOT_THE_ASKED_FORMAT` or `TEXT_UNREADABLE`. So is a plane refusal
  (`PLANE:<reason>`). A target with fewer than 2 readable takes is **UNDETERMINED**, never stable and never unstable.
- **Pacing.** 6 s between calls, on top of the plane's own governor. D-111's rule applies: no rate is probed.

### The `.odt` `content.xml` diff class, measured on 2 of the 5 targets (not all 5)

not claim to know what differed there.

- **For D-351's evidentiary digest:** on this evidence, the `.odt` normalisation D-351's scope calls for is

### Fidelity: UNDETERMINED for every format, and why

The row asks for fidelity "against the Drive-rendered text where a reference rendering exists". **None was
reachable:**

1. **This container cannot reach Google.** `curl https://docs.google.com/document/d/…/export?format=odt` →
   `CONNECT tunnel failed, response 403`, 2026-09-23 22:40:30Z. The agent proxy denies the host, and
   `www.oaklandca.gov` and `webapi.legistar.com` are denied the same way.
2. **The plane's egress cannot fetch a non-ODF rendering, by design.** `readDriveAddress` turns any
   `docs.google.com/<kind>/d/<id>/…` locator into the ODF export address (D-112: the export address is composed,
   never taken from a caller). So `export?format=txt`, `csv` or `html` is not reachable as a reference through
   `op=acquire`.
3. **Any Google-served reference would be another Google conversion**, not an independent one. The reference that
   would be independent, the publisher's own original file, exists for none of these targets in the record.

So fidelity is UNDETERMINED, and not "fine". Stability across fetches is **necessary** for a calibrated letter
but **not sufficient**: a conversion can be perfectly repeatable and still wrong the same way every time.

### What this measurement CANNOT see

- **N and time.** 6 takes per target over **13 minutes on one day**. A drift over days, a Google-side change in the
  converter, and edits the owner makes to the document are all unobserved. A change in text between days would be
  real content change or converter change, and this entry cannot tell those apart.
- **Scope of the text.** Only what `odtEntry` / `odsEntry` extract is compared. Formatting, list numbering, comments,
  tracked changes, formulas, hidden sheets and the `Fonts/` members are outside it. Text stability says nothing
  about them.
- **Population.** 8 readable targets from one corpus. The census's PDF half is a **3.6 % sample**, so Drive links in
  the other 96.4 % of the PDFs were never found (M-13's blind spots (a)–(f) all carry over). **50 links is a floor.**
- **One egress, one instance, one account.** Access narrower than "anyone with the link" was never exercised.

### A defect found on the way: D-459

**`op=acquire` reports `existed: true` for every first-time single-part capture.** In every one of the 48 takes,
three digests per target per run were new and yet `existed` read `true`.

- **Cause** (`bio-plane/src/index.mjs`, the acquire streaming path). `flush()` writes the single part to
  `${store}/captures/${psha}`, and for one part `psha` IS the whole-body sha. Only afterwards does
  `existed = !!(await env.CAPTURES.head(\`${storeName}/captures/${sha}\`))` run, so it finds the object the same call
  just wrote.
- **Why no suite caught it.** `test/acquire.test.mjs` asserts only the idempotent half ("acquiring the same document
  again … `existed`, true") and never that a first acquire answers `false`, so it asserts an equality that costs
  nothing.
- **Why it matters.** The record claims "we already held these bytes" about bytes it had never seen, which is the
  overclaim direction. Anything that uses `existed` to mean "a re-fetch corroborated an earlier capture" is misled.
- **FIX NAMED:**
  - Take the `head()` inside `flush()` before the part is written: it already runs there as the write guard. Carry
    its answer out for the single-part case.
  - Add a first-acquire arm asserting `existed === false` beside the idempotent one.
  - Negative control: move the `head()` back after `flush()`, and the new arm must fail by name.
