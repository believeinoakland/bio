**The index finding, and why it is measured rather than assumed.** SQLite carries a table's indexes through `ALTER TABLE …
RENAME`, under their old names. The schema's `CREATE INDEX IF NOT EXISTS reading_refs_ref` then finds the name taken and
creates nothing, and the interim table's DROP removes the index — a re-keyed table with no lookup index, failing nothing.
The control arm `noindexdrop` (the two `DROP INDEX IF EXISTS` removed) turns exactly one assertion red, the
indexes-on-the-new-table arm (38/1), which is the evidence the trap is real and the migration closes it.

**Why the count is small, stated.** Three rows is a fixture, floored in the suite (`>= 3`) so the equality cannot pass over
an empty table. The migration is one `INSERT … SELECT` over the whole table with no WHERE and no LIMIT and an old key that
is a subset of the new one, so no row can be refused by the new key; `INSERT OR IGNORE` is there for a boot that died
between the copy and the DROP, and drops nothing on a first run (the equality above is that run).
