Refused BY NAME, never decoded (each asserted on the code AND on the process it names): progressive
(`progressive-huffman`, SOF2), arithmetic (`extended-sequential-arithmetic`, SOF9, cjpeg `-arithmetic`), CMYK
(4 components), and a stream cut to half its length (`TRUNCATED`: 6,949 bits would have been zero-filled — libjpeg
fills them and warns; this decoder refuses).

**Why "pixel-exact" was reachable at all, and it is the design rather than luck.** JPEG decoding is not
bit-defined by the standard. The decoder copies libjpeg's integer arithmetic step by step — `jidctint.c` ISLOW with
the post-IDCT range table's wrap, `jdsample.c` FANCY upsampling with `jdmainct.c`'s replicated context rows,
`jdcolor.c`'s SCALEBITS-16 tables, `jdapimin.c`'s colour-transform rule — so the digests agree on the first run over
every case above. **A decoder that merely conformed would have produced a picture whose `pixels_sha256` no
independent decoder reproduces**, which is the property DEC-41's published-rendering hash depends on (D-246).
