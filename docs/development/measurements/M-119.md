## M-119 · 2026-09-23 · D-74: Oakland's shared identifier spaces, the first measurement (Framework §8.3, CONSTRUCTS Step 5a) (D-74; minted on its clone as M-117, which collided with D-178's M-117, and RENUMBERED M-119 by CONDUCT #18 with `node tools/mintid.mjs M` at c17-batch7)

**What this measures.** For each of Framework §8.3's five identifier classes: which City of Oakland systems publish a value
of it, how many distinct values each system showed (N), and whether ONE value appears in TWO systems with the SAME referent.
Recorded per institution and per system, the way a host stack is recorded per host. **Nothing was built.** A shared
identifier found here is a FINDING; building on it is its own row, designed by BOB.

**The one-paragraph answer.** Three of the five classes were seen in two Oakland systems at least once: **project number**
(budget ↔ Legistar, 7 values, every referent agreeing), **fund code** (budget ↔ Legistar, 3 values; and budget ↔ budget
across ten years, 34 values), **resolution/ordinance number** (Auditor ↔ Legistar, 1 value). **Contract/PO number and APN
are UNDETERMINED**: the systems that assign them (the procurement system, the county assessor, the permit system) were not
read, and nothing below is evidence that they are not shared. The sample is small and was captured for ONE inquiry (the sewer
fund), so every "found in one" or "none" below is a statement about THIS sample, and says which systems were not sampled.

### The instrument

- **Corpus: the record, not the web.** This container's egress refused every Oakland host (below), so the corpus is what BIO
  already holds: every bundle in store `bio` on instance `biosmoke7` (31 bundles), read with `op=list`, `op=image` and
  `op=capture` (GET, read-only; member token; nothing written). **Every one of the 31 blobs was checked against its sha256
  on arrival: 31/31 matched.** The captures were taken by the plane on 2026-07-19 (the budget book FY23-25 on 2026-07-21, the
  calendar on 2026-07-30). So the sample's DATE is those capture dates; the matching was done on 2026-09-23.
- **Text:** PDFs through `pypdf` 6.19.0 (Python 3.11.15), page by page, 0 page failures; HTML by stripping tags; the
  Legistar JSON and the Open Data CSV read as STRUCTURED rows (the `MatterEnactmentNumber` field; the `Fund Code` and
  `Project Code` columns), plus the text of every matter title.
- **Matcher:** `tools/m119-idspace.py <corpus-dir>` at this commit. Per class, a pattern for how Oakland writes the value
  (below). **A value counts as SHARED only when the SAME normalised string is in two different Oakland systems**, and for
  fund codes only when the two occurrences' LABELS share a word (a four-digit fund code collides with years). Normalisation
  folds the marker's spelling (`C.M.S.` = `CMS`) and NEVER digits: a leading-zero variant is a DIFFERENT value, printed as
  a NEAR-MISS and never counted. Every counted project and resolution match was then READ by hand for referent agreement
  (below).
- **What the matcher can and cannot see.** It sees values written in the forms below. It cannot see: a value in an image
  (two Legistar PDFs have no text layer); a value written in a form it has no pattern for; a contract number not introduced
  by "Contract/Agreement/Purchase Order/P.O. No./#"; an APN not in Alameda's `ddd-dddd-ddd(-dd)` form or after "APN". A
  four-digit fund pattern also catches YEARS and resolution numbers — those are printed, counted in N, and named below.

| class | the pattern (and the structured field where there is one) |
| --- | --- |
| contract / PO | `(contract\|agreement\|purchase order\|p.o.) (no.\|number\|#) <value>` |
| project | a letter + 5–6 digits (`C329142`); `project [no.\|number\|#\|code] <[letter]5–7 digits>`; ODP column `Project Code` |
| resolution / ordinance | `<4–5 digits> C.M.S.` in any spelling; Legistar `MatterEnactmentNumber` |
| APN | `ddd-dddd-ddd[-dd]`; `APN <value>` |
| fund / account | `<code> <Name> Fund`; `<Name> Fund (<code>)`; `Fund [No.] <code>`; ODP column `Fund Code` (+ `Fund Description`) |

### What a match has to show to count — and what these do and do not show

A value found in two systems counts only when (1) the string is identical, (2) the systems are different SYSTEMS rather than
two publications of one, and (3) the referent agrees, read in both places. **A class is a shared identifier SPACE only when
that holds for many values, across different subjects, with no referent disagreement** — a handful of matches in one
inquiry's documents is a lead, not a space.

- **Project number, ODP ↔ LEG: the strongest finding.** 7 of 7 matches agree on referent, read by hand (every Legistar
  award title names the same streets as the budget line's description; C329142's title names West Grand Avenue between Wood
  and San Pablo AND 20th Street, the budget line names the first). The two are genuinely different systems: the budget's
  project code and the council's award resolution. The same Legistar titles also carry the contractor and the enactment
  number, so this one identifier walks **budget line → council award → contractor**, which is exactly the
  need-to-signed-contract progression §8.2 names. N is 7, all sewer rehabilitation, all FY13-15: **a lead, not yet a
  space.**
- **The project number space has at least TWO FORMATS.** The FY13-15 budget writes a letter + six digits (`C329142`); the
  FY23-25 budget book writes seven digits (`1006635`); Legistar carries BOTH, and they do not overlap in time: the C-form
  in 102 matter titles introduced 2000-10-17 to 2016-11-16, the `100xxxx` form in 33 introduced 2017-02-21 to 2023-11-07
  (by `MatterIntroDate`, else `MatterAgendaDate`). So the format changed between late 2016 and early 2017, in this sample. FIN's 8 new-form values and LEG's 30 new-form values did not intersect in this sample, and no crosswalk between the
  forms was seen. Whether one exists is UNDETERMINED.
- **Fund code: stable, but the 34 need a caution.** FIN (the FY23-25 and FY25-27 budget books) and ODP (the FY13-15
  budget CSV) agree on 34 codes with agreeing names ten years apart — `1010` General Fund: General Purpose, `3100` Sewer
  Service Fund, `3150` Sewer Rate Stabilization, `4100` Equipment, `2415` Development Service Fund, and so on. **But both
  are publications of ONE source, the city's budget system**: that shows the code is STABLE across a decade, not that two
  systems share it (*several documents agreeing is usually one source copied*). A further 21 values matched as strings with
  labels the heuristic could not align (mostly budget-book notes that cite "Fund 2108" with no name); they are printed and
  NOT counted. The cross-SYSTEM evidence is budget ↔ Legistar: 3100, 4100, 7760, each with agreeing names in staff reports
  and matter titles. **The ACFRs carry NO fund codes** (their 2 candidate strings each are years): the audited statements
  name funds, never number them, so an ACFR ↔ budget link through a fund rides on its NAME alone.
- **Resolution / ordinance number: one match, and a structural lead.** 13035 agrees on subject and date in both places.
  Legistar ASSIGNS these numbers (`MatterEnactmentNumber`), and the ACFRs and budget books cite them by the same
  `NNNNN C.M.S.` form (13279, 13487, 83679, 83680, 87551, 88717, 59916…). None of FIN's 14 was in the Legistar sample —
  **because the Legistar sample is only matters whose title contains "sewer"**, not because they are absent. That is the
  single most promising unmeasured pair: ACFR/budget ↔ Legistar through the C.M.S. number.

### Negative control

Declared before running. MUST match: a value planted in two systems; the same resolution number spelled `C.M.S.` in one
and `CMS` in the other (the over-strictness arm). MUST NOT match: `3100` against `03100`; APN `…-018-00` against `…-018-01`;
a four-digit string whose two labels disagree (a year against a fund).

- **Synthetic** (`tools/m119-idspace.py --selftest`): GREEN 6/6.
- **On the real corpus** (`--plant`): `99917` planted in LEG as `99917 C.M.S.` and in FIN as `99917 CMS` → SHARED, LEG+FIN.
  `9917` in LEG against `09917` in FIN → NOT counted, printed as NEAR-MISS `9917 [LEG] ~ 09917 [FIN]`. Every other figure in
  the output unchanged (fund SHARED stays 34).
- **Arm A — the fund label check disarmed** (`label_agrees` returns True): RED 5/6, failing at the named check *fund 2010
  with disagreeing labels does NOT count*; the other five pass, as declared.
- **Arm B — normalisation strips leading zeros**: the FIRST run was RED 5/6 **but the check "03100 does NOT match 3100"
  PASSED under the arm.** That check was vacuous: a matcher that folds the zero files `03100` under the key `3100`, so the
  key `03100` never exists to be found. Only the near-miss check caught the break. The assertion was corrected to what it
  meant (FIN's occurrences under `3100` must number exactly 1), with a comment saying why the old one was wrong. Re-run:
  RED 4/6, failing at *03100 does NOT match 3100* and *03100~3100 printed as NEAR-MISS*. Arm A re-run on the corrected file:
  RED 5/6 at the same named check.
- Every restore verified by sha256 and `cmp` against a per-arm pristine copy (12,868 bytes, `322fcb95…`); selftest GREEN
  6/6 after; the real-corpus output byte-identical to the run before the correction.
