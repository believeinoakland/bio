## M-167 · 2026-09-25 · D-473 — IS A GOOGLE `.odt` / `.odp` EXPORT'S content.xml BYTE-STABLE ONCE NORMALISED? A FRESH PUBLIC POPULATION, TWO ROUNDS APART

D-473 (owner CAPTURE). This entry re-measures D-351's `.odt` normalisation, which was never re-measured. M-123 proposed it
on 2 census documents: strip `xml:id` on `text:list`. The earlier worker's pull of CAP-11's scratch captures was
**refused (PII)**. This entry does **not** route around that refusal: it reads **none** of CAP-11's captures and
**none** of M-123's census targets. It uses a fresh population, chosen as described below.

**Headline.**

- **`.odt`.** 8 public government Docs, each fetched twice about 38 minutes apart.
  - Raw content.xml differed on **5 of 8** pairs. Relabelled by `odtNormalisedContentXml`, it is byte-identical on
    **6 of 8**.
  - On every pair that carries a list, the only list difference is `text:list@xml:id`: 8 spans over the 3 Docs that
    have lists.
  - The 2 pairs that stay unstable differ **only** in `draw:frame@draw:name`. Google names embedded images
    `imageN` in a per-export order. Both Docs reference `Pictures/` members, so D-351's member rule already refuses them.
- **`.odp`.** 8 public government Slides decks. content.xml is **raw byte-identical on 8 of 8 pairs**, with no
  normalisation.
- **What the product claims on this population: nothing, for every target.**
  - `odfEvidentiaryDigest` answers UNDETERMINED on all 16.
  - For `.odt` the reason is that **every** Google Doc export here embeds its fonts: 8–9 `Fonts/font*.ttf` members,
    referenced by `svg:font-face-uri`. The member rule refuses those references. That is **D-612**, minted by this
    item and not built here.
  - For `.odp` the reason is the stated undetermined below.

### Verdict, stated on the figure

- **`.odt`: WIDENED.** `ODF_EVIDENTIARY_MEASURED.odt` is set in `bio-plane/src/odf.mjs`. The digest is taken over
  content.xml normalised by `odt-list-ids v1`:
  - each `xml:id` on a `text:list` start tag is relabelled `L1`, `L2`, … in document order;
  - every `text:continue-list` naming a relabelled id is rewritten to match.

  **Why relabel rather than the row's literal "strip".** Stripping would leave a `text:continue-list` naming a random
  id, so the digest would stay unstable on any Doc that continues a list. The suite's STRIP control arm shows exactly
  that. Stripping both the id and the continuation would fold a real change, which the ERASE arm shows.

  **In the field this changes nothing until D-612 lands**: every real Doc read here is refused for its embedded fonts.
- **`.odp`: STATED UNDETERMINED.** The raw figure is 8 of 8, but it does not carry the widening, for three reasons:
  1. The population is not a census population.
  2. **Every** deck in it references a package member (images), so no pair exercised a digest the widening would
     claim.
  3. The plan's note for D-473 asks for a census target first.

  **The census target that would widen it**: a `docs.google.com/presentation/d/<id>` link found in COFF-6's census by
  `python3 tools/measure-office-corpus.py drivelinks` (M-13's instrument; M-123 found 0 in the 3.6 % PDF sample).
  Then two rounds of this instrument over it, on a deck whose content.xml references no package member.

### Instrument

`tools/measure-odf-stability.mjs`, landed with this entry.

- **`fetch`.** One `POST op=acquire` per target, with **`store=scratch` named on every call**. It ran through the
  plane's own egress and Drive arm, on **biosmoke7 serving 0.79.0** (`/version`, read on every take).
- **Read-back.** The bytes are read back with `op=capture` and checked against `document.capture.sha256`.
  - A capture over the 8 MiB part bound is read part by part, each part checked, and the whole checked again.
  - This path was added after round 1 refused 3 decks as `READBACK_DIGEST_MISMATCH`. The first draft had read only
    part 0 of a two-part capture: a fault of the instrument, not a difference in the bytes. Those 3 decks are paired
    from rounds 2 and 3, and the pair used is printed per target.
- **`derive`.** For each pair it computes:
  - raw content.xml equality;
  - the **candidate**: sha256 of content.xml through the plane's own `odtNormalisedContentXml` for `.odt`, raw for
    `.odp`;
  - the **product** verdict (`odfEvidentiaryDigest`);
  - the **diff class**: the element and attribute NAMES whose values differ, with counts.

  It never records a text run or an attribute value, and the log holds digests, counts and names only. The fetched
  packages stayed in the session scratchpad and were not committed.
- **`control`.** 15/15 passing, exit 0.

### A defect found on the way: D-612

**Every Google Doc export references its embedded fonts, so the `.odt` digest is refused on every real Doc.**

- **Cause.** `referencedMembers` in `bio-plane/src/odf.mjs` treats an `svg:font-face-uri xlink:href="Fonts/fontN.ttf"`
  like an image reference, and the digest is refused naming `Fonts/font1.ttf, …`.
- **Why it is presentational.** A font face is presentational, the same judgment §5 already licenses for `styles.xml`,
  which is discounted.
- **FIX NAMED.**
  - In `referencedMembers`, do not count an href carried by a `font-face-uri` element (by local name) toward refusal.
    References to `Pictures/` and `Object N/` still refuse.
  - Add an arm where a real-shaped `.odt` with `Fonts/` members and no image reads **determined**.
  - Negative control: count font refs again, and that arm fails by name.
- **Owner:** CAPTURE. Minted with `node tools/mintid.mjs D` and sent to SCHEDULER. **Until it lands, the monitor's
  false "changed" alarm for Google Docs survives**, which is the goal D-473's note named.
- **Built by D-612, 2026-09-25** — see the addendum at the foot of this entry.

### Addendum, 2026-09-25 · D-612 — the font faces discounted; what moves on this population

**Built.** `referencedMembers` in `bio-plane/src/odf.mjs` skips an element whose local name is `font-face-uri`
(`PRESENTATIONAL_REF`). Every other href-bearing element is still counted, so a `draw:image` naming `Pictures/…` or a
`draw:object` naming `Object N/` still refuses. The suite's section 6 (`d473-odt-evidentiary.test.mjs`) drives it
through `op=acquire`: a real-shaped Doc (8 `svg:font-face-uri` → 8 `Fonts/` members, font bytes differing per
export, no image) reads **determined** with one digest across two exports; the same Doc with one picture **still
refuses**, naming the `Pictures/` member and only it; a `font-face-uri` under another prefix reads determined.

**The moved count on THIS population: NOT RE-MEASURED, and why.** The row asked for the 8 Docs to be re-read through
the plane, read-only. That cannot be done from what the record holds:

- This entry committed only **truncated** file ids (`1aJYj4NbsFYX…`), and the target list and fetched packages stayed
  in D-473's session pen, which is gone. The Docs cannot be re-addressed.
- The 36 captures are still in `store=scratch`'s R2, but no read-only op lists them: `capturedLocators` is not wired
  to an op (REC-26, deliberately), `op=tasks` reads 0 (the 36 tasks sit undrained in `task_queue`, and draining
  would write), and `op=capture` needs a sha this entry did not record.

**What the recorded table says instead, labelled as a reading of it, not a measurement.** Reading the `refs` column
above through the new rule: the 4 Docs whose only references are `Fonts/` (`1aJYj4Nb…`, `1jZcxvXs…`, `1fdT5r3t…`,
