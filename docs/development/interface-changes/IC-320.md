## IC-320 · I3 + I5: THE REQUEST TO JOIN (Membership v2 §7.14, step 2) — ask, withdraw, an owner's grant (writes `invited`, never `joined`) or decline, the lapse when a project goes hidden, and the requests read · ACCEPTED 2026-09-25, MAJOR — I3 126.0.0, I5 7.8.0 (MINOR) (resolved by CONDUCT #22 at c22-batch29; REC-150)

- **Interfaces:** I3 (four new ops; one changed answer shape on `op=projectdirectory`; one new field on
  `op=projectvisibilityset`'s answer) and I5 (one new table, `project_join_requests`, before the `host_governor` block,
  with a partial unique index; cleared by both purge arms).
- **Classification (the integrator's):** proposed MINOR for I3 with ONE removal the integrator must weigh:
  `op=projectdirectory` no longer carries its `requests: "NOT_BUILT: …"` field, and each row's `request` is now
  `null | { state, asked, closed }` where it was always `null`. No consumer reads either (measured below), and the field
  said the request was not built, which is now false. I5: additive.
- **New ops** (all four `classes: ["admin","member","probe"]`; the three acts are in `PROJECT_ACTIONS`, so `by` and
  `viewer` are the server's stamps; the read takes the viewer stamp and the `by` stamp):
  - `op=projectrequest&projectId=[&comment=]` (mutating) → `{ ok, projectId, name, state:"open", comment, asked, detail }`.
    Only at EXISTENCE sight. NONE (hidden, absent, not a project) → `NO_SUCH_PROJECT`, byte for byte as a never-minted
    id; FULL (participant, administrator, founder) → C-95.2 `PROJECT_REQUEST_NOT_OUTSIDE`; no member behind the
    credential → C-95.1 `PROJECT_REQUEST_NEEDS_A_MEMBER`; one already open → C-95.3 `PROJECT_REQUEST_ALREADY_OPEN`.
  - `op=projectrequestwithdraw&projectId=` (mutating) → `{ ok, projectId, state:"withdrawn", closed }`; C-95.1; nothing
    open → C-95.4 `PROJECT_REQUEST_NONE_OPEN`, ONE answer whatever the id names.
  - `op=projectrequestanswer&projectId=&handle=&answer=grant|decline[&comment=]` (mutating) → `{ ok, projectId, handle,
    state:"granted"|"declined", comment, closed[, participation:"invited", detail] }`. Sight before position (C-70.1 at
    EXISTENCE, `NO_SUCH_PROJECT` at NONE); not an owner → C-95.5 `PROJECT_REQUEST_ANSWER_NOT_THE_OWNER` (administrators,
    the founder, machines); another word → C-95.6; no open request from that handle → C-95.4; a grant to an inactive
    requester → C-95.7, to one already a participant → C-95.8 (the request stays open in both). A GRANT writes
    `project_participants` `(state 'invited', owner 0, invited_by = the granting owner)` — the row `op=projectinvite`
    writes — and never `joined`.
  - `op=projectrequests[&projectId=][&limit=]` (read) → with `projectId`: `{ ok, own:false, projectId, requests[{handle,
    comment, state, asked, closed_by, closed_comment, closed}], count, limit, truncated }` to an owner or an administrator
    (the founder included); another participant → C-95.9 `PROJECT_REQUESTS_NOT_VISIBLE`; EXISTENCE → C-70.1; NONE →
    `NO_SUCH_PROJECT`. Without: `{ ok, own:true, requests[{project, name, comment, state, asked, closed_comment, closed}],
    count, limit, truncated }` — the caller's own, `name` as shown when asking, never the answering owner; C-95.1 for a
    credential with no member. Bounded by `Store.PROJECT_REQUESTS_LIMIT` (200; the caller may lower it), `truncated`
    measured one row past the cap.
