## IC-403 · I3: a RATIFIED case document's sha is a published hash — `op=verify` answers `published:true` with kind `case_document`, and `op=publishedbytes` serves its bytes · **PROPOSED 2026-09-25, additive (the proposer's reading; CONDUCT classifies)**

- **Interface:** I3 (the public verify and read surface). I5: no table or column changes. `published_shas` gains rows of a new `kind` value, `case_document`, in the existing columns.
- **Design:** `docs/architecture/BIO_Publication_v0_1.md` §4, "A ratified case document's hash is a published hash". The ruling is BOB #36's of 2026-09-25 11:50Z on D-731, part (b).
- **Proposer:** the D-734 worker, 2026-09-25, branch `land/worker/D-734`, stacked on `land/worker/D-712` @ f10b1024. **Owner:** RECORD.

### What a caller sees

| read | before | after |
| --- | --- | --- |
| `op=verify&sha256=<a ratified case document's doc_sha>` | `{ok:true, published:false, matches:[]}`. The public page's sentence for that answer says the hash was never ratified. | `{ok:true, published:true, matches:[{bundle_id:<case id>, path:"case-document-edition-<n>.md", kind:"case_document", published:<ratified_at>}]}` |
| `op=publishedbytes&sha256=<same>` | 404 `NOT_FOUND` | 200. The body is the signed case document's bytes (`case_documents.text`), re-hashed to exactly the sha before they are sent. The headers are `x-published-kind: case_document` and `content-disposition` `<case>-case-document-edition-<n>.md`. |
| `op=publishedbytes&sha256=<same>&format=zip` | 404 `NOT_FOUND` | 400 `NOT_A_CONTAINER`, the existing answer for any part that is not a manifest |
| `op=publishedmanifest` → `shas[]` | bundle parts and `MANIFEST.json` | adds one `case_document` row for each ratified edition |
| `op=verify` / `op=publishedbytes` for an UNSIGNED document's sha | not published / 404 | unchanged |

- **One new refusal code.** `CASE_DOCUMENT_UNSERVABLE` (HTTP 500) at `op=publishedbytes` means the hash is registered, but the store's bytes do not re-hash to it. It is never `NOT_FOUND`, because that code's sentence would call the hash never ratified. No op can reach it: every writer of `case_documents.text` recomputes `doc_sha` beside it, and a ratified row is never rewritten. It is minted bare, in arm F's F6, beside `NOT_A_CONTAINER` and `MANIFEST_UNREADABLE` at the same op. `check-refusal-codes.mjs` moves census 730 → 731 and untranslated 280 → 281, from its own print.
- **Rows for editions ratified before this landed.** A boot pass in `Store`'s migration writes the missing rows. It uses only values the record already holds: the signed `doc_sha`, the text, and `ratified_at`. It writes only where no row exists, so later boots write nothing. `d734-casedoc-published.test.mjs` §1 and §4 drive this.

### Classification (the proposer's; CONDUCT decides)

- **I3 additive (MINOR).** No op, argument, key or status is removed or renamed. The one answer that changes value is `published`: it goes `false` → `true`, and only for a hash the group signed, which is the correction BOB #36 ruled. By IC-25's test, no request that answered `ok:true` now answers `ok:false`. A new `kind` value is a value added to an open vocabulary.
- **Measured consumer impact, 2026-09-25, on this tree** (`git grep` for `.matches`, `x-published-kind`, `op=verify` and `publishedmanifest` over `*.mjs`, `*.js` and `*.html` outside `node_modules`):
  - `civicos-ui/app.html` `pubVerify` (the public verification surface) renders `matches[0]`'s path, kind and bundle id. For a case document it will now say PUBLISHED, naming `case-document-edition-<n>.md (case_document) in CASE-…`. The kind is printed as its raw token, the same way `manifest` already is. **For UI:** the words for that token are a follow-up, and so is the optional switch of D-731 (a)'s button from `op=casedocument` to `op=verify`. Neither is required by this row.
  - `pubVerifyCaseDoc` does not read `op=verify`.
  - `civicos-ui/check-mock-envelope.mjs` pins `verify`'s envelope `{ok:true, ...out.result}`, which is unchanged.
  - `newgroup/` and `tools/` never call either op.
  - This repository cannot measure a third-party verifier that treated `published:false` for a case document's sha as meaningful. That is stated here, not scored zero.

### Evidence

- `bio-plane/test/d734-casedoc-published.test.mjs`: 12 pass, 0 fail. It first reproduces the false answer on a plane booted without the registration, then drives the backfill on reboot, the committer path, the unsigned document, `format=zip`, the retry, and idempotence across boots.
- `civicos-ui/test/draft-binding.test.mjs` §7: 72 pass, 0 fail. The six ratified editions each answer `published:true`, kind `case_document`, and `publishedbytes` bytes hashing to the signed sha. An unratified document's sha still answers not published.
- **Negative control:** four arms, recorded in both suites' headers. (A) With the registration skipped, draft-binding falls to 60/12, and every failure is one of the six editions' two rows. (B) With the backfill removed, the new suite falls to 8/4. (C) With corrupted bytes, 10/2 and 66/6, the publishedbytes rows only. (D) Re-spelling the path leaves both suites green.
