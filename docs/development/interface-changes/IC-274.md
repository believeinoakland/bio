### Why, in one paragraph

D-64's allowance claimed a bound it did not hold, and CONDUCT #20 diagnosed it at integration: `renderAdmit` admitted
while `spent_ms < allowance`, but the render RUNS IN THE WORKER and `renderSpend` adds its cost afterwards through a
SEPARATE dispatch arrow, so every render in flight at once was admitted against the same `spent_ms`. The overrun was
(renders in flight) x (one render's maximum time), whose first factor nothing bounded. A record that claims more than it
can support is the worse defect (CLAUDE.md §2), so the docstring was corrected in place at integration and the fix
placed as D-492.

### The change, on the wire

- **I5 — `render_allowance` gains `reserved_ms INTEGER NOT NULL DEFAULT 0`**: browser time COMMITTED to renders now in
  flight and not yet reported. Added to an existing store by `store.mjs` `#migrate`'s `ADDITIVE_COLUMNS` pass (both
  passes, guarded on `PRAGMA table_info`, idempotent on every boot), and to the `CREATE TABLE` for a fresh store.
- **Admission (`renderadmit`, internal DO route)** takes `reserveMs` and admits only when
  `spent_ms + reserved_ms + reserveMs <= allowance`; the reservation is added to `reserved_ms` on admission.
  **A caller that offers NO positive reservation is DEFERRED, not admitted** (`why: "no reservation was offered…"`),
  so the defect cannot return by omission. The answer gains `reserved_ms` and `reserve_ms`.
- **Release (`renderspend`, internal DO route)** takes `releaseMs`; it adds the time the render REPORTED and subtracts
  the reservation, clamped at zero so a double release cannot make the day's committed time read negative.
  **An unreported render STAYS CHARGED**: a render that reported no elapsed time may have burned anything up to its
  reservation, so the reservation is kept for the rest of the UTC day and the allowance is UNDER-used, which is the
  direction that cannot overrun.
- **I3 — `op=acquire`'s 429 `RENDER_DEFERRED` answer:** `render.allowance` now carries `reserved_ms` and `reserve_ms`
  beside `day`, `spent_ms`, `allowance_ms`, `renders` and `deferred`; `detail` says the allowance is *committed* and
  names both figures. **C-83.4's translation is CORRECTED** (not a new code, not a new row): it said the instance had
  *used* today's allowance, which since this change is true only of the part already reported — a deferral can also mean
  the remaining time is held by renders still running, and a member told "used" would have gone away for the day when the
  answer may be a minute off. It now says which, without naming a mechanism.
- **The renderer's request gains `navigation_timeout_ms`** (`RENDER_DEFAULTS`, 30,000 ms), so the bound the reservation
  is computed from is one the renderer was ASKED to hold rather than one the plane invented for the arithmetic. Not an
  interface with any built consumer: no renderer exists on any instance.
- **`RENDER_NOT_A_PAGE` (C-83.6) now releases the reservation WITHOUT CHARGE** before it refuses, because no renderer was
  ever asked on that path. Without it a caller could empty the day's allowance with addresses that serve PDFs.

### What this does NOT close, stated because both are load-bearing

1. **The reservation binds only a renderer that HONOURS what it was asked.** A renderer that spends longer than its own
   navigation and wait timeouts reports the longer time and `renderSpend` adds it, so `spent_ms` can pass the allowance
   by exactly that excess. The plane cannot check it: the elapsed time is the RENDERER'S CLAIM, as `render.mjs` says of
   everything else a renderer reports.
2. **The allowance is an ACCOUNT, not a throttle.** Nothing here caps CONCURRENCY, and nothing here is a platform meter.
   A day's renders are bounded in total browser time, not in how many run at once.

Both are recorded at `store.mjs` `renderAdmit` and in `CLIENT-RENDERED.md`'s Incomplete sections.
