### The change, on the wire

`op=promote` accepts a `replay` flag in the request body. Inside `Store#promote` that flag exempts the promotion from
every SHAPE fence the op has: the gathering grammar (`GATHERING_REFUSED`), the inquiry basis arms, the action basis and
correspondence arms, the bias arm, the creation-time group stamp, the inquiry freeze, and **C-32.19's rule that no
machine writes a member's `risk_tier`**. The exemption is deliberate — a replay re-states the record's own past
verbatim and that past predates the fences — but nothing removed the flag from the body, so the exemption was the
caller's to claim. `index.mjs`'s `op=promote` stamp block now carries one statement, beside the `author`,
`actorIdentity`, `actorViewer`, `ownerMemberId`, `assistantPrincipal` and `migrationReplay` stamps that already follow
the delete-first discipline:

```js
if (viaSession || cls !== "admin") delete b.replay;
```

- **Newly refused** — every promotion that carried `replay: true` from a caller that is not the ADMIN class with no
  session now answers with whatever fence the flag was skipping, by that fence's own name and with nothing written.
  The measured case (D-505's, `risk-tier.test.mjs` §7 arm (ix)) is
  `{ ok: false, reason: "MACHINE_CANNOT_SET_RISK_TIER", check: "C-32.19", risk_tier, held, detail }` — byte-identical
  to REC-189's shape. Before this change that promote LANDED and `op=projection` published `risk_tier: 1`.
- **Unchanged** — the ADMIN class with no session (a deploy token, never a session): its `replay` is honoured exactly as
  before, which is the whole of `migrate.mjs`'s path. Every promotion that sent no `replay` at all, of any class. Every
  member's ordinary promote. REC-173's server-verified migration replay, whose `migrationReplay` stamp and its
  `b.replay = true` are set AFTER this statement and are unaffected.
- **The answer's shape does not change.** No new key, no new code, no new refusal sentence. A caller that sent `replay`
  is not told the flag was dropped: it is told what its promotion is, which is the fence's own answer.

### Why the condition is the ADMIN class WITH NO SESSION, and both halves measured

`migrate.mjs` narrowed its token to admin at REC-173 and refuses to run under any other class, so the class half leaves
the migration untouched. The `!viaSession` half exists because `index.mjs`'s session block sets `cls = kind` from
`sess.role === "admin"`, so **the FOUNDER'S session** — stored role the literal `admin`, `Store.ROOT_ADMIN`,
`rootOfTrust: true`, minted by `op=claim` and `op=login` — arrives as `cls === "admin"` exactly as the deploy token
does. That is the session `op=export` already refuses in the same file, in the same words: *this refuses the founder's
own browser too, which is the one place in this system where being the founder is not enough.*

**MEASURED, and the first draft of this item was wrong about it.** The build asserted that an ADMIN-ROLE MEMBER's
session also arrives as `cls === "admin"`. The negative control's `any-session` arm came back GREEN, which is a finding
about the arm and not the subject, and `op=whoami` then measured the classes: a member login stores `member:<id>`, so
her class is `member` and `m.role === "admin"` decides only her capabilities (`Store#sessionRights`). The arm was moved
onto the founder's session, a REACH arm now asks the plane for all four callers' classes rather than asserting any of
them, and the source comment carrying the same wrong sentence was corrected with it.
