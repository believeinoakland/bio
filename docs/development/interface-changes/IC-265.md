## IC-265 · I3 MAJOR: `op=livefire`'s `ok` narrows to "the op answered"; the canary's result moves to `verdict` and `failing` · PROPOSED 2026-09-24 (D-506, `land/worker/D-506`; minted with `node tools/mintid.mjs IC` before building) — the version bump and the RESOLUTION are CONDUCT's

- **Interface:** I3 (**Answers**) — MAJOR. The meaning of an EXISTING key narrows for one op; two keys are added.
- **Design:** `docs/architecture/BIO_Distribution_v0_1.md` §6 "The deploy-to-serve ladder", rung 6 (the live verification), as amended by this landing, on **BOB #32's ruling of 2026-09-24 06:07Z**: *"livefire RULED (b): ok = op answered; canary result in `verdict` + `failing` names; IC entry; callers updated."* That settles the interface question `refusal-wire.test.mjs` §6c raised under D-495 and deliberately did not settle — D-270's boundary between a translation and an interface decision.
- **Proposer:** the D-506 worker, 2026-09-24. **Owner:** DIST (the release's canary). **Proposed version:** I3 **87.0.0 → 88.0.0** on `origin/main` 68fecb8d's line. CONDUCT takes the bump and the resolution; if another branch has taken I3 in parallel, only the NUMBER moves, never the classification.

### What changes

`op=livefire` (`bio-plane/src/livefire.mjs`) answered:

```
{ ok: A.every((a) => a.ok) && r2.ok, ranAt, store, nonce, totalMs, summary, assertions, r2, storeState, note }
```

dispatched at `bio-plane/src/index.mjs` as `json(out, out.ok ? 200 : 500)`. It now answers:

```
{ ok: true, verdict: "pass" | "fail", failing: string[], ranAt, store, nonce, totalMs, summary, assertions, r2, storeState, note }
```

- **`ok` narrows to THE OP HAVING ANSWERED.** `ok:false` is reserved for a catalogued refusal, and every refusal this op can raise — the class gate, `SESSION_ROUTE_NOT_RECORDED`, the namespace gate — is raised before `livefire()` is reached. Reaching the return IS the op answering, so `ok` is `true` and never a verdict.
- **`verdict`** carries the canary's result, `"pass"` or `"fail"`. It is derived from the assertions and `r2.ok` DIRECTLY — the same expression `ok` carried — and deliberately NOT from `failing.length`, so the row's negative control moves one variable.
- **`failing`** names every assertion that failed, in the order they ran. A `fail` never answers an unnamed verdict; a guard line names the verdict itself if some future arm flips `r2.ok` without recording an assertion.
- **No key is removed or renamed**, and `summary`, `assertions`, `r2`, `storeState` and `note` are byte-identical in shape.
- **The HTTP status does not move.** `index.mjs` keys it to `verdict` (`out.verdict === "pass" ? 200 : 500`), so every outcome answers the status it answered before this change. A caller reading the status alone is not silenced by the move — which is the reason the verdict was given keys of its own rather than being deleted from the wire.

One defect is fixed in the same act, and it is this item's own subject found in its own subject: the R2 throughput arm could flip `r2.ok` — and therefore the whole answer — on a **length mismatch that NO assertion named**. It now records an assertion on its failing branch only, so `failing` is complete and a green run's assertion count is unmoved (19/19 in the local fixture).

### Why MAJOR

By IC-25's test. `ok:false` disappears from this op's successful answers, so a consumer that read `ok:false` as "the canary is red" reads `ok:true` on a red canary and is WRONG IN THE SAFE-LOOKING DIRECTION — the worst shape a narrowing can take, and the reason this is not MINOR despite being purely additive in keys. Every such consumer must move.
