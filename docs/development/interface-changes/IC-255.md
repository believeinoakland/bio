## IC-255 · I5 + I3: a proposal disposition records the definition version it judged, and governs no later one · PROPOSED 2026-09-24 (REC-184; the id pre-minted by CONDUCT #19)

- **Interface:** I5 (`proposal_dispositions` gains a column) and I3 (`op=proposedispose`, `op=proposals`, `op=queue`,
  `op=stats`, `op=purge` answers gain keys; `op=proposals`' ageing rule changes for a revised definition).
- **Classification (proposed; the integrator classifies):** MINOR, ADDITIVE on the wire — no key is removed or renamed and no
  refusal is minted — with ONE BEHAVIOUR CHANGE a consumer can see: a disposition taken against an earlier version of a
  progression definition no longer ages that proposal out of `op=proposals`' open lists (`proposals[]`, `instances[]`) or
  `op=queue`'s open items once the definition is revised (D-128's append-only revision). The integrator decides whether
  that reads as breaking; no measured consumer depends on the old behaviour (below).
- **What moves:**
  1. **I5:** `proposal_dispositions.definition_version INTEGER`, NULLABLE, added by `#migrate`'s additive pass on an existing
     store and NEVER BACK-FILLED. Written by `op=proposedispose` from the store's one reader of the current version
     (`#definitionVersionOf`), never the caller's word; a re-decision re-stamps it.
  2. **`op=proposedispose`** (instance arm) answers `definition_version`.
  3. **`op=proposals`** — each `dispositions[]` entry gains `definition_version` (number or null),
     `definition_version_state` (`recorded` | `not recorded`), `current_definition_version`, `applies` (boolean) and
     `applies_because` (one of `decided_against_current_version`, `decided_against_earlier_version`,
     `version_not_recorded_definition_not_declared_since`, `version_not_recorded_definition_declared_since`,
     `version_not_recorded_order_undetermined`, `definition_not_declared`). Each `proposals[]` entry gains
     `prior_disposition` — `null`, or the decision that no longer applies, with its version fields. `disposition_count`
     still counts every recorded disposition.
  4. **`op=queue`** — each `disposed.findings[]` entry of scope `instance` gains `definition_version`,
     `definition_version_state`, `applies`, `applies_because`.
  5. **`op=stats`** gains `progressionDefVersions` and `progressionStageVersions`; **`op=purge`**'s `removed` gains the same two.
- **How rows written before this change read:** `definition_version` null, `definition_version_state: "not recorded"`.
  Such a row governs while the definition has not been declared since the decision (`progression_defs.at` against the
  row's `at`, which every declaration wrote before and after D-128); once the definition is declared after it, or when the
  order is not in the record (an instant missing, or equal), it does not govern and the proposal is open again with the
  decision beside it. The version number is never guessed.
- **Why:** framework §8.2 "The declared flow, and its revisions" (D-128, BOB #27): a finding names the version it was read
  against; a member's decision about that finding applied to a later definition is the record claiming a judgment nobody
  made (CLAUDE.md §2).
- **Consumers, measured 2026-09-24 by grep over the tree at `15b2a4c0` plus this change:**
  - `civicos-ui/app.html` — reads `op=proposals`' `proposals`/`dispositions` and `op=queue`'s `disposed`; no site reads a key
    this change adds, and none depends on a disposed proposal STAYING out of the open list after a revision (the surface
    has no revision form with a basis, D-128's own NOT BUILT). No change required; showing `prior_disposition` is a UI
    follow-on, not owed by this IC.
  - Tests: `bio-plane/test/proposedispose.test.mjs` CORRECTED at one site (the purge's dispositions count 2 -> 3, because
    this item's arm records a third before the purge; the comment says so). No other suite changed.
- **Evidence:** `bio-plane/test/proposedispose.test.mjs` — the REC-184 block (the arm through the op; the stats and purge
  counters) and the legacy block L0–L4 (a column dropped from a live store, re-booted through `#migrate`). NEGATIVE
  CONTROL on the suite's line: (A) stop writing the version, 38/6; (B) the read ignores the version, 41/3; (C)
  over-strictness, 44/0.
