**THE SHAPE.** `store.mjs` `promote`, inside the transaction. (1) `REC-176 is-promote-resend`, after the sight check
(REC-138) and BEFORE `EXISTS` and `CAS_STALE`: the manifest row at `(bundleId, snapKey)` is read; if it records THIS
promotion — the same base (a creation's is the empty-string sha), EVERY file by name and digest as a set (order-free,
hex case-free), the same kind (`promotion` / `promotion-replay`), writer, operation and author — the answer is the no-op.
A digest either side does not state makes the two UNDETERMINED, never equal. (2) `DEC-49 REGION is-promote-snapkey`, the
last line before the first write: any held key reaching here is refused by name. (3) The two manifest INSERTs and the history
snapshot INSERT lose `OR REPLACE`, so a held key that ever reached them fails the primary key and rolls the promotion back.
Existing refusals keep their precedence: a creation reusing a key on an existing bundle still answers `EXISTS`, a stale base
still `CAS_STALE`; `SNAP_KEY_TAKEN` is answered exactly where the overwrite used to land. The digests compared are those
`files` carries at that line — after REC-175's `is-promote-digest` (not yet on `main`) computes them from the bytes, and after
D-436's deterministic group stamp — so the two items compose without either touching the other's region.

**THREE REFUSALS MOVED AHEAD OF THE FIRST WRITE — found by this item, the same class.** `FILES_DROPPED`
(`is-promote-files`, C-33.24), `NO_BUNDLE_MD` and the bias-set refusal (`bias-set-refusal`, C-26.11) were returned

moved unchanged to just before `is-promote-snapkey`. Wire change: none of their answers changes; only a refused
promotion now writes nothing, and their PRECEDENCE moves ahead of the refusals between the old and new sites (a request
that is both refused FILES_DROPPED and something later now answers FILES_DROPPED).

**THE WIRE.** Refusal: `{ ok: false, reason: "SNAP_KEY_TAKEN", code, check: "C-67.1", translation, snapKey, detail }`.
No-op: `{ ok: true, bundleId, idempotent: true, wrote: false, snapKey, bundleSha /* the bundle.md digest that promotion
produced */, recorded: { kind, base, author, created }, current: { bundleSha, rowVersion } | null, detail }` — `bundleSha` is
the RECORDED promotion's output, and `current` says separately what the head is now, so a caller is never told a stale
promotion is the head. `op=snapkeycensus` (admin, probe; `limit` default 50, max 500): `{ ok: true, bundles, manifest_rows,
promotions, overwritten, undetermined, bundles_with_deficit, excess, orphan_manifest_bundles, listed: [{ bundle_id,
promotions, manifest_rows, overwritten, undetermined, creation_row, unanchored: [snap_key…] }], rewritten: 0, note }`.

**WHY THE CENSUS IS EXACT WHERE IT SPEAKS:** `manifest` has one writer (`promote`, one row per successful promotion), and
`bundles.row_version` is advanced by that write and nothing else, so `row_version − COUNT(manifest)` is the number of lost
rows. **Where it cannot speak it says so:** a bundle with no creation row may have lost it to an overwrite OR predate the fix
that began writing a creation's row, so one of its promotions is `undetermined`, never `overwritten`. Which key collided is
recorded nowhere and is not guessed; `unanchored` lists rows whose base is no surviving row's output — the trace in the chain.
