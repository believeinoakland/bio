### The change, on the wire

- **In:** `store: <namespace token>` becomes `store: "bio" | "scratch"`, exact and case-sensitive, on both routes.
- **A named value outside that set** — `biosmoke`, `biosmoke-fleet`, `bio_smoke`, `Scratch`, `BIO`, `a b`,
  `"scratch "`, the empty string — answers
  `400 { ok: false, reason: "NAMESPACE_UNKNOWN", detail, asked, namespaces: ["bio","scratch"] }`, after `BAD_SHA` and
  before R2 is touched at all. `asked` is truncated at 80 characters, as the plane's is. The code is the plane's own
  spelling (C-78.1): the set is fixed in the plane's code rather than per instance, so "no such namespace" is the same
  fact on every instance a member can be bound to.
- **Absent or non-string `store`** still answers `400 BAD_STORE`, and only now is BAD_STORE the condition it always
  claimed to be. Before this, both members coerced an absent field and a bad one to the same `""` and refused both as
  a SHAPE failure; `store: ""` therefore read `BAD_STORE` and now reads `NAMESPACE_UNKNOWN`, which is the line I8
  already draws (IC-253).
- **Unchanged:** `store: "bio"` and `store: "scratch"`; every other field, every success shape, and `NOT_FOUND`
  itself, which keeps its exact old meaning — the namespace exists and holds no such capture.
- **Neither member carries `check`/`translation` fields.** No member-facing surface, no DEC-49 family
  (`agent-worker/src/index.mjs`'s note on `refusal` states the reasoning and it holds here).

### Why it is a defect and not a tightening

Neither member ever wrote anything — no STORE binding, no `.put`/`.delete`, and IC-237 measured that. The bucket was
never at risk. **The ANSWER was.** `store` is spent as the R2 key prefix `<store>/captures/<sha>`, and a bucket with
no key under a prefix that does not exist answers the same 404 `NOT_FOUND` as a capture genuinely absent from a real
namespace. The caller reads a fact about the CAPTURE where the truth is a fact about the NAME it asked under — the
conflation `CLAUDE.md` §1 names outright, and the class the whole product is: a record claiming more than it can
support. IC-253's own consumer-impact section named these two members as **"Not edited here"**; this is that half.
