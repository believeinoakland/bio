## IC-287 · I3: op=acquire's multi-part `existed` answers `true` when the register holds the whole document, or `null` with `existed_undetermined` — never a `false` that claims the bytes are new · ACCEPTED 2026-09-24, MAJOR — I3 96.0.0 (resolved by CONDUCT #20 at integration on c20-batch25, on base 95.1.0; D-476; minted at integration because the row assigned the mint to CONDUCT)

- **Interface:** I3 only. No table changes; a new read-only store route `registerholds` is internal.
- **What changed:** a multi-part capture's `existed` was a flat `false`. That is the positive claim THESE BYTES ARE NEW, and op=acquire made it on every re-fetch of a parted document the record already holds. Now one bounded register read answers: `true` if a live bundle registers the whole sha; otherwise `null` with a sibling `existed_undetermined` sentence naming what was and was not asked. It is never `false`. Single-part answers are unchanged.
- **Classification:** MAJOR by IC-25's test, because the same request now receives a different answer (`null` or `true` where it received `false`). Measured consumer impact is NIL: nothing in civicos-ui, newgroup, tools or INTERFACES.md reads op=acquire's top-level `existed`, and it is not on the `document` callers copy into a bundle.
