## IC-268 · I5 ADDITIVE: `project_sight`, the owner-set-derived index the sight predicate reads · ACCEPTED 2026-09-24, MINOR — I5 3.10.0 (resolved by CONDUCT #20 at integration on c20-batch22, on base 3.9.0; D-497) · was PROPOSED 2026-09-24 (D-497; minted with `node tools/mintid.mjs IC`)

- **Interface:** I5 (the store schema) only. ONE new table and ONE new index in `bio-plane/src/schema.mjs`:
  `project_sight (project_id TEXT PRIMARY KEY, setting TEXT NOT NULL CHECK (setting IN ('discoverable','hidden')))`
  and `project_sight_setting ON project_sight(setting, project_id)`. No column is added to,
  removed from or retyped in any existing table. **I3 does not move**: `op=projectdirectory`, `op=projectvisibility`
  and `op=projectvisibilityset` answer the same keys, with the same spellings, the same types and the same values.
  No refusal code is minted, and no check id.
- **Classification (PROPOSED — CONDUCT classifies and takes the version bump):** I5 ADDITIVE. The schema pass is
  `CREATE TABLE IF NOT EXISTS` at every boot, so an existing store gains the table on its next start and a fresh
  one is created with it. Nothing reads the table before `Store#reindexProjectSight` fills it, which runs in the
  same boot, after the schema pass, in `#seedMintLedger`'s position and for its reason.
- **Why:** Membership v2 §7.14, "The directory", and the row D-479 REPORTED rather than took, in its own words —
  *"bounding that needs a row source the sight predicate itself READS, not a second copy of its rule"*.
  `Store#sight` was a JS predicate with no row source, so `op=projectdirectory` established "this caller sees none
  of them" by asking it about every project in the group: each statement bounded (D-479), the NUMBER of statements
  growing with the record. With the index the read is ONE statement — the discoverable half joins `project_sight`,
  which `Store#visibilityOf` itself reads, and the not-full half is `viewerPredicate`'s own compiled predicate
  NEGATED rather than restated.
- **The table is DERIVED, and that is what keeps the rule stated once.** `project_visibility` stays the record:
  append-only, one row per owner's act. Every row of `project_sight` is computed from it by ONE statement, in one
  method, which is also the only place the rule "the latest act, and HIDDEN where the owners never acted" is
  written. It is recomputed for a project at every promotion and at every owner's act, and WHOLE at every boot,
  so a row that disagreed with the log — including because a landing moved the rule — cannot survive a restart.
- **Consumers, measured 2026-09-24 by grep over the tree at `68fecb8d` plus this change:**
  - `civicos-ui/` — 0 reads of `op=projectdirectory` and 0 mentions of either table. No change.
  - `newgroup/` — untouched. Its `src/release.mjs` carries a FROZEN copy of a released plane bundle (DIST's
    artifact, not a consumer of this schema); it is not edited here and needs no change.
  - `pdf-worker/`, `ocr-worker/` — no store access. No change.
  - The plane's own suites: `bounds.test.mjs` (five new arms), `derivation-bounds.test.mjs` (three pinned rosters
    moved from printed output), `project-discoverable.test.mjs` (its predecessor fixture corrected — see below).
- **Migration, stated exactly:** none is written and none is needed. The index is a projection, so the first boot
  after this lands derives every row from the acts already in `project_visibility`; a project with no act derives
  `hidden`, which is what §7.14 promises and what every such project already read. `op=purge` clears the table in
  BOTH arms beside `project_visibility` (the `project_participants` precedent), and a whole-store purge is safe
  for the same reason the derivation is: what survives is re-derived at the next boot.
- **The row carries NO DATE, and that is a defect this landing's own first draft had and paid for.** It began
  with an `at TEXT NOT NULL` written fresh on every recompute, so an UNCHANGED boot rewrote every row with
  different bytes and A RESTART PLUS A PURE READ MOVED A TABLE. `versionnotice.test.mjs`'s no-write WITNESS
  caught it by name on the first full battery — `WITNESS QUIET` and `NOTHING WRITTEN (the whole store)`, both
  naming `project_sight` — which is precisely what that witness exists for: CLAUDE.md §5 rests every live
  verification's no-write guarantee on the record's tables reading the same before and after, so a derivation
  that writes on every boot does not cost a test, it costs the instrument. Two narrower fixes at the STATEMENT
  are REFUSED BY WORKERD with `Error: incomplete input: SQLITE_ERROR` — a `WHERE` on the conflict action, and
  the same guard moved into a LEFT JOIN against the index — while `node:sqlite` prepares both without
  complaint, a measured difference between the plane's engine and a local one, recorded at the site. So the
  COLUMN went instead: a projection needs no date, the act log carries every date there is, and an unchanged
  recompute now writes rows byte-identical to the ones it found.
- **One superseded test, CORRECTED rather than exempted.** `project-discoverable.test.mjs` §1 builds a
  "predecessor" tree — today's `src/` over a schema with the visibility table stripped — to prove that projects
  created before REC-149 boot HIDDEN. Since D-497 that tree describes a build that never existed: the sight index
  is derived AT THE BOOT, so a predecessor holding `project_sight` while lacking `project_visibility` is this
  build with half a landing, and the recompute throws on it. The fixture now strips BOTH tables' DDL and neuters
  the three calls into the derivation, asserting each count before arming — a call left standing shows up as the
  throw it is.
