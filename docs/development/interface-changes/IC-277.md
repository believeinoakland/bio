## IC-277 · I3: `op=acquire`'s `render: true` answers a CAPTURE, not 501, on an instance with a `BROWSER` binding; and C-83.3's sentence is corrected · PROPOSED 2026-09-24 (D-490, `land/worker/D-490`; minted with `node tools/mintid.mjs IC`)

- **Interface:** I3 (the op surface). The QUEUE row named I3 and said "the integrator classifies". BEHAVIOURAL, not additive: no key moves and no key is added — an arm that could ONLY refuse can now succeed, and one refusal's prose changes.
- **Design:** `docs/development/CLIENT-RENDERED.md` §"What must be recorded on a rendered capture" and §"There is no collision: rendering is available on the free tier", with BOB #31 and BOB #32 (2026-09-23).
- **Supersedes the behavioural half of IC-252** (D-64, which introduced this arm answering 501 on every instance). IC-252's record of what D-64 did stands and is not rewritten; this entry is where the behaviour moved.
- **Proposer:** the D-490 worker, 2026-09-24. **Owner:** CAPTURE. **Resolved by:** CONDUCT (the version bump and the resolution are the integrator's).

### What changes

**1. `render: true` can now succeed where it could only refuse.** D-64 shipped the render arm with no renderer any instance could have: `rendererFor` answered `{kind: "browser-binding-without-driver"}` for `env.BROWSER` and the op answered **501 `RENDER_NO_RENDERER` (C-83.3)** on every instance, every time. D-490 builds the driver (`bio-plane/src/browserrender.mjs`, a CDP client over the Browser Rendering binding's own two endpoints), so on an instance holding a `BROWSER` binding the same request now returns **200 with D-64's pair** — the rendered document primary under its own digest, the served shell beside it, joined by `render.of`.

No response SHAPE changes. The 200 body is exactly the one D-64 designed and `rendered-capture.test.mjs` has asserted since; the 501 body is unchanged in shape. What changes is **which of the two a caller gets**, and that is the whole of the interface change.

**2. C-83.3's `detail` sentence is corrected, and the `browser-binding-without-driver` kind is narrowed.** The refusal's code, its C-number and its canned translation are UNCHANGED. Its `detail` said *"a Browser Rendering binding (BROWSER) is bound, but the in-plane driver over it is not built"*, which was true of every instance when D-64 shipped it and is now true of none. It reads *"BROWSER is bound to something this plane cannot speak to: it is not a Fetcher, so there is no endpoint to open a devtools session on"*, which is the only thing that branch can still mean. The `else` arm now also names the `BROWSER` binding as one of the two an instance may hold.

**3. Precedence is stated where it was previously vacuous.** `env.RENDERER` (a service binding, how a render fleet member would arrive) still wins over `env.BROWSER`. Before D-490 that ordering could not matter, because the browser branch never produced a renderer; it matters now, and `browser-render.test.mjs` block H fences it so a browser binding never silently takes a dedicated renderer's work.

### What a consumer sees

**Measured, not assumed** (grep, 2026-09-24). No first-party surface asks for a render: `render: true` occurs **zero** times in `civicos-ui/`, `agent-worker/src/`, `pdf-worker/src/` and `ocr-worker/src/`. `newgroup/src/` returns ONE hit and it is NOT a caller: `release.mjs`'s `RELEASE_SOURCE`, the embedded copy of the plane's own bundle, so it is this arm's own source read back — stated because a bare count there would read as an installer consumer. And `capture_requests` carries no `render` column at all (`schema.mjs`, 0 matches in its `CREATE TABLE`; that is D-491). The only callers today are a member calling `op=acquire` by hand and this repository's two suites. **NO DEPLOYED INSTANCE IS AFFECTED BY THIS LANDING AT ALL**, because no instance has a `browser` binding to bind: `wrangler.jsonc` carries no `browser` line and DIST's deploy derivation refuses the class (`UNKNOWN_BINDING_CLASS`). The behaviour change becomes reachable only when **DIST-11** deploys the binding, which is the row this one is ordered behind.

### Classification

**Proposed MINOR for I3**, and the argument for it rather than MAJOR: nothing a caller sends or reads changes shape, no key is removed or renamed, and every caller that gets a 501 today gets the same 501 tomorrow unless its instance gains a binding it does not have. The one non-additive edge is a caller that has come to depend on `render: true` ALWAYS refusing — which is a dependency on a defect, and the only instance that could develop it is one that then chose to bind a browser. **CONDUCT takes the number and the resolution; this file is PROPOSED and states the measurement rather than the verdict.**

### What this landing does NOT establish

**The live half is unverified and this entry is not evidence about it.** That the binding speaks the two endpoints and the CDP dialect the driver uses is **the vendor's claim, read out of `@cloudflare/puppeteer@1.4.0`'s own source on 2026-09-24**, not a measurement against Cloudflare. `browser-render.test.mjs` drives the driver against a fake that implements exactly that protocol, which proves the DRIVER and proves nothing about the service. The first true test is DIST-11's deploy plus one live render.

**`@cloudflare/puppeteer` is deliberately not vendored**, and this is measured rather than preferred: with the package imported into `src/render.mjs`, `node test/rendered-capture.test.mjs` dies at its first `new Miniflare(...)` with `ERR_MODULE_RULE: Unable to resolve "src/render.mjs" dependency "@cloudflare/puppeteer": no matching module rules`, because the battery runs `src/` RAW under miniflare and a bare specifier matches none. A dynamic `import()` of it fails identically. If the estate wants puppeteer, the shape that works is a FOURTH FLEET MEMBER bound at `env.RENDERER` — the seam already admits it, and it is how `pdf-worker` and `ocr-worker` already carry dependencies the plane cannot. That is DIST's and FLEET's ground.
