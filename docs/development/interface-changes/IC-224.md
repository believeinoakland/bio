## IC-224 · I3: the `per-item` weight — `op=proposedispose`, `op=taskresolve` and `op=taskforward` take a SET as `items`, each item applied or RETAINED WITH ITS OWN REASON; `op=affordances` publishes `set_acts`; `NOT_YOURS` gains a DEC-49 code · PROPOSED 2026-09-23 (D-126; id minted with `node tools/mintid.mjs IC` by the D-126 worker; CONDUCT resolves the version)

- **Interface:** I3. I5 does not move (no table, no column).
- **Design:** `docs/development/NOTIFICATIONS.md` §Applying a handler to a selection — *"each item independently succeeds or is
  RETAINED WITH A REASON"*, the reason a named refusal in the plane's own words.
- **What changes on the wire (all ADDITIVE; the proposer's classification is MINOR — CONDUCT decides):**
  1. **The set form.** A body carrying `items` (an array of objects) is the per-item act. Every item is decided by the SAME
     method the single form calls (`store.mjs` `proposeDispose` / `taskResolve` / `taskForward`, whose FIRST statement is the
     set branch into `#perItem`). Other body fields are SHARED by every item (`to`, `reason`, `now`, …) and an item may
     override them for itself; the server's stamps (`actor`, `decidedBy`, `viewer`, `identity`) are forced onto every item
     after its own fields. At most `PER_ITEM_MAX` = 100 items.
  2. **The answer.** `{ op, weight: "per-item", count, applied, retained, items: [{ index, outcome: "applied"|"retained",
     asked, ...that item's own act result }] }`. `ok: true` ONLY when every item applied; otherwise `ok: false`,
     `reason`/`code` `SET_ITEMS_RETAINED` (C-75.5) with `items[]` beside it — **the applied items stand; it is not a
     rollback.** CALLER HAZARD, measured: on an APPLIED `proposedispose` item, `reason` is the MEMBER's reason (the single
     act's own success field); read `outcome`, never `reason`, to learn what happened to an item.
  3. **New refusals, family `PER_ITEM_CHECKS` (C-75), each with a canned translation:** `SET_NO_ITEMS` (C-75.1) and
     `SET_TOO_LARGE` (C-75.2) refuse the whole set BEFORE any item is tried; `SET_ITEM_MALFORMED` (C-75.3) and
     `SET_ITEM_FAILED` (C-75.4) retain ONE item; `SET_ITEMS_RETAINED` (C-75.5) is the summary.
  4. **`NOT_YOURS` (the task-actor fence) now also carries `code`, `check: "C-76.1"` and `translation`** (family
     `TASK_ACTOR_CHECKS`), because a selection can now surface it to a member. `reason`, `detail`, `assignee`,
     `assignee_role` are unchanged.
  5. **`op=affordances` (no target) answers `set_acts`**: the three ops, each `decorateAct`-decorated with `weight:
     "per-item"`, `set_key: "items"`, `item_keys`, `shared_keys` and `max_items` (= `PER_ITEM_MAX`).
- **Unchanged:** a body with no `items` gets the single act, byte-for-byte (driven: `peritem.test.mjs` block 7). The DO
  dispatch map is unchanged.
- **Consumers, measured:** `civicos-ui/app.html` — the queue (this landing) reads `set_acts` off the act source it already
  loads and sends ONE call per selection; no other surface sends `items` to these ops. Suites whose reading of the source
  had to move: `civicos-ui/test/member-respect.test.mjs` (ARM 4d's `proposedispose` carry and the `queueEntryControlsHtml`
  SETS row, CORRECTED with dated reasons). `identity-claims.test.mjs` and `rung-ladder.test.mjs` resolve these ops to their
  methods through the dispatch map and stay green BECAUSE the set branch sits inside the methods (measured red when it sat
  in the dispatch map, and moved for that reason).
