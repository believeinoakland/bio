## IC-194 · I3: `op=links&capture=` states a SELF-REFERENCE basis for a link whose resolved target is the source's own capture, and a ONE-CAPTURE basis where one capture sits on both sides of the retrieval — never a fourth verdict · PROPOSED 2026-09-23 (D-57, minted with `node tools/mintid.mjs IC` BEFORE the entry was written) — the version bump, the classification and the RESOLUTION are CONDUCT's

- **Interface:** I3 (plane → UI and fleet, the op contracts), `op=links&capture=<sha>` — the per-link `basis` and
  `detail` strings of a `linked` row (answered by `Store#resolveLinks`). **Base read off THIS TREE (`origin/main` @
  `0e7cc03e`, `INTERFACES.md` I3 Version): 59.2.0. Proposed MINOR — 59.2.0 → 59.3.0. Read the base AT RESOLUTION.**
- **The change.** Two new BASIS sentences, no new verdict, no key added or removed:
  (1) **self-reference** — the resolved target's capture IS the source capture (a page linking to itself; every
  paginated Legistar calendar does). `basis` begins *"this link points at the document itself"*; `detail` begins
  `self-reference: <sha12>` and names the hash ONCE. Verdict: `undetermined` on one observation (unchanged), or
  `contemporaneous` when those same bytes were observed on both sides of the retrieval (unchanged).
  (2) **one capture on both sides** — a NON-self target whose only capture at-or-before and at-or-after the retrieval
  is the SAME capture (made at the source's retrieval instant, observed once). `basis` says the record holds one
  capture and it establishes nothing either way; `detail` begins `one capture: <sha12>`. Verdict `undetermined`
  (unchanged).
  Both cases used to fall into the two-sided arm and read *"the target changed somewhere between the captures
  bracketing this document's retrieval"* with `detail` *"bracketing captures differ: X … , X …"* — ONE hash named twice
  as two captures. That sentence now appears ONLY for two DIFFERENT captures bracketing the retrieval.
  `tally`, `verdicts`, `target_capture`, `target_bundle` and the row set are unchanged: the self-link is still listed
  and counted.
- **Why MINOR:** a string a consumer renders changes to a TRUE one; no field, verdict value, key or class moves, and the
  record claims LESS than it did (IC-114's and IC-187's precedent: a change that weakens a published claim). **Argued the
  other way, for the integrator:** a consumer matching the old sentence to detect "changed" would stop matching on a self
  link — measured below at zero such consumers.
- **Proposer:** RECORD, D-57 worker (CONDUCT #16, cloud), 2026-09-23. **Owner to land it:** `RECORD`.
- **Design:** `docs/development/LINK-FIDELITY.md` §The three-valued verdict (the verdicts and what each basis may claim).
- **Consumers, MEASURED** (`git grep -e "bracketing captures" -e "captures bracketing" -e "self-reference:"` over
  `civicos-ui agent-worker pdf-worker ocr-worker tools docprofile`, on this tree): **0.** `civicos-ui/app.html` `linkRow`
  renders `basis` and `detail` VERBATIM and matches no literal in them; its `linkTally` self-reference count keys on
  `target_bundle`, which is unchanged. No UI literal needs to change.
- **Evidence:** `bio-plane/test/d57selflink.test.mjs` (through `op=acquire` and `op=links`): 24/24; its `NEGATIVE
  CONTROL:` line records two arms (self-reference test removed → 2 fail by name; the whole D-57 test removed → 7 fail,
  the self-link arm by name at the "changed" sentence).
