  `op=capturerequestdraining`, `op=capturerequestdrain`). Bases read off THIS TREE (`origin/main` @ `58293bf3`):

### The change, on the wire

- **I5 — `capture_requests.render INTEGER NOT NULL DEFAULT 0`**, declared inside the existing table (before the
  `host_governor` block) and added to `#migrate`'s additive `ALTER` list, so a migrated store and a fresh install
  present the same table. **It is the one non-nullable column in that list and the reasoning is stated at both
  sites:** every column above it is nullable because a legacy row carried an unstated value a default would invent;
  this one has no unstated value to invent, because a request written before the column existed could not ask for a
  render — no door read the flag and no drain could have honoured one — so `0` states what was true of it. No new
  table, so `purge` is unchanged (the per-bundle and whole-store arms already take the table) and hygiene's
  structural check is unaffected.
- **`op=capturerequest` (request):** `render: true` asks for the page as a visitor saw it. `render: false`, `null`
  and an absent key are the document as the site serves it, ANSWERED and not refused. Any other value →
  `CAPTURE_REQUEST_RENDER_MALFORMED` (C-28.16), nothing queued. The refusal is C-83.1's argument one layer up: a
  `render: "yes"` normalised to "no render" queues a plain capture and the served shell is then filed as the
  content, and here the row outlives the call, so the drain fetches under a flag nobody can see was dropped.
- **`op=capturerequest` (answer):** new key `render: boolean`, on the fresh row and on the standing row.
  **Idempotence now keys on `(run, address, render)`** where it keyed on `(run, address)`: a rendered page and the
  document a site serves are not one document (D-64's founding claim — the plane files them under two digests and
  calls the rendered one primary), so a render ask is no longer answered with a standing plain row and
  `already: true`. DEC-47's politeness is not spent by the second row: the drain admits one request per host per
  tick either way.
- **`op=capturerequests` (read):** new key `render: boolean` on every row of the explicit projection. It is what
  makes a held render legible — without it a row sitting at `requested` under C-83.3 reads as a fetch that keeps
  failing.
- **`op=capturerequestdraining` (read, admin/probe; op=acquire's own oracle):** new key `render: boolean`, `false`
  on a row that does not exist (the fail-closed direction: a silence can never become a render nobody asked for).
- **op=acquire's capture-request arm:** takes the flag FROM THE ROW and overwrites the body's own, exactly as it
  already does for the locator. **No third field is added to the drain's request body** — it still sends `via` and
  `request` and nothing else, because a value a caller can supply is a value a caller can differ from what was
  checked, and a render is a second load of the page.
- **`op=capturerequestdrain` (answer):** a render that could not happen appears in `held[]` (never `refused[]`,
  never `captured[]`) with `code` = the C-83 code op=acquire gave, plus `check`, `translation` and
  `render: { state: "deferred", content: "undetermined" }`. The row is written `state='requested'` with that code
  and detail, so the next tick asks again; its `expires` bounds the hold. **The code is never collapsed into one
  deferral word:** C-83.3 says this instance cannot render at all and C-83.4 says it can and has spent today's
  allowance, and only the second may tell a member to ask again after midnight UTC.
- **The run's log (I1/I3 via `op=airunlog`):** the deferral is one `LOOKED_INDETERMINATE` observation with
  `governed: true` and no `condition`, naming the C-number. Governed on D-104's own reasoning: the allowance, the
  per-host pacing and a missing renderer are facts about US, and an ungoverned indeterminate would put "we looked
  and could not tell" against an address nothing was sent to — which is the counter the archive fallback reads. NO
  new `condition` kind was invented; `client-rendered-shell` would claim a shell was captured when nothing was
  fetched.

### What this does NOT do

- **It does not render anything.** No instance has a renderer (`node tools/status.mjs 2.rendered`), so every
  unattended render today answers `RENDER_NO_RENDERER` (C-83.3) and is held. The suite drives the DEFERRAL through
  an injected `RENDERER` binding and a zero allowance; an unattended render that SUCCEEDS is driven nowhere and is
  undetermined until DIST deploys a renderer.
- **It does not give the monitoring sweep (CAP-3) a way to set the flag.** The caller here is a run
  (`op=capturerequest` names one), which is what BOB #32 item 3's "unattended sweep" reaches through the drain. A
  monitor tick that decides to render on its own account is not built and is not this item's scope.
- **It mints no queue `condition` kind**, so a deferred render does not surface on `op=queue` as an item of its
  own. It is visible on `op=capturerequests` and in the run's log. If a member-facing item is wanted, that is a
  roster change on another surface and belongs to whoever owns it.
