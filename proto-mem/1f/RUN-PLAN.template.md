## 6. Ambiguities and contradictions found in the files read

Each item quotes the files; line numbers are those of the files as read on `origin/lane/platform` (`PLATFORM.md` as on this branch).

1. **Memory limit: 128 MB or 256 MiB.** `PLATFORM.md` line 120: "Memory is 128 MB per isolate, shared"; `LOAD-PER-TYPE.md` line 9 (M1): "A Worker or Durable Object dies at about 256 MiB of buffers (not 128); one buffer <= ~128 MiB; a step shares that" (stage0 P-M2, live); `PROBE-SPEC-L1-L2.md` line 34 uses "memory under 256 MiB (M1)". PLATFORM.md was written before the live measurement; the pass bars use 256. The probe cannot tell which, it reports only completion.
2. **"The same scratch copy" or the same account.** `levels-2-3-study-plan.md` line 21 (S1 additions): P-M17 and "FILES' L1-L6 on the same scratch account", needs column "the same scratch copy"; `load-test-draft.md` line 21: "measured on the same scratch copy's account in the same deploy cycle as S1". `plat-s1` runs the plane (alpha today) and has no container binding I can find; L3-L6 need a container, so they cannot run "on" that copy as deployed. I took "account" and made a sibling probe Worker.
3. **Duration.** `levels-2-3-study-plan.md` line 21 gives "+0.5 day" for P-M17 plus L1-L6; `PLATFORM.md` line 265 (P-M17) includes "a week of an idle probe for host restarts" and a SIGTERM wait that `PLATFORM.md` line 134 (point 15) states as "SIGTERM then SIGKILL after 15 minutes". A week is not 0.5 day of calendar time (lane time may be).
4. **L3 names a different operation than the image has.** `PROBE-SPEC.md` line 11 (L3-HEIC) "photo redraw" with pass "(JPEG local: 0.55 s/80 MB at 48 MP)", from `LOAD-PER-TYPE.md` M14 (libvips JPEG to JPEG). `reader-container` has no re-encode route; `/frames` is ImageMagick to PNG (`container/images.mjs`), and `LOAD-PER-TYPE.md` M11 puts ImageMagick on the same 48 MP JPEG at "9.3 s, 388 MB". The two are not comparable; PROBE-SPEC does not say which program the live L3 is meant to run.
5. **"streams at ~14 MB" (L5 pass bar, `PROBE-SPEC.md` line 13) against the server's code.** The 11 to 14 MB figures are M16 (`LOAD-PER-TYPE.md` line 23: 7-Zip and tar to stdout/null). `container/archives.mjs` `walkSeven` collects each member's whole output (`run(..., { maxOut: bounds.member })`, then `new Uint8Array(r.stdout)`), and `walkTar` `Pull.take(size, true)` concatenates a member whole; `src/records.mjs` `readRecords` delivers each payload "whole, as one Uint8Array". With `archive.member_bytes` active at 2 GiB (`read-bounds.mjs`, beta row) a member is held whole in the container, copied, and held whole again in the caller (a Worker). Section 3, L5 shows what the local server did.
6. **"500 MB".** `PROBE-SPEC.md` line 13 "500 MB ZIP as uploaded"; `read-bounds.mjs` `archive.uploaded_bytes` is 524,288,000 (= 500 x 2^20) and its header says "MB and GB count 2^20 and 2^30 bytes (K4840 (1))". A 500,000,000-byte file and a 524,288,000-byte file are both "500 MB" under different readings; fixtures at 503,318,422 B, and exact blobs at 524,288,000 and 524,288,001, cover both.
7. **Ratio bomb against the ratio bound.** `PROBE-SPEC.md` line 13 asks for "a ratio bomb"; the bound is 1,100:1 (`read-bounds.mjs` `archive.ratio`). Deflate (ZIP) cannot compress below about 1/1032 (general knowledge, not from the files), so a ZIP of one run of zeros stays under 1,100 per member and under 2 GiB unpacked and passes both `zipBreaks` in `reader.mjs` and the container's listing check; bzip2, xz and 7z can exceed 1,100. The fixture `zip-zeros-1900mib.zip` is that case; section 3, L5 shows what happened.
8. **Time bound that does not stop the work.** `src/limits.mjs`: "the most time one container request may take: the file scanner's row ... (milliseconds)" = 900,000; `container/run.mjs` kills the child it spawned after `timeMs`. Section 3, L4 records what happened locally when that bound passed.
9. **Unclear ODS clause.** `PROBE-SPEC-L1-L2.md` line 27: "ODS | 10 MB, 50 MB, 20 MB with a 1 MB zip-expansion ratio". I cannot tell whether "1 MB" is the archive size, the declared content size or a ratio; `read-bounds.mjs` has `ods.content_xml` and `file_safety.ods_declared` (8 MiB) which I did not read as rows. One reading was generated (a small file whose `content.xml` expands by a large factor).
10. **65,535 or 65,536 rows.** `PROBE-SPEC.md` line 12 "its 65,536-row limit"; M15 (`LOAD-PER-TYPE.md` line 22) used 65,535 rows. Generated here: 65,535 rows (and 20 and 100 columns), via LibreOffice from a CSV; the 100-column file is 84.9 MB, over the 50 MiB spreadsheet bound, so it tests the refusal, not a wide read within bounds.
11. **Instance type unspecified.** `PROBE-SPEC.md` rows L4 and L5 say "at the instance type"; `reader-container/wrangler.jsonc` sets `standard-1` (the cold-start/idle clause of P-M17 names `standard-1` and `standard-4`). The probe takes either by flag; which one the pass bars belong to is not stated.
12. **"The intended image".** `PLATFORM.md` P-M17 says "the intended image"; the only image I can name is the reader's. Its digest in `wrangler.jsonc` is stated as published by the release (`container-images.yml`), and `Dockerfile` says "never built in a session, K1898"; whether it exists on Docker Hub I cannot check.
