**The mechanism (record-core alone; no other module changed how it gets its storage).** `BOOKKEEPING_TABLES` (exported, frozen: `sessions`, `admission_door_window`, `admission_session_window`, `keeps_pending`, `keeps_last`, `knock_rate`, `doorbell_tally`, `doorbell_limit_last`, `acquire_stages`). On every `writeCount()` until each listed table that exists has been found, the module makes three triggers on it (insert, update, delete: `CREATE TRIGGER IF NOT EXISTS`), each doing `UPDATE bookkeeping_tally SET n = n + 1`. A bookkeeping row changes `total_changes()` by exactly 2 (its own row and the tally's), so `writeCount() = total_changes() - 2 * (tally - tally at the connection's start)`; the baseline is read in the constructor and shared by every instance over the same `sql`. `bookkeeping_tally` is a new own table of this module (`schema.mjs`, made whole by `CREATE TABLE AS SELECT`, which counts no row, so a record nothing has written still reads 0), declared exempt from purge, export never, sight group (`OWN_DECLARATIONS`); the three table-list tests that enumerate this module's tables (`record-core.test.mjs` R31, R71; `t33.test.mjs` R21) name it now. If the platform refuses the triggers the counter falls back to `total_changes()` whole (never wrong, recomputes more).

**What it does not do (stated, not hidden).**
1. **KV writes cannot be excluded.** The scheduler's heartbeat (`storage.put("sched_beat", …)`, `scheduler/index.mjs:642`) and any `storage.put` are rows of the platform's `_cf_KV` table: a trigger on it is refused (`SQLITE_AUTH`, measured on workerd) and a `put` raises `total_changes()` by 1 (measured: two puts, counter 0 to 2). So each scheduler firing moves the counter once. That is per firing, not per request; the Queue's own 5 s bucket already allows one recompute in 5 s. This is QUESTION J-next below.
2.
