### R41 (CHANGE B3) — the four fields
1. **Root cause** (measured with EXTRACTION #30's files; Node, same session as the numbers below). `PdfDoc` parsed every object of the file into a map and kept it beside the whole file as a string: 107.7 MB retained after open for the 8.4 MB volume (56,309 objects, mostly its tagged structure tree); anchors were read after the last page, holding every link page's glyph positions; every font's code map was cached for the document; the answer itself held one object per undecodable code (313,990 markers for the 2.4 MB volume, 738,872 for the 8.4 MB, 281,547 and 644,973 of them `unmapped_code`, R12) and `document` as a second flat copy of the pages' text (27 MB more for the 1,354-page volume, whose text is two-byte). Live memory after the call (answer alone, after a collection): 34.6 / 80.0 / 53.5 MB for BUD / PER / APP.
   What changed: (a) `ObjectTable`: an object is a place (file offset, or offset in an object stream) plus the facts the loads ask of every object (dictionary/stream, `/Type`, Standard-handler candidate); the value is parsed from a window of bytes when asked for and the recent ones kept (3M cost units); every definition is still parsed once at open, so "a later definition wins" and "an unparseable object is absent" are what R8 states; the file is no longer held as a string. (b) An object stream is decoded at load, then read again when an object in it is asked for: `inflateChecked`, a synchronous RFC 1951 decoder whose output is proved by the stream's Adler-32 (otherwise the platform's decoder and its recoveries, and the first decode is kept as first decoded, or compared with the second if under 2 MB); at most 16 MB of decoded object streams held. (c) Anchors are computed page by page. (d) Identical markers on a page are one frozen object. (e) `document` is a rope of the pages' own text. (f) The font cache holds 25,000 code-map entries. (g) Large (>= 128 KB) Flate streams are decoded once at exact size and proved, not collected as chunks and copied.
2. **Why the tests missed it, and the fix.** No test measured memory, and the real volumes were never read in a test (the module's tests are hand-built, small). Fix: `memory.test.mjs` reads the three real files, each in a process of its own with the V8 heap held to idle + 56 MB (the collector then runs as a limited isolate's does), asserts it completes and that heap + array buffers polled above the baseline stay under 64 MB, and that the answer's digest (all of it, structurally, not written out) equals the pinned digest of the tranche tip's answer; plus eight small-file tests of the table, the second reading (and its fallback), markers, fonts, embedded-file trees, large streams and the anchors.
