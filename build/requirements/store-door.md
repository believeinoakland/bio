## Public

### Purpose

The record store's door, `dispatch(req)`: it routes each internal request to the module map that serves it, answers a project-naming read with the existence act first, refuses a purge a litigation hold forbids, holds the promotion step the old store registered, files a doorbell pull and its promotion as one act, and resolves the assistant for a draft before the draft's handler. It decides no route's behaviour: each answer is its owner's, and the envelope is `answer-envelope`'s.

### Provides

Terms. **The door** is `dispatch(req)`, reached only from the Worker through `plane`'s store. A **stamp** is a value `control-plane` sets from the authenticated caller (`store-request` R4); this door reads stamps from the request and never from a body's own fields.

**`dispatch(req)`, the record store's door**
- **R1** (was `control-plane` R26) An empty POST body is `null`, and a body that is not JSON is refused 400 `BAD_JSON`. A route no module serves is refused 400 `unknown op: <op>`. An answer is `{ok: true, result}`. The routes are the modules' own maps (the `membershipOps` pattern).
- **R13** (K2157; `control-plane` R61) A route-map answer that is a `Response` (`file-safety`'s byte answers: `openoriginal`, `openwithwarning`, `safeview`, `safecopy`) is returned as given, its status, headers and body unchanged, never wrapped in R1's JSON envelope.
- **R2** (was `control-plane` R27) A read whose parameters name a project (the declared `PROJECT_NAMING_READS`), asked with a stamped `viewer` and naming a discoverable project, is answered by `membership.existenceAct` first (C-70.1), before its route runs. The reads declared to name no project are listed with the reason. (T51 fix round 6, G12c; K4571) `PROJECT_NAMING_READS` also holds the list keys `casedrafts` `projects` and `inquirystrength` `ids` (`PROJECT_NAMING_LISTS`), beside their single keys. A read whose parameter is a list of bundle ids is fenced id by id exactly as the single read: each distinct id is asked of `visibilityOf`, and `existenceAct` for a discoverable one, before the route runs; a project the viewer sees only at EXISTENCE is answered with the single read's answer for that id, byte for byte, the lowest such id when several (so the answer does not depend on the order listed); a hidden or fully seen id falls through to the route with the list as sent. A list is an array (body, or a string) or, in the query, a JSON array, a comma list or the repeated key, split on anything that cannot be in an id; a single parameter is read as before (a comma in `id` is not a list). The door never truncates: the list's bound is its owner's. `reviewcopy`'s `drafts` (and `draft`) are draft ids, not bundle ids, so they are unfenced and the read stays among the reads naming no project. Test: `dispatch.test.mjs`: the batch in five spellings, six id mixes, hidden and seen controls, order independence, one `visibilityOf` per distinct id and `existenceAct` for the discoverable one only, no viewer (membership not consulted), malformed lists (no throw), and `reviewcopy` unfenced.
