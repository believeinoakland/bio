## Public

### Purpose

The record store's door, `dispatch(req)`: it routes each internal request to the module map that serves it, answers a project-naming read with the existence act first, refuses a purge a litigation hold forbids, holds the promotion step the old store registered, files a doorbell pull and its promotion as one act, and resolves the assistant for a draft before the draft's handler. It decides no route's behaviour: each answer is its owner's, and the envelope is `answer-envelope`'s.

### Provides

Terms. **The door** is `dispatch(req)`, reached only from the Worker through `plane`'s store. A **stamp** is a value `control-plane` sets from the authenticated caller (`control-plane` R17); this door reads stamps from the request and never from a body's own fields.

**`dispatch(req)`, the record store's door**
- **R1** (was `control-plane` R26) An empty POST body is `null`, and a body that is not JSON is refused 400 `BAD_JSON`. A route no module serves is refused 400 `unknown op: <op>`. An answer is `{ok: true, result}`. The routes are the modules' own maps (the `membershipOps` pattern).
- **R13** (K2157; `control-plane` R61) A route-map answer that is a `Response` (`file-safety`'s byte answers: `openoriginal`, `openwithwarning`, `safeview`, `safecopy`) is returned as given, its status, headers and body unchanged, never wrapped in R1's JSON envelope.
- **R2** (was `control-plane` R27) A read whose parameters name a project (the declared `PROJECT_NAMING_READS`), asked with a stamped `viewer` and naming a discoverable project, is answered by `membership.existenceAct` first (C-70.1), before its route runs. The reads declared to name no project are listed with the reason.
- **R3** (was `control-plane` R47) (DEC-113, DEC-36) `projectholds` (`actions` R58) is among the reads declared to name no project (R2), with the reason that it answers each project the viewer does not see at `FULL` as `held: null`, never refused, so R2's existence answer is not run for it. `actionholdrelease`, `actionholdpreview` and `projectholds` are routed through `actions`' own map (R1) with the stamps `op-declarations` R12 declares and none taken from the caller (`control-plane` R29).
- **R4** (was `control-plane` R46) (DEC-113; K1252, K1253) In the store's door (R1), an `op=purge` reaching the store of the `bio` namespace (the real record; the object's own name, `plane` R2) is refused 409 `PURGE_HOLD_IN_PLACE` (C-69.5, its row held in `answer-envelope`'s table, its R8) when `actions.purgeHeld({bundleId})` (its R60) answers `true`: the whole-store purge (`bundleId` absent or empty, `record-core` R22, R72) while any litigation hold is `in_place`, and the single-bundle purge of material in a held project, of an action carrying a standing hold, or of a bundle whose project cannot be determined. A failure to ask it refuses too. The check runs before `record-core`'s `purge` arm (its R72), so nothing is cleared, read for proof or written. The refusal names no action, project, member or bundle but the `bundleId` asked. A removal ordered while a hold stands waits for the hold's release (`op=actionholdrelease`, `actions` R56). A purge reaching the `scratch` store (the test store) is never refused for a hold.
- **R6** (was `control-plane` R25, the store's half; the Worker's is `answer-envelope` R5) An error thrown anywhere in the store's door is answered with a named internal-error code (`STORE_INTERNAL_ERROR`, C-69.4) and a correlation id. It never carries the stack, the message, a path or a line, and the stack is logged server-side under the correlation id.
- **R9** (was `control-plane` R59, the door's read in the store; K1943) The store's door reads a stamped `session` and an ask's `grant` (R11's read log) from the request's body or a header, never from its query (`control-plane` R59 sends them so; `dispatch.mjs`:220's grant among them), and places no credential, secret or digest of either in the address of any request it makes. (K2038) The headers are `x-bio-session` (a stamped session, and the token `admission` asks `session` to resolve), `x-bio-grant` (an ask's grant) and `x-bio-credential-sha` (the digest `admission` asks `aicredentiallook` to resolve); the door hands each value to its owner's map on the in-process URL object it passes to `store.routes(url, body)` (as `session`, `grant`, `t`, `sha`), which is no request's address, so the owners' maps are unchanged. (T37; N761, its share; plan T37 rule 4; K2129, K2175) A grant's `secretSha` (a review grant's, a template grant's, a case edition's or a statement acknowledgement's digest, and `aicredentialmint`'s) reaches the owners' maps only in the internal request's body, which the door hands to `store.routes(url, body)` as it arrived: the door hands no `secretSha` on the in-process URL, adds no header for it, and removes a `secretSha` found in the internal request's query from that URL before any owner's map receives it, so no owner can read one there (`credentials` R53, `review` R29, `ratification` R32, `case-authoring` R62, `filing-templates` R27; the control plane's send is its N761 requirement).

**The promotion step** (`step.mjs`)
- **R5** (was `control-plane` R42) (K764, K861; provenance R52) This module holds the promotion step `legacy-store` registered (plane R10). It exports the step whole for `plane` to register under this module's name, and registers nothing itself and edits no file of `plane`'s. The step is `provenance`'s `testimonySlot()` (its `check`; its `project`, whose refusal rolls the promotion back and whose `testimony` joins the answer on the testimony path only) and `membership`'s sight index (`reindexProjectSight` on every promotion, D-497), which `membership` cannot register because it does not use `promotion`. It runs at the rank `legacy-store`'s step had, whatever this module's own place in the order: its `check` after the checks of every module before `legacy-store`'s old place in the order (`monitoring`'s included) and before `tasks`', and its `project` after those modules' projections and before any later module's. So every step's checks and projections, every answer's keys and values, and the order of refusals are those of today.

**The doorbell's pull** (`pull.mjs`; N364, DEC-78 item 1)
- **R7** (was `control-plane` R36, the pull and its promotion; `control-plane` keeps the routing and the `by` stamp) The store's pull (`pullAndFile`, the internal route `inboxpullfile`) reached by `op=inboxpull` pulls through capture's `pullKnock` (capture R65), with `by` as the door stamped it, and in the same act promotes the pulled document as a new information bundle at `collected`, the puller its author; the pull and its promotion are one act, through capture R65's `within` (K559, K580): a refusal or a fault of either leaves neither written, and a fault answers a fixed sentence, never store text. A knock already pulled whose capture no bundle holds (pulled through capture's own route) is promoted by the door's next pull of it (K609). `op=inboxresolve` with `status: "pulled"` is that pull reached as capture R32's resolve, and it takes capture R32's reason: a `reason` absent, not a string, blank or over 2,000 characters is refused `RESOLVE_NO_REASON` (capture's row, C-118.7, 400) before anything is written, and an admitted reason is carried to capture so that it is recorded on the knock's row with the pull, in the same one act as the pull and its promotion; `op=inboxpull` takes no reason (capture R65; K1023). (DEC-88 (2); K1037)
