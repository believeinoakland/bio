## 1. The three open questions

### (a) Record-type registration for `STD-`, `CONF-`, `CONS-`, `ESC-`

**Proposed ruling.** A layer-9 record type is registered in the catalogue, as `BIAS` was (PL-12/D-84): `legacy-checks` gains each prefix in `BUNDLE_ID_RE` and `ANN_ID_RE` (bio-checks 23–24), its type in `OBJECT_TYPES` (40) and its state table in `STATES` (272ff.); `promotion` gains no type-registration service. All four types are added by **one small `legacy-checks` job at the head of layer 9**, not by the four module jobs, so four jobs never edit the same three lines concurrently. The tables: `standard`, `determination`, `consequence` each one state (`recorded`) and no edges (a correction is a successor, never a move: standards R6, conformance R7, consequences R6); `escalation` `open`, `suspended`, `ended` with the edges open→suspended, suspended→open, open→ended, suspended→ended (R14 does not refuse ending a suspended escalation; R15). Ids are `allocId(prefix, year)` followed by a slug the module writes, the form every existing type has.

**Reason.** Promotion's own contract says the state table "is the catalogue's" (promotion R15) and it lists `STATES`/`vocabFor`/`normalizeType` in its Uses; on `main`, `promotion/index.mjs` 16 imports them from `bio-checks.mjs`, and the catalogue refuses an unknown type at bio-checks 1182. A registration service would be a new promotion capability for four entries the existing pattern already carries; the catalogue moves out of `legacy-checks` whole when it is split, taking these entries with it. `allocId`'s `<prefix>-<year>-NNNN` plus a slug satisfies `BUNDLE_ID_RE`, so the map's id-shape worry (standards map §5.2) is not a conflict.

**Also, because K108 (3) already ruled an escalation a record object:** `modules.json` gives `escalation` the use `promotion`, and `escalation.md`'s Uses gains it (the escalation map §3 and §4's "if K108 (3) stands" are stale: it stands). The job checks that the catalogue's per-type front-matter checks admit each new type's document (the rows the legacy-checks job adds).

### (b) A subject-neutral `lawProposalLabel`

**Proposed ruling.** The same head-of-layer `legacy-checks` job adds one composer, `proposalLabel(proposedBy, subject)`, over `lawProposalState` (already subject-neutral: blank → `unstated`, `isMachineIdentity` → `machine_proposed`, else `member_proposed`), with the sentences in one closed table keyed by subject: `governing_laws` (today's `LAW_PROPOSAL_STATES`, word for word), `standard` (standards R9), `comparison` (conformance R12: "not a determination"), `filing_draft` (filings R5: "a draft nobody has approved or sent"), `theory` (filings R14: "a candidate, never the group's position"). `lawProposalLabel(p)` stays, as `proposalLabel(p, "governing_laws")`, so `actions` and `rec195-laws-proposal.test.mjs` are unchanged. The requirements' phrase "`lawProposalLabel`'s three states, one composer" is read as this composer (a wording change in standards R9, conformance R12, filings R5, R14, done by BOB when folding).

**Reason.** The three states and the one composer are what the requirements ask for (standards "Decided by BOB": "one composer, never a second copy"); the sentence is what differs, and today's sentences say "this action's list of governing laws" (bio-checks 769–776), which is false on a standard, a comparison or a draft. One table in one place keeps PL-17's rule (the plane publishes the sentence; no surface composes a second) and lets each module name its subject without a copy. A per-module sentence beside the shared state would put four label sentences in four files, which is the REC-46 failure the composer exists to prevent.
