# G54 diagnosis: two complete published editions on biosmoke8 have no case file (read-only; 2026-10-23)

Input: `no-manifest-diagnosis.md` (CASE-2026-4783 and 6227: complete, `manifest_sha` null; 4864 and 8024 are incomplete and expected). Nothing was written to biosmoke8 or the repository. Account checked on every call: `20b533579290b9b93168345edd3b7f72` only (the settings, versions, observability and GraphQL answers all came from it; no other account appeared). No secret was printed.

**Verdict: the cause is PROBABLE, not proven.** It is not the data and not the case-file builder. It is in the input/output of the post-commit block (the Worker's or the object's), which records nothing. The deploy of G54 carries the logging that names it (section 5).

## 4. Candidates, ranked (cause: probable)
1. The post-commit block did not run to its end for the request that completed the edition: a client disconnect or the invocation cancelled by the platform (op=ratify/op=caseratify run it inside the request, with no `waitUntil`), or a transient R2/DO error thrown (uncaught on those two paths). Consistent with: identical data succeeding and failing, no record, 4783's half-copied materials, the object being killed minutes earlier.
2. A transient `STORE_SILENT` on `casefilefacts` or `recordcasemanifest` (returned as `{ok:false}` inside an answer seen once by the caller).
3. Ruled out: the data (builder reproduced), the version/binding, a missing material, CPU, subrequests, value bounds, and "assembled on read" (nothing assembles on read).
What would prove which: a log line naming the step, the error and the sizes, which G54 adds, written by every assembly, and the durable outcome row.

## 5. What the deploy carries so the cause is named (K4426)
`assembleCaseContainer` writes one structured `console.error`/`console.log` line per attempt (event `casefile_attempt`, case, edition, via, step, ok, reason, error name and message, file count, bytes, elapsed wall) and records the same fields durably (columns on `published_cases`); a throw is caught at its step and recorded, never lost. Workers Logs must be on at the deploy: the script upload resets it (it was off after the 10-20 upload); the bundler/installer step that enables `observability` is named in G54 as a check of the deploy (P), because a log line nobody can query is not logging.
