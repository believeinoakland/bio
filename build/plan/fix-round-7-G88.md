### G88 · A 12 MB plain text is classified whole in one synchronous stretch (docprofile; the longest wait 631-806 ms against G82's 500 ms bar)

**Source.** READING-PIPELINE #29's record, section "G82" (`build/jobs/T51/reading-pipeline.md:605-612`); `r7-phase.probe.mjs` (header); `r7-contention.test.mjs` asserts p95 only (57 ms for the text shape), and prints the longest. Plan G82 (`fix-round-7-T51.md:301-310`) and §0 R-CLOCK. Read in full: `reading-pipeline/index.mjs:2385-2445`, `docprofile/readtext.mjs:255-420`, `docprofile/doctypes/registry.mjs:60-140`, `site-profiles/recogniser.mjs:47-75`. Nothing in the repository was changed; one timing script run in the scratchpad (node, local, no deployment).

(1) **Cause, with file:line.** `bio-plane/src/reading-pipeline/index.mjs:2419-2420` (`classify()`, called at :2436 for a text read as text) runs `identify(profCtx)` then `doctypeFor(...)` over the whole decoded text. `doctypeFor` (`docprofile/doctypes/registry.mjs:85`) calls `types.recognise(ctx)` (`site-profiles/recogniser.mjs:56-66`), a plain `for` over the registered types calling each `detect(ctx)` synchronously, then `alsoOf` (:`registry.mjs` `askAll`) asks the types after a CERTAIN winner. Measured in node on the probe's 12 MB text with the real eight types: `identify` 56 ms, `doctypeFor` 827 ms (types: regulation 237, meeting_minutes 97, meeting_agenda 56, staff_directory 55, staff_report 20, policy 29, the rest small), against workerd's ~1.0 s. Nothing in the chain awaits, and a bare `await` would not yield anyway. **Owner: docprofile** (`build/modules.json`: id `docprofile`, paths `docprofile/`, tests `docprofile/test/`). `doctypeFor` and the walk over the registered types are docprofile's; the detectors are `doctypes`' (and the other readers'), the loop engine is `site-profiles`' (`recognise`), and the call site is reading-pipeline's. Why the bound does not cover it: `CLASSIFY_WHOLE_MAX_CHARS` (2 MiB, `readtext.mjs:270`) is applied only at `readtext.mjs:409`, `sheets && flat.text.length > BOUND`, i.e. only to a sheet container inside `readText`, by design ("a PDF's text, a page, a paragraph shape and a bare string are classified whole, of any size", :263-265). A plain text has no `sheets`, and reading-pipeline's own `classify()` (R42, one classification per read) never goes through `readText` or `classificationView`, so it passes the full 12 MB to every `detect`. G48 bounded the 17 MiB CSV path only. R38 bounded this classification by HEAP only (no second copy), never by time. A sample is wrong for a text (a type may rest on any page), so the fix is a yield, not a bound.
