What the study of Team and Institution found, and three decisions

You asked for a study of how to support the Institution and Enterprise levels (K5444), and said Institution is built in T53 once the study reports and you decide (K5570). This is that report. Every figure says whether it was measured on the test copy or not yet measured. The test copy is plat-s1, running the alpha's code (0.87.0) at the Team level, with test prototypes added.

What we found

  • The errors members saw come from one cause. The team's record lives in one "room" (one Cloudflare Durable Object). When the room runs out of memory, Cloudflare restarts it, and every request in progress at that moment fails. We counted 227 such restarts in 36 hours of testing. measured
  • It is not caused by having many members. With 5, 10, 15, 20, 25 and 30 members, each repeated three times, the restarts happened at every level, from 5 members up, with no point where things break. More members only means each restart catches more requests in progress: 1 to 10 at 5 to 25 members, 17.5 at 30 (averages). measured
  • What uses up the memory is reading newly added documents, which happens inside the same room that answers members. Most of that memory is short-lived scrap the reading leaves behind: when the scrap is cleared, memory falls back to where it started, so it is not data the room keeps. measured, on our own machine
  • Five code changes are already decided (K5798). They cut that scrap by about half for a typical reading step (9.6 to 5.3 MB), and by three quarters for the first step of an 8 MB file (158 to 40 MB), with identical results. Whether that is enough to stop the restarts is not yet measured. The load test after the build will show it.
  • Enterprise would not fix it. Cloudflare's pages give every plan the same 128 MB of memory for the room and the same 10 GB of storage. They give no separate Enterprise figure and no way to raise either. Enterprise adds uploads up to 5 GB, the US government (FedRAMP) data region, control over where requests are processed, and a contract. stated by Cloudflare, not measured by us
  • Members' screens are fast; administrators' screens are not. A member's screens appear in 0.5 to 0.65 seconds. With 500 documents waiting for review, the administrator's Home, Queue, Add and Project screens took 2.8 to 4.8 seconds. The cause is heavy lists, and the fixes are already in the drafts. measured
  • A correction. Keeping a team's stored data in one region (Europe or the US) is available on the ordinary paid plan, not only on Enterprise. Your earlier decision to offer "keep my data in this region" (K5440) is unaffected. Only where requests are processed needs Enterprise.

Sources: the study files on the PLATFORM lane (s1-results, s1-upload-and-resets, s1-b-ramp-memory, s1-n-determination, enterprise-s3-draft), each with its commands and logs.

Three decisions

Architecture · S4-1

Where should files be read: inside the team's room, or beside it?

Today a file added to the record is read into text inside the same room that answers every member. Reading a large file needs a lot of memory for a short time, and when that tips the room over its 128 MB, everyone's requests in progress fail.

  • A · Keep reading in the roomRely on the five decided code changes and on load management (below). This is the least work, but it is not yet shown to stop the restarts. A large file can still tip the room, because the memory a reading needs grows with the file.
  • B · Read beside the room · recommendedA separate reader takes the file, turns it into text, and hands only the finished text to the room. The room's memory then no longer depends on how large a file is, and a reader that runs out of memory fails one reading, not everyone's work. The five code changes stay. Cost: an extra step for each document read, of a size not yet measured, and some reading code moves. It is built and proven by the load test.
  • C · Decide after the load testBuild the code changes first, run the load test, and choose A or B from its restart count. This is cheaper if A turns out to be enough, but Institution would wait for the result.

Why B: the restarts happen from 5 members up and come from the reading, not from the number of members. So no member limit removes them; only taking the reading's memory out of the room does. B does that for both levels whatever the file size.

Architecture · S4-2 · Institution (Level 2)

How should an Institution's larger record be held?

At Team level all of a team's text and its search index sit in the one room, and they are 96 % of everything the room holds. They are what grows as documents are added. We tried three ways to make room for a bigger record.

  • A · A room per projectEach project gets its own room, with a directory linking them. It splits the load, but screens that look across projects need several rooms, and you noted it would be "non-trivial" (K4747). Costed on paper only; not yet measured.
  • B · Text and search index in file storage, packed · recommendedThe bulk text and its index move to Cloudflare's file storage (R2), packed into one file per document. Measured: a screen reads text about 0.1 s slower (136 against 29 ms for 100 passages), search takes the same time (about 0.26 s), and storage is 1.24 times the text. The room keeps its small working tables. The room's own search read 341,131 rows for one common word and slows as the record grows; the packed index needed 6 small reads. Whether it stays that fast at a much larger size is not yet measured. measured on a small sample
  • C · A cache of shared screensKeep frequently read answers near the member. It made no visible difference to the screens, and its effect under load could not be measured.

Why B, together with S4-1's B: the two answer different limits. Moving the reading out stops the restarts; moving the bulk text out stops the room filling up. A stays on paper in case the measured Institution still falls short; C is set aside for now. Institution's figures (record size, members at once) stay not yet measured until its load test, and the install shows them that way.

Architecture · S4-3 · load management

What sets how much work runs at once, and where does the waiting line live?

You asked that a busy copy queue requests and tell the member, never "try again", and that it sense the risk of a restart (K5760). The tests show the limit cannot be a number of members: restarts came at 5 members as at 30. What fills the room's memory is the work in progress: files being read and large uploads.

  • A · A waiting line inside the roomSimplest, but a restart empties the line at exactly the moment it is needed, and the waiting requests fail.
  • B · A small gatekeeper in front of the room · recommendedA gatekeeper holds the line and lets work into the room by its size, so that heavy work runs one or two at a time. After a restart it halves the amount it lets through and raises it slowly. Waiting requests survive a restart. Cost: one more step per request, about 50 ms by the hop we measured, plus the gatekeeper's own time, which is not yet measured.

Why B: it keeps your rule that nothing a member asked for is lost, even when the room restarts. The short, non-modal "a bit slow" sign you asked for is with the design lane as a need; it shows when a request waits longer than its screen's time budget.
