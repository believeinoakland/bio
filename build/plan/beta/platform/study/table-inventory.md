# Civicsmith record: table inventory for the split study (S0)

**The 14 KB cap cannot hold one row per table: 616 tables are declared.** This file gives one row per module cluster. Every one of the 616 tables has its own row (module, scope, project/bundle columns, sight, purge, export, derive, keys) in the companion `table-inventory-all.tsv` (this folder; columns table, module, scope heuristic, project columns, bundle columns, sight, export, derive).

## How this was made, and what the sources do not say

- `record-core.md` R21 says every table is declared by its owner with `purge`, `expunge`, `export`, `sight`, `derive` and `version_chain`, but the file lists none of them: the module files do not either. So the 616 were read from the code's own `declaredTables()` by booting the test suite's real store (`bio-plane/test/m/store-assembly/world.mjs`, every module real). Class counts are from that run.
- **Scope is my reading, not a declared class.** No source declares a table's scope. In the TSV, PROJECT = the table has a project key column or belongs to a project-only module; MIXED = keyed by `bundle_id` (so reachable to a project only through `bundles.project`, which is NULL for a bundle that states none, record-core R34, promotion R53) or has a project column that is not its key; TEAM = neither. This is a heuristic: counts PROJECT 106, MIXED 217 (176 bundle-keyed, 27 project-column-not-key, 14 two-bundle), TEAM 293.
- **No source states a per-table size.** Stated: SQLite 416,444,416 B for 496 documents, 1,794 files, 535,983 text units; R2 `bio-captures` 2,164.9 MiB in 1,355 objects; DB about 19% of captured bytes, 0.84 MB per document (`lane-performance-HANDOFF` P17); 4,800 rows read per call, about 30 ms CPU; the DB grows by extracted text, about 1.4-1.5x its size (FILES F5, via `service-levels-draft.md`). Every size cell below is UNCLEAR unless it says otherwise.

## (1) Hard cases for a per-project split: rows that name more than one project or are read across projects

1. `bundles` and `bundles.project` (nullable): the one link of a bundle to a project. Project-less bundles (documents stating none, project bundles, standards, registries) have no room by this rule: UNCLEAR what room holds them.
2. `register` / `seen_in` (provenance, capture): a capture has one home (possibly project-less, possibly project A) and appears in project B only as a `seen_in` row; its readings and text units sit with the home.
3. `connections`, `asserted_connections`, `refs`, `theme_placements`: two-bundle keys, ends in different projects; backlinks and dangling checks read every bundle (R19 of record-core: audit resolves against the WHOLE corpus).
4. `contradiction_*`: cross-project by definition (K5 keys the two projects); `_optins`/`_responses` keyed project+pair.
5. `entities*` and `resolutions`, `reading_refs`/`_terms`: one registry for the team, joined to every project's readings.
6. `inquiry_findings`, `steps`, `step_proposals`, `leg-earning` reads, `costShares`: one question drawn on by several projects.
7. `queue_state`, `tasks`, `finding_dispositions`, `action_hold_projects`: Queue and Home are a union over a viewer's projects.
8. `cases`, `case_documents`, `published_*`: a case names several projects.
9. `bundles_fts`, `selection_items`, `bundle_projection`: search over group scope.
10. Sight: `viewerPredicate` and `hiddenBundles` are SQL over `bundles.project` plus `project_sight`, `project_visibility`, `project_participants` (membership R43, R88), applied to every read.

## (2) Bulk text and indexes that could move to R2

- Already in R2: captured file bytes (`CAPTURES` bucket, 2.1 GB, keyed `<store>/captures/<sha>`), blob-backed files (`files.blob_sha`, NULL `content`), evidence store (record-core R38).
- In the database today: `capture_text` (the text units; a unit over 128 KiB is chunked, no cap per capture since R22/R99; units land in batches of about 1 MB), `capture_text_fts` (stored, FTS5; whole-store purge only), `bundles_fts`, `bundle_projection`, `bundle_terms` (derived-rebuildable, retrieval R30, R3 `reproject`), `reading_refs`, `reading_ref_terms`, `readings.reading` (whole reading as JSON), `reading_history`, `calc_table_bytes`, `portal_snapshot_parts`, `case_import_blobs`.
- Sources state: text units are the growth term (535,983 in the test copy); the DB holds 1.4-1.5 times the extracted text; a 100 MB text file lands about 150 MB of units. They do NOT state `capture_text`'s or the indexes' bytes, nor whether FTS5 can leave the object (UNCLEAR; a search over R2-held text needs a replacement index).

## (3) Transactions and invariants that span projects

- `transact(fn)` (record-core R32) is one transaction over the whole store, every module's tables; a promotion commits everything it writes in one transaction (promotion R2). A split loses this across rooms: UNCLEAR which promotions touch tables outside their own project room (listeners write `refs`, `readings`, projection, `connection_dirty`, entity resolution in the same transaction: extraction R24, R19; retrieval R1).
- Id uniqueness and no reissue (R1, R8, R28, I-1): one `seq` and one `minted_ids` ledger; `seedMintLedger` reads ids from every module's tables.
- `manifest`/`history` append-only and `seq` order per bundle (R16, R29): per bundle, so room-local.
- `forkProject` (promotion R44) copies one project's files into a new project.
- Entities, people, standards: shared version-chained registries; `identity_claims` link, never merge.
- Connections and contradictions: derived over every pair; `connection_dirty` queues work from any promotion; contradiction's per-project disclosure rule (DEC-85) needs both sides' holders.
- Ledgers: write counter (R89-R91), `observation_log`, `ai_usage`, doorbell and door windows are team-wide; `ai_limits` per project.
- Purge (R22): whole store or one bundle, in one transaction over every declared table.
- Expunge (R79): tombstones, append-only, record-wide; purge-exempt.
