**Status** · PLATFORM #3, 2026-10-28. The upload-stage study, the failures traced in the Worker telemetry to the store object exceeding its memory limit, and the readout and piece prototypes. Continues `s1-results.md` (steps 1a-1e, the baseline and C on); same copy and conventions (through the agent proxy, raw times with the proxy in unless stated; credentials never printed).

## Upload stages, C=1 against C=3 (PLATFORM #3, 2026-10-28, BOB #330's ask for CAPTURE T53-108)

**What ran.** `plat-s1` with `proto/levels-2-3-stages` d9abfdaa live (`PROTO_STAGES=1`, `PROTO_C=1`, `PROTO_C_HELD=1`; alpha 0.87.0, Level 1, Seed A of 503 documents, reading idle at the start). Driven **through the real Add door in Chromium** (`study/door-stages.cjs`): the project's Add door, "A file or photo", a text file of 250 KB-1.9 MB with 8 random trailing bytes (so none is a second sighting), then the page's own `captureupload` and `promote`; each response's `Server-Timing` read. C=1 (control) and C=3 uploaders, 6 files per batch, each run twice, alternating (c1, c3, c1, c3): **12 uploads at C=1, 12 at C=3**. Signed in as the **administrator** (`plat-s1-admin`; no member was enrolled yet, so the uploader is not a plain member). Raw times, proxy in. Also run: `scripts/upload-stages.mjs` (API call only, `study/upload-stages-fixed.mjs`: it called `/?op=` where the page calls `/api/?op=`, and its statement lacked the three lines), n=6: wall p50 2.6 s at C=1, 3.8 s at C=3, no failure.

| stage (median, ms) | C=1 | C=3 |
|---|---|---|
| whole page wait, click to "Captured" | 4,398 (max 7,417) | 5,405 (one 16 s; one never) |
| `captureupload` call, page's view | 1,992 | 2,392 |
| door admission (`up-door`) | 48 | 53 |
| room wait (`up-room-wait`) | 15 | 0 |
| body read (`up-body-read`) | 51 | 83 |

| profile, registrar, promote-within | 0 | 0 |

| `promote` call, page's view | 1,319 | 1,574 |
| `promote` in the room (`do-promote`) | 1,000 | 1,185 |

(Zeros are synchronous stages: workerd's clock does not advance in them; they are marked, not measured.)

**Reading.**
1. **On this copy, now, an upload takes 4.4 s at C=1 and 5.4 s at C=3, not 11-13 s.** About 2 s is `captureupload` (0.3 s hash and put, 0.7-0.9 s the door's read of what the object answered, the rest the proxy and the hop), then 0.5 s of the page's own work, then 1.3 s `promote`. No stage grows much with three uploaders: door admission and the room wait stay under 0.1 s. **The earlier 11-13 s did not recur**; what differed then was the reading of 380 just-landed files behind every upload, which is not what was running now (reading had finished; each of this study's files adds a little). So the 11-13 s is the reading backlog's wait, not a stage of the upload itself: **not shown by this run, it needs the same study during a bulk load**.
2. **The "timeout at 120 s" is, in the one case seen, not a slow upload.** One C=3 upload (410 KB) got **a 502 from `captureupload` after 2.8 s**, its stages stopping in `up-hash-put` (3,302 ms, the longest of any; no `up-read`, no `up-answered`): the object failed in the hash-and-put stage (the write of the bytes). The page then showed no "Captured" and my driver waited 150 s. So a small file "timing out at 120 s with three uploaders" may be **a fast failure that the page does not report**, which the earlier study read as a wait. I did not look at what the page printed; the driver waited only for the success text. **To confirm:** one C=3 run that also records the page's text at the failure (next).
3. One `promote` took 12.6 s (C=3, file 5), the only slow tail; its time inside the room (`promote-within`) cannot be timed (synchronous). One in twelve at C=3 failed; none at C=1. Twelve uploads each is a small sample.

**Caveats.** The uploader was an administrator; reading was idle; 24 uploads in all; the 502's cause (a write error from the object's store call, or the object's overload answer) is not known: the stages say only that it came in hash-and-put.

**Follow-up, the failures (same session, more C=3 batches; driver now waits 45 s and records the page's text).** C=3 in all: **54 uploads, 5 failed (9 %)**; C=1: 12, none. The five, none ended by a slow wait: `captureupload` 502 after 2.8 s (stopped in `up-hash-put`, 3.3 s), `captureupload` 500 after 1.8 s, `captureupload` 502 after 2.6 s (stopped with `up-body-read` 2.5 s and `up-hash-put` 1.0 s, neither near the others' 0.05 and 0.3 s), and **two `promote` calls that answered 502 after 2.7 and 1.6 s, after a good `captureupload`** (so the file was held, the document was not made). **In all five the page stayed on the Add screen and showed no result line and no words of an error that my check found (the first 400 characters of its text; the rest was not read)**; the success text never came. So the failure is **a quick 5xx from the room, shown to the member as nothing**, and any 2 minute wait in the earlier study was the driver waiting for text that never came. The admission, the room wait and the other stages do not grow with three uploaders; what does is the chance that a call in the object fails. `object-age` (the room object's age at the call) is 0-10 s on both the good and the failed calls (failed: 4.4-7.0 s), so the object is young at nearly every call and its age does not separate them; the cause of the 5xx is **not found by these stages** (a candidate to check: the object's memory with three bodies in hand, or an overload answer; the cron every 5 minutes is not the cause, the failures came within seconds of one another). Medians over all C=3 runs: page wait 5.9 s, `captureupload` call 3.0 s, `promote` call 1.5 s.

**Correction, and the repeat after a bulk load (PLATFORM #3, same day).** (1) **The page does say something on a 500.** With the page's text read to its end (earlier I kept only the first 400 characters), one failed upload shows: "This team's Civicsmith failed while handling the request, before it could produce an answer. That is a fault in this team's Civicsmith ... whether any part of it took effect is not known from here. The administrator can find the details in its logs under the reference given with this answer." So the statement above that the page shows nothing is **withdrawn**: the page names a fault, but it leaves the member without a retry and without saying whether the file was kept (a `promote` failure after a good `captureupload` leaves the file held and no document). Whether the same text shows on a 502 (an answer from the Worker's edge, not the room) was not read. (2) **Counts.** C=3: 7 of 87 uploads got a 5xx (8 %: the five above, a `captureupload` 502 after 20.6 s, a `captureupload` 500 after 2.3 s); C=1: 0 of 18. One more C=3 upload failed with no server error at all (the driver's file choice did not take: "Choose a file or take a photo first"); it is left out. (3) **Bulk load.** 45 uploads through `captureupload` at C=3 (`study/upload-stages-fixed.mjs`) all answered 200, 2.9 s median, 7.0 s longest; they make **no reading backlog** (the reading follows `promote`, which the API script does not send), so the repeat that was meant to bring back the 11-13 s did not: straight after it, the door at C=1 took 3.9 s (6 of 6) and at C=3 6.5 s (8 of 9; the failure the 502 after 20.6 s). The 11-13 s is therefore still unexplained; the candidate remains the reading of many documents being promoted while uploads land (needs promoted documents, i.e. the browser path in bulk, three at a time for many minutes). (4) **The room is heavier than Seed A now:** `op=stats` read 569 bundles and 761,416 text units (Seed A: 503 and 127,502): the 66 generated files of this study (one line a unit, 250 KB-1.9 MB) carry about 9,600 units each, five times the seed's density per document, so the later runs (including the failures) were in a room with 6 times Seed A's text units. The failures also came in the first batch (569 → 575 documents), so density is not shown to cause them.

## The 5xx traced in the Worker's telemetry (PLATFORM #3, 2026-10-28; BOB #331's ask, K5733)

**Method.** Cloudflare's observability query on our account (`POST /accounts/<account>/workers/observability/telemetry/query`, filter `$metadata.service = plat-s1` and `$metadata.error` exists; `study/tq.py`, no key shown), 36 hours back, 2,262 error events; each event carries the request's op (`$workers.event.request.search.op`), its event type (`fetch` or `alarm`) and, for the alarm, a stack.

**What the telemetry says.**
1. **The cause of the 5xx is the store object (the team's room) exceeding its memory limit and being reset** ("Durable Object's isolate exceeded its memory limit and was reset."): 227 such events in 36 hours (141 on a request, 86 in the alarm), each followed by "Internal error in Durable Object storage caused object to be reset" (298). A reset kills **every request in flight in the room**, so the op named in a `fetch` event is a victim, not the holder: 38 `captureupload`, 16 `bootstrap`, 7 each `heldcaptures`, `projectvisibility`, `notices`, `projectparticipants`, 5 `rerunread`, `aiuseovertime`, `projectstake`, 4 `promote`, `inbox`, and about 30 other reads.
2. **When.** By hour (Z): 10-27 19: 8, **20: 91, 21: 59** (PLATFORM #2's Seed A upload and its mixed ramp, whose "502 at 15 members" (§1e-mixed) is therefore the same fault), 22: 10; 10-28 06: 11; 13: 34, 14: 18 (this study). None in the quiet hours between. They stop within minutes of the last promoted document being read (last event 14:05:33, the last upload 14:04).
3. **Where in the alarm.** The 86 alarm resets all have the stack `set < #reconcile < Scheduler.onAlarm < Scheduler.alarm < Store.alarm` (`scheduler/index.mjs`): `set` is `setAlarm`, the first storage call after the alarm has run its due consumers, so **the memory is taken by what the alarm ran just before** (the consumer is not named: the scheduler's `scheduler_consumer` log line, written only for a call past its slow threshold, is not in the telemetry for this window). Alarms that reset ran 25 ms-1.5 s.
4. **What does not do it, by test.** (a) **45 `captureupload` calls at C=3 (the API only; 0.2-1.9 MB) made no reset and no failure** (13:57:40-13:58:32; no promote, so no reading follows). (b) **30 `heldcaptures` calls, three at a time (266 KB answer, 3.0-9.8 s each), made no reset** (14:10:43-14:11:41). So neither the upload's own memory nor the heavy administrator read alone does it. (c) **The failure rate does not rise with file size** at C=3 (400 KB 2 of 29, 800 KB 2 of 25, 1.2 MB 2 of 18, 1.6 MB 0 of 7, 2 MB 1 of 7), as a victim's would not.
5. **What does it, by the shape of the evidence (not proved).** The browser path: `captureupload`, then the door's `extractread` of the file, then `promote` with the document's reading and units embedded (up to 1 MB), then the reading of the new document in the alarm; at C=1 the alarm still reset (13:40, three times) with no upload failing, at C=3 three such chains are in the isolate at once and the resets take the requests in flight. **So the holder is the reading of newly promoted documents in the store object (the alarm's consumers and the `extractread` / `promote` ops around them), at the room's present size (about 880,000 text units, 6 times Seed A's)**; the module is whichever consumer the alarm runs for reading (reading-pipeline or extraction; scheduler is only where the limit is noticed). To name the op and its peak: a run with a member uploader (no `heldcaptures` on its page), C=1 against C=3, sizes 200 KB and 2 MB, with the reading consumer's slow log lowered (a prototype change), is the next step.

**The consumer named (PLATFORM #3, same day; no prototype needed).** The scheduler's `scheduler_consumer` lines are in the telemetry after all: they are structured (`source.scheduler_consumer`: name, outcome, started, ended) on the alarm's own request, not in a message text, which is why a text filter found none. Joining the 34 alarm resets of the last 4 hours to the consumers run in the same alarm (`study/alarm-consumers.json`): the always-due consumers (`overdue-scan`, `connection-derive`, `archive-monitor`, `task-drain`, `selection-sweep`) end `ok` in 0 ms; **in 22 of 34 the first consumer to error is `pending-work`**, after running 40-881 ms (median about 500 ms); in 4 `overdue-scan` is the first to error (collateral, memory already spent), in 1 `document-copy` was still running, in 7 no consumer shows an error. **`pending-work` is store-assembly's `pending.mjs`, the owed-work ledger finished by the alarm: for documents promoted from the Add door its job kind is `reading` (`extraction.readHeld`), the reading of a held file into text units and their search index.** So the holder is the reading of a newly promoted document, run by the alarm in the same isolate as the members' requests. The ledger itself expects this failure ("an owner that kills the isolate (memory, CPU) never returns"; it counts an interrupted run, stamps the unit, halves the budget after two kills and states a unit unread after three), so a reset is retried and not lost, but each reset kills every request in flight. **Not measured:** the reading's peak memory (no memory figure in the logs; workerd offers none in the isolate), which unit (page, window) it was on, and whether the job kind was always `reading`. What would size it: the job rows' `interrupted` and `job_unit_attempts` counts for the study's documents (an owner read), and a run with units per tick limited.

## Readout prototype, control arm (`PROTO_READOUT=0`) (PLATFORM #3, 2026-10-28 14:31-14:40Z)

**Deploy.** BOB #331, 14:32Z: `proto/levels-2-3-readout` ac1f0a88, bundle sha256 d86a2ae57796da58c69602ee9e26438196b7544ec85583a883acf9fd9be5d9d0, `PROTO_READOUT=0` (normal behaviour plus two structured log lines per reading: `proto_readout_read` after the file is read into units, `proto_readout` after the units are landed). **What ran.** The browser flow at C=3, 3 batches of 12 (36 uploads, the study's generated text files 250 KB-1.9 MB, administrator uploader), then the telemetry for 14:31:30-14:40:30Z.

**Results.** (1) **4 of 36 uploads failed (11 %)**: `captureupload` 502, 500, 502 and a `promote` 502 after a good `captureupload`: the same rate as before the build (7 of 87). The control arm adds no failures. (2) **16 error events** in the window: 10 memory resets in the alarm, 6 on requests, 16 storage resets. (3) **`process.memoryUsage()` exists in workerd and answers zeros** (`rss` 0, `heapUsed` 0, at every point): no memory figure is available from inside the isolate; the figures that remain are the proxy and the resets themselves. (4) **A reading runs in pieces of at most 4,096 units** (median 4,096; about 340 KB of unit text from a 1 MB file; `more: true` until the file is done); the proxy's strings held by one landing are about 512,000 characters (0.5 MB), so **what the landing holds in JavaScript is small beside the 128 MB limit**. A reading step's wall time is 141 ms median (1,050 ms longest). (5) **Where the reading died** (the alarms that reset, joined to the log lines of the same alarm): of 6 reset alarms that ran `pending-work`, **5 logged no `proto_readout_read` line and no landing line: they died inside the read step** (reading the held file into units), or before it; 1 logged the read line and died in the landing. So, at this sample, **the memory is taken by reading the held file into units (the reader, its working strings and the parse), not by writing the rows and their search index**. Alarms that did not reset show 17 landings and 45 reading steps, so most pieces complete.

**What it predicts.** If this holds, writing the units to R2 instead of the room (`PROTO_READOUT=1`) will **not** stop the resets; it would, at most, save the rows. The `=1` arm is the test; it also answers whether the FTS triggers weigh in at all. **A second candidate not tested:** the isolate's baseline: the plane's bundle is one line of 28 MB of JavaScript (`bio-plane.bundled.mjs`), the code alone being part of the 128 MB the object may hold, so a reading that is small in itself can tip it over.

## Readout prototype, `=1` arm (units to R2, no `capture_text` or FTS rows) (PLATFORM #3, 2026-10-28 14:41-14:47Z)

**Deploy.** BOB #331, 14:42Z: the same bundle d86a2ae5…, `PROTO_READOUT=1` (one change from 0). **What ran.** The same 36 uploads at C=3 (3 batches of 12), then the telemetry for 14:41:20-14:48:30Z.

| | control (`=0`), 9 min | readout (`=1`), 7 min |
|---|---|---|
| uploads failed | 4 of 36 (3 `captureupload`, 1 `promote`) | 3 of 36 (all `promote` 502, after a good `captureupload`) |
| memory resets (alarm / request) | 10 / 6 | 12 / 12 |
| `capture_text` rows written by the readings | all | **0** (23 landings, 46 R2 objects, 34.5 MB) |
| reset alarms that logged a read line before dying | 1 of 6 | 1 of 8 |
| reset alarms that logged the landing line and died after it | 0 | 3 of 8 (a fourth died after `pending-work` was already "running" and the landing) |

**Reading.** (1) **Writing the units outside the room does not stop the resets**: with no `capture_text` and no FTS rows written at all, the room still reset 24 times in 7 minutes and the same share of uploads failed (3 of 36 against 4 of 36). So **the rows and their search index are not what exhausts the memory**; row-saving from B (96 % of the room's rows) is a size and cost matter, not the fix to the 5xx. (2) **Where it dies is not one place**: in the control, 5 of 6 reset alarms died before the read step's line; in `=1`, 3 of 8 died after the landing line, in what follows the landing (the state write, the next piece's start, or another consumer of the same alarm), the others before any line. The alarm is the unit that runs out, as a sum, not a single step: with the 28 MB bundle, the SQLite page cache and the isolate's own state already resident, a reading that is small (about 0.5 MB of strings held) is enough to tip it. (3) The packed objects are large: 34.5 MB of R2 for 23 landings (1.5 MB per landing against about 340 KB of unit text per 4,096-unit piece), because each unit carries its extent and reference in JSON (4 times the text). (4) **Formats and sizes of what died** (BOB's question): every held file in these runs is plain text (`text/plain`, `.txt`), 250 KB-1.9 MB, so one reader (the text reader); no PDF, office or CSV file was in the runs of this session (Seed A's earlier mixed files, 10-27 20-21Z, had 150 resets with text, CSV, DOCX and PDF together, which this session did not separate). **One file is enough to die** at the alarm: at C=1 (13:38-13:40Z) the alarm reset 4 times and no upload failed; three at once makes the requests in flight the victims (C=3: 8 to 11 % of uploads against none of 18 at C=1).

**Next test.** A smaller piece (`PROTO_PIECE_UNITS`, the units a read step handles at a time; today 4,096 in `reading-pipeline`): if the resets scale with the piece, the fix is the read step's bound; if they do not, the baseline (bundle, caches) is what the 128 MB lacks.

## Smaller read piece, `PROTO_PIECE_UNITS=512` (PLATFORM #3, 2026-10-28 15:05-15:13Z)

**Deploy.** BOB #331, 15:05Z: `proto/levels-2-3-piece` 17cf5848 (base: the readout build), bundle sha256 e13b0ba7ec30881961f3d0abdf230c7ada589f95cc94d219a86a2980af78c582, `PROTO_PIECE_UNITS=512` and `PROTO_READOUT=0` (the control arm's normal write plus log lines; the live value was 1 from the earlier arm, so this was changed with it). **What ran.** The same 36 uploads at C=3, then the telemetry for 15:04:56-15:13:20Z.

| | control, piece 4,096 | readout `=1`, piece 4,096 | **piece 512** |
|---|---|---|---|
| uploads failed | 4 of 36 | 3 of 36 | **2 of 36** (both `captureupload` 502) |
| memory resets (alarm + request) | 10 + 6 in 9 min | 12 + 12 in 7 min | **13 + 4 in 8.4 min** |
| rate per minute | 1.8 | 3.4 | **2.0** |
| landings seen | 17 | 23 | **182** (88,831 rows in `capture_text`) |

**Reading.** **An 8 times smaller piece did not reduce the resets or the failures** (about 2 resets a minute and 2 to 4 of 36 uploads in all three arms; the differences are inside what 36 uploads can show). The alarm ran 182 landings of up to 512 units instead of 17 of 4,096, so the work was done in many small steps and the object still ran out. So **the units a read step produces are not what bounds the memory**; EXTRACTION's R122 as worded (a budget of units and index rows per run) is not by itself the fix. The candidate this leaves: **a read step takes the whole held file into memory every piece** (bytes, the decoded text and its lines, about 1-2 MB for these files and more for PDF or office files), whatever the piece's units, and the pieces after the first read it again: a smaller piece then costs the same peak and more reads. The tests of the worker show the file taking 24 readHeld calls at 512 against 3 at 4,096 on a 1.1 MB text, which fits it. **Not verified**: that the reader holds the whole file per piece (the code was not read for it); and the baseline (28 MB bundle, caches) is the other candidate. **What would settle it:** a read that takes a byte window of the file per tick (the reader asked for a byte range, not the whole), or a measurement of the reader's peak on one 1 MB text in a local workerd; the isolate gives no memory figure (P-34).

**Correction to the reading above (same entry, after reading the reader's code).** `reading-pipeline/index.mjs` (`readInner`, G68) already reads a later piece **from a byte window** named by a `w` cursor ("the object is not read whole", `WINDOW_BYTES`), and a PDF from its open document; so "the whole file every piece" is **not** established and may be false for these text files (which cursor kind the 1 MB texts got is not known: the `proto_readout_read` lines do not carry it). What the piece-512 run still shows stands: **the units a piece produces do not bound the memory**. What it leaves open is wider than the file's bytes: the first piece's read of the object (whole), the window's own size (`WINDOW_BYTES`), the FTS and SQLite page cache on landing (not the cause alone: P-35), the other consumers the same alarm runs, and the 28 MB bundle's baseline. The next measurement is the reader's own: its peak on one 1 MB text in a local workerd, or a log line of the cursor kind and window bytes per piece.
