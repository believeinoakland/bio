**A6-R97** (T53; DEC-462; amends R12, R96, R28; `queue-producers` R56) **A signing-key item passes a choice of act through for each key it lists.** For a `signer-self-registered` item the `disposition` is `available: true`, `scope: "key"`, `requires: ["key"]` (the key field as `credentials` R7 and R83 name it, BOB's), and `keys`: one entry `{key_b64, acts: ["signerknown"], instead: "signerset"}` for each key in the item's `basis.keys`, in the same order, no entry for a key `basis.keys_more` only counts. A viewer to whom the plane would refuse an act is offered no entry for it (R17's gate), whichever key. The top-level `acts: [signerknown]` of R96 is kept as the name of the answer that ends a key. The bridge (R28) refuses a `signer-self-registered` key with `CLASS_NOT_DISPOSED` and `instead: [signerset, signerknown]`, the first the one the screen leads with (R12's `door` rule: a list of op names). After an act on one key the next feed lists the item with that key's entries gone and the others unchanged; after the last key's act it lists no item. *(not yet met: T53)* Test: a member with three listed keys: `disposition.keys` has three entries in `basis.keys` order, `options` six entries, each pair carrying its own key; `signerknown` for the second key, then the next feed has two entries each and the first and third keys unchanged; the last two acts clear the item. ## 3. The key-making step's sentence ("a key not kept is gone when the browser closes")

Where it lives: not in `queue` or `screens-daily`. The step is `screens-settings` R57 (1) "Making the key" (the tick `signing.ceremony.keepkey`, `cs.signer.register({keep, passphrase, defer: true})`), and (2) "After it is made" (`screen.account.key.save`, "Save the key file" only when a file was made, then `screen.account.key.lost`; the file and passphrase live in page memory for the sitting). The maker is `interface-shell` R40.

Checked against `interface-shell` R40: it keeps the key on the device only when the tick is set (non-extractable, this origin's IndexedDB). Unticked, "the page offers a key file in the passphrase form ... made in the browser, and keeps nothing"; "Use a key file you already have" loads a key "for the sitting only". So with the box unticked:
1. "Gone" is true only for a member who also does not save the key file. A member who saves it can load it again; the sentence must not say the key is gone to her. R57 (2) draws "Save the key file" only for a key made unticked, so the file is offered, not forced.
2. The key is lost at the end of the sitting (page closed or reloaded), not only when "the browser" closes; and the loss is of the private key only. The public key stays registered and `active` (`credentials` R9: nothing replaces an earlier key) until an administrator revokes it, so the group's Queue then shows an unusable key: the member who loses a key makes a new one and the old is revoked.
3. The sentence must be shown at the tick, before the key is made (R57 (1)), not only after (`screen.account.key.lost` is in (2), after it is made, too late to choose). If the sentence is placed beside the tick it must give both ways to keep it: tick the box (kept on this device), or save the key file when it is offered.

Result: "If you do not keep it on this device, save the key file when it is offered; otherwise you cannot sign with this key once this page is closed" is true under R40; the bare "gone when the browser closes" is not true for a member who saved the file. No requirement line is needed (the box is already unticked; DEC-462 changes a keyed word). At START BOB checks whether `screen.account.key.help` or `.lost` already says it; if not, REPORT the key owed to UX-DESIGN with points 1-3 as the brief.
