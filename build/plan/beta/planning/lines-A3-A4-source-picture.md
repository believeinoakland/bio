## A4. A member's own photograph

**Findings.** (a) file-safety does not yet use image-cover or image-codecs; BOB adds the edges (layers 1 < 3). (b) `coverAreas` gives pixels only for baseline JPEG and 8-bit non-interlaced PNG, is not a redraw, refuses progressive JPEG and interlaced PNG and exposes no metadata as data. (c) image-codecs decodes baseline JPEG, PNG and JPX but writes none. (d) `stripMetadata` (R8) never re-encodes, so it would carry a hostile bitstream.

**Lines touched** (existing ids). file-safety R11 ("`NO_SAFE_VIEW` (another format)") amended; R45's Control ("a PNG, an HTML file and a NUL file still `NO_SAFE_VIEW`") and C-140.10's translation contradicted for JPEG and PNG. screens-intake R36's Control ("a PNG draws `refusal.NO_SAFE_VIEW`") contradicted; R5 widened (it speaks of pages). These stand and bind the picture: file-safety R1, R10, R12, R22, R23, R25, R35, R37, R55, R56 (an image is graded by its source, its structure check `not_examined`, never `clean`); case-disclosures R33 / DEC-185 (2) (camera metadata is not read for `photosOf`); image-cover R2. Highest ids: file-safety R59 (R42a lettered), image-cover R11, image-codecs R13 (no change drafted).

**What is kept and what is dropped.** Rule (Bob's DEC-460): no metadata byte of the file is carried into the picture. What can be read safely as typed, bounded values is shown beside the picture as "the file says" (unchecked). All else is dropped and only named in `left_out`; each drop below is for a safety reason.

| Kept as data (shown beside the picture) | Why |
|---|---|
| Orientation (1-8) | Bob's words: the camera's orientation |
| Time taken (and the file's modify time) as stated | Bob's words: when. Never graded, never dates a document (L9) |
| Place: latitude, longitude, altitude, direction, time, datum, as numbers range-checked; shown as "near {place}" with the exact figures one step away | Bob's words: where (L8; K5471, K5473) |
| Width, height | The picture's own |
| Camera make and model, lens, software, exposure, ISO, focal length, flash | Beyond Bob's examples (Q-A3A4-5) |
| Camera and lens serial numbers, image unique id, owner name, artist, copyright holder: read into the record as data, **not shown by default** (K5471, K5473) | Identify a person or device beyond what the picture needs (L7: keep or drop, still bracketed) |
| Text the photographer wrote: description, comments, keywords, byline, credit, place name, PNG text | Beyond Bob's examples (Q-A3A4-5 = L22); plain text only, capped |

| Dropped (named in `left_out`; the data given beside) | Why it must go |
|---|---|
| Thumbnails and other second pictures (previews, extra pictures, gain and depth maps) | A second image that may show the unedited picture; count given |
| Maker notes and vendor blocks | Opaque structures that parsers have been exploited through; presence and size given |
| ICC colour profile | A parser reached by a stranger's bytes; name and colour space given (Q-A3A4-4) |
| XMP packet, C2PA / JUMBF credentials, other embedded blocks and other PNG chunks | Nested containers and markup; XMP properties named in the kept list are read as data; "credentials present, not checked here" |
| Bytes after the image's end | A hidden payload; size given |
| Binary-valued fields (GPS processing method, area information) | Opaque |

### file-safety

**A4-R1** (T53; DEC-460; amends file-safety R11, R45, C-140.10) **A photograph has a safe view: a picture redrawn from its pixels.** [depends on L6: as written if Bob says as recommended; else no safe picture is offered until every photograph kind has one] `safeView` of a baseline JPEG or an 8-bit non-interlaced PNG answers `{ok:true, kind:"picture", derived:true, of, sha256, content_type, width, height, file_says, left_out, original}`. The picture is redrawn from the decoded pixels and holds nothing else: no EXIF, XMP, IPTC, comment, profile, thumbnail, second image, trailing byte or orientation tag (`file_says.orientation` says how to turn it). No note is written and `clean` is never implied (R56); a held file has it (R12). A kind not covered by A4-R7 stays `NO_SAFE_VIEW`, and its translation names pictures. *(not yet met: T53)* Test: a JPEG with GPS EXIF, thumbnail, maker note, ICC profile, XMP, IPTC, an extra picture and a trailer answers a picture whose pixels equal the original's (rotation 0), and a byte search of the served bytes for each marker, string and coordinate finds none; likewise a PNG with text, EXIF and ICC chunks. Control: a PDF answers as before; an HTML file, a NUL file and an unlisted kind still answer `NO_SAFE_VIEW`.

**A4-R2** (T53; DEC-460; K5471, K5473; new in file-safety) **What is kept as data is a closed list.** `file_says` holds only the kept fields of the table above, each `{value, from:"the file", checked:false}`. The camera and lens serial numbers, the image unique id, the owner name, the artist and the copyright holder are read into the record as data but are not shown by default (A4-R5, A4-R10) [these depend on L7: as written if Bob says as recommended; else the field is dropped]. [Coordinates depend on L8; exposure, lens, ISO and the text fields on Q-A3A4-5 = L22; the profile's name and colour space on Q-A3A4-4 = L21: each as written if Bob says as recommended; else the field is omitted.] A field that is absent, malformed, out of range or over its bound is omitted and counted in `left_out`, never guessed. Strings are plain text. `file_says` is display only [depends on L9]: it never changes a grade, a date the record holds, `photosOf` or a note. *(not yet met: T53)* Test: each kept field by name, the serials, id, owner, artist and copyright holder present in the record and absent from what is shown by default; latitude 91, a 1 MB string, `<script>` and a bidi override, a self-pointing directory and a 5 MB maker note each omitted or neutralised within bound. Control: nothing outside the list appears.

**A4-R3** (T53; DEC-460; DEC-467; K5471, K5473) **What was left out is said.** `left_out` is `[{kind, count, bytes}]`, `kind` in a closed set: `thumbnail`, `maker_note`, `profile`, `extra_picture`, `after_end`, `xmp`, `credentials`, `other_metadata`, `unreadable`. The set is the closed list the design's "Left out of the safe picture: {what}" reads by key (DEC-467): the screens' `{what}` keys are these kinds and no other. *(not yet met: T53)* Test: the A4-R1 fixture lists each with its size; a bare image lists none; every kind has a screen key and the screen draws no `{what}` outside the set. Control: a kind outside the set is never answered.

**A4-R4** (T53; DEC-460; amends file-safety R1, R12, R25, R35) **The picture shares the original's life.** A picture is made once for a file, is not itself a capture (never registered, R37) and is purged with its original (R25); `file_says` is kept only with it. While it is not yet made `safeView` answers `SAFE_VIEW_PENDING`; when it cannot be made it answers `SAFE_VIEW_FAILED` with the maker's reason, final. No `file_says` value reaches a log, a note, a forwarded count or a `file-scanner` request (R10, R23, R35). The original's bytes, digest and grade are unchanged (R22). *(not yet met: T53)* Test: a queued photograph answers pending, then a picture; a progressive JPEG answers `SAFE_VIEW_FAILED` with its reason; logs, notes and the forwarded record hold none of the fixture's coordinates or serial. Control: bytes, digest and grade are as before.

**A4-R5** (T53; DEC-460; K5471, K5473) **Who sees the picture and what the file says.** The picture and `file_says` are answered only to a viewer who may see the capture, as the original's views are. Serial numbers, the image unique id, the owner name, the artist and the copyright holder [depend on L7] are not shown by default, are shown no more widely than the picture itself, and appear in no list, count or forwarded record. The exact coordinates [depend on L8] are one step away from "near {place}" (A4-R10), shown as text with no link, and the page makes no request to a map service or any outside service. *(not yet met: T53)* Test: a viewer who may not see the capture gets what a capture that is not there gets; the coordinate text carries no link and no map request is made; the serial is absent from every list and from the default view. Control: a viewer who may see the capture reads the figures one step away.

**A4-R6** (T53; DEC-460) **The picture maker withstands a hostile file.** The module's test runs a corpus of hostile photographs against the maker: size bombs, truncation, bad Huffman or restart data, `%PDF` or HTML in a comment, bytes after the end, cyclic or out-of-range directory offsets, huge entry counts, a compressed-text bomb, bidi text, a profile claiming a gigabyte and a polyglot; each is refused or made safe within the stated bounds, with no allocation above a bound and the isolate alive, and its pixels agree with an independent decoder and with exiftool / Pillow fixtures. *(not yet met: T53)* Test: the corpus passes. Control: an ordinary photograph of each kind still makes a picture.

### image-cover

### Suggestions (A4; bind nothing)
- **file-safety.** `file-safety` uses `image-cover` and `image-codecs` (BOB's edges). The picture is a queued `safe_view` job made by `renderBatch` within R55's bound, stored once under its own digest outside `captures/`; maker refusals travel as `renderer_reason` carrying the image-cover code. The security review of the maker (the threat; every parser reached: JPEG, PNG, the directory walker, the XMP scanner, IPTC, the profile header read, text decoders, inflate; each bound; where it runs and what that process reaches; the escaping where drawn; the corpus of A4-R6) is the process BOB runs under DEC-460's "safe-picture maker and its security review"; a reviewer other than the builder signs and BOB records each finding's disposition (P17). It is not a line here.
- **image-cover.** Decode through image-codecs (`rotate:0`) to 8-bit samples and write a fresh PNG holding only IHDR, IDAT, IEND (PLTE if used), streamed (image-cover R4), because a 90-degree turn cannot stream in 128 MB (a 48 MP frame is 144 MB); the PNG writer is new (pagepixels.mjs:706-831 to read, not import). New read-bound rows: `meta_bytes`, `ifd_entries`, `ifd_depth`, `string_bytes`, `inflate_bytes`; answer bound `boundOf("image","picture_bytes")`. XMP properties are read by a scanner that expands no entity and follows no reference. HEIC or any native or WASM decoder runs only in `file-scanner`'s separate process. No codec change is drafted: HEIC, WebP, GIF, TIFF, BMP, progressive JPEG and interlaced PNG have no decoder in the plane.
- **Screens.** A list thumbnail (`screen.held.thumb`, R11) should be the safe picture, never the original: not verified.

## Questions for Bob raised in L4

Each is small and has a recommendation; "as recommended" to all leaves the lines as written.

**Q-A3A4-1 · Do administrators see a source's link?** Bob's words give the link to "the members the team listed". Today administrators may read the log of who has read a source's details. Should an administrator who is not listed also see the link? A: no, listed members only (Bob's words). B: yes, administrators too. **Recommend A**; the draft first said B and now follows Bob's words. **Decided (K5456): A, as recommended.**

**Q-A3A4-2 · Who is "listed" for a source?** Today the team lists members only when it records a detail about a source ("these members may read this detail"). A source about whom nothing has been recorded has no list, so nobody would see its link until a detail is recorded. A: listed means named on the list of any recorded detail of that source (nothing recorded, no link for anyone). B: the team keeps a separate list of who may see each source's link, set when the knock is pulled. **Recommend A**: it adds nothing new to keep; B if members must see a fresh knock's link at once.

**Q-A3A4-3 · Does the Inbox follow the same rule?** The Inbox shows "A source" to every member today. If it keeps doing so, the link is open to every member there although closed on Held and Document. A: the Inbox shows it to listed members only. B: the Inbox keeps showing it to everyone. **Recommend A**; otherwise the rule can be walked around.

**Q-A3A4-4 · A photo's colour profile.** A phone photo often carries a colour profile (wide-gamut, "Display P3"). The safe picture holds nothing from the file, so the profile is dropped and the picture is shown in standard colours; colours may look slightly flatter. A: drop it, say "shown in standard colours", show the profile's name beside the picture. B: carry the profile into the picture (truer colours, but the viewer's browser then reads a stranger's profile, a known attack surface). C: convert the pixels to standard colours before drawing (truer colours, but the plane must read the profile, the same risk, inside the safe-picture maker). **Recommend A**: the rule is "nothing from the file", and profiles are parsed by software that has been exploited.

**Q-A3A4-5 · How much of a photo's own text and camera data is shown?** Bob named when and where it was taken and the camera's orientation. The draft also shows (a) camera make, model, lens, software and exposure settings, and (b) text the photographer or software wrote: artist, copyright, description, comments, keywords, credit, place name. All are shown as "the file says", unchecked, plain text only, capped in length; serial numbers and owner name are L7's. A: only what Bob named. B: Bob's plus (a). C: Bob's plus (a) and (b). **Recommend C**: nothing in them is a risk once read as plain text, and "software" shows a photo was edited; the member can read the note that each is only the file's own claim.
