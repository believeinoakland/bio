## events (highest bold id R57; draft ids R58 and R59)

- **R58** (T53; N1259; C13 (5); DEC-406 I8; `court-doctypes` R6, R18; `following` R41; amends R38, R25) *(not yet met: T53)* **One entry of a followed register is one event, however many readings state it.** `followedRegister({captureSha, proceeding, by})` takes, besides the three court-doctypes content types it takes now (`courtlistener_docket`, `cpuc_proceeding`, `ecourt_roa`), `courtlistener_api`, the keyed JSON reading of CourtListener's docket entries (`court-doctypes` R18); any other content type is still refused `NOT_A_REGISTER`. (1) **Identity.** An entry's identity is `(register system, proceeding, entry id)`, never the reading's content type: the system is the one that assigns the entry id (`courtlistener_docket` and `courtlistener_api` are both CourtListener's; the other two assign none, `court-doctypes` R6, so their rows are skipped as now), and the held source key is `register:<system>:<proceeding>:<entry id>`. An entry id is the number the source assigns (`court-doctypes` R6, R18); a JSON reading and an HTML reading of one docket state the same number for one entry, and a reading that states none is skipped as now (`skipped`, never matched by date or text). (2) **A second reading adds evidence, not an event.** A reading whose entry already has an event under that key adds its capture as one more attestation of that event (the capture extent and, where the entry's date can be read, its dated fact, as the first reading's are held), found and never repeated (R7's `sameAttestation`), and writes no second event, no second `concerns` end and no change to the event's kind, status or `within`. The answer lists it in `readings_added: [{entry_id, event_id, content_type}]`, not in `written`. A reading of a content type that already attests the event with the same date and text adds nothing (`unchanged`), so a daily re-read of an unchanged docket, or of one that gained entries, adds attestations only for entries first seen in a new form. (3) **The first reading's facts stand.** The event's kind (`filing` or `order`) is the first reading's (R38); `when` is derived only from the governing attestation (R8, R9), so a later reading never moves it, and a second reading that states a different kind or a different date is answered in `disagreements: [{entry_id, event_id, field, held, stated, content_type}]`. A disagreement is reported, never fails the tick (`followedRegister` answers normally, the tick's outcome is unchanged) and is never silent (K4571): it is held with the second attestation and shown to members wherever the event is shown (the event's read, `readEvent`, lists each disagreement beside the governing reading, with both readings' captures). It never overwrites, merges or chooses: a member's `chooseGoverning` (R8) or `mergeEvents`/`splitEvent` (R14) settles it. (4) **Grading and attribution of each reading.** Each attestation carries its own capture's grade (`provenance.captureGrade`, as R2 and R7 read it), two readings giving two attestations and two grades beside each other, never one combined grade (R12); a `provisional` reading (`court-doctypes` R7, R18: the JSON shape is assumed until a member's authenticated capture replaces it) is answered with `provisional: true` in `readings_added` and `disagreements` and is never graded above its capture. Every row is stamped as the machine's (`class:daemon`, R22), cites its capture, and is correctable by R13, R14 and R20; the reading's content type is the one `extraction` holds for the attestation's capture, so no attestation column is added. (5) **Events written before this line** under the old key `register:<content type>:<proceeding>:<entry id>` are the same events: `followedRegister` looks the entry up under the new key and then, for a `courtlistener_docket` entry, under the old, and re-keys the source row to the new key in the same transaction when it finds the old; no event is rewritten, merged or duplicated by the change. Test: an HTML reading of docket entries 1 to 3 followed by a JSON reading (fixture marked as assumed, `court-doctypes` R18) of the same entries writes three events and then none: `readings_added` has three items, `written` is empty, each event has two attestations (two captures, two grades) and `readEvent` answers one event per entry; the same pair read JSON first, then HTML, ends with the same three events; a re-read of the same capture changes nothing. A JSON reading whose entry 2 states `order` where the HTML stated `filing` leaves the kind `filing` and answers one `disagreements` item; a different date leaves `when` as the first reading's, holds the second's dated fact, and `readEvent` shows both to a member. An event written under the old key is found by the JSON reading and gains the attestation, with no second event. Control: the same entry id on two proceedings is two events; an entry id of one docket and a different docket's same number are not matched across proceedings; `cpuc_proceeding` and `ecourt_roa` rows (no entry id) are skipped as before; a capture of any other content type, an HTML page and a JSON error body are `NOT_A_REGISTER` and write nothing; a hidden capture (R40) contributes no attestation to a viewer who may not see it, and the event is answered through the first reading only.
- **R59** (T53; N1259; C13 (5); amends R41, R25) *(not yet met: T53)* **A second reading is not a change, and no event is minted to join readings.** R41's rule that no event is minted only to join two readings of an aggregate holds here: the second reading of an entry is a further attestation of the entry's event (R58), recorded neither as an update by R25 (the source row's facts are unchanged by a reading in another form) nor as a `when_moved` or `participant_re_resolved` told to R16's listeners unless the new attestation moves the event's `when_cache` (it cannot, R58 (3)). A reading whose entry shows a changed date or text in the same form as before is R25's update and recorded as R25 says. Test: the second reading of an entry tells R16's listeners nothing; a changed date in a later HTML reading of the same docket is R25's recorded change. Control: R41's absence rule is unchanged (a row a later reading no longer states is not an event that ended, and no event is deleted).

## Refusals

The two new answer fields (`readings_added`, `disagreements`) are not refusals and need no catalogue row. Codes grepped across `bio-plane/src` and `build/` and found unused, in case PLANNING wants a refusal for a disagreement after all: `READING_DISAGREES`, `ENTRY_READING_DISAGREES`, `ENTRY_KIND_DISAGREES`, `READING_UNDATED`, `REGISTER_SYSTEM_UNKNOWN`; I propose none, since K231 wants one code and one row, and a refusal would stop the follow's tick failing on a harmless difference between two forms. BOB decided: a disagreement is told, never fails the tick.

## Suggestions (checks the events job makes first, before coding R58)

1. Entry-number equality: with a token, fetch one real docket's `/docket-entries/?docket=<id>` and its docket page; compare `entry_number` to the page's `entry-<n>` for every entry (including attachments, sealed and gap numbers). Until then JSON readings stay `provisional`, and a mismatch makes R58 (1) key JSON entries apart.
2. Stability: compare two reads of a docket across a consolidation or an amended docket if one is found; otherwise record it unproven (R6 treats the number as the source's identity).
3. Token and limits: call the endpoint with a free token; record the status code, the throttle headers, and whether 5/50/125 applies; size the tick's reads inside 125 a day.
4. Shape: `OPTIONS` on `/docket-entries/` and one real response; replace R18's assumed fixture with it.
5. Old-key events: the job checks read-only on biosmoke8 whether the store holds events under `register:<content type>:<proceeding>:<entry id>` (R58 (5) is needed only if so); it writes nothing there.
6. Filing path: how a keyed answer is filed as a capture and whether its `captureGrade` is null (`acquisition/keyed.mjs` files none; `following` R41).
7. `addAttestation` on a machine event after a member's `chooseGoverning` or a merge (`index.mjs:839`); two proceedings of one docket stay separate events (keyed by proceeding).
