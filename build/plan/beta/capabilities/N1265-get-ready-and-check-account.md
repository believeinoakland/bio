## 1. Bob's points

**B1. How "Check my account" knows a payment card is on file (the drawing says "a payment card" line; the ruling says "a throwaway probe made and removed").**
*Explanation.* Cloudflare gives Civicsmith no way to ask "is there a card on this account": the sign-in Civicsmith asks for has no billing permission (K4943). What it can learn is whether the account is on the paid Workers plan and whether R2 storage is turned on; Cloudflare requires a card for both (UNVERIFIED: that is my understanding, not read from Cloudflare today). Today's install learns about the card only when it tries to make the storage buckets and Cloudflare refuses.
*Options.*
- **C1. Derive the line (recommended).** "Payment card: ready" when the account is on Workers Paid **and** R2 answers as turned on (R43 reads this without writing anything). If R2 refuses as not entitled, the line says what was measured ("Storage is not turned on yet, which needs a card on file at Cloudflare") and links to Cloudflare's storage page, as R84 (1) already words it. Nothing is created, so the "creates nothing that stays" promise is true without exception.
- **C2. A real probe: make a small storage bucket and delete it at once** (as DEC-415 describes). It is the only direct test that a bucket can be made; but for a moment it creates something in the founder's account, and if the delete fails something is left behind (the check would then say so by name). It also asks Cloudflare for a billable resource on an account that may not be ready.
- **C3. Drop the card line**; the plan and storage lines carry the news.
*Recommendation.* C1. It keeps the promise made on the page ("Checking creates nothing that stays in your account") literally true and uses the evidence R84 already measured; the screen's line keeps the words Bob drew.
*Decision wanted from Bob:* C1, C2 or C3. (If C2: the probe is `installer-steps` R49 below.)

**B2. The second Allow page (UX consequence, through BOB to UX-DESIGN).** The installer keeps no secret and no token (R27: it has no storage). Cloudflare's "Allow" page gives the check a short-lived permission that ends when the check's page is drawn. To start the install after a passed check the founder is sent to Cloudflare once more. If Cloudflare shows the page again, "Install now" opens two Allow pages in a row. *Options:* (i) accept it, saying so on the screen ("Cloudflare will ask once more"); (ii) keep a sealed copy of the permission in the founder's browser for 15 minutes (this makes the installer hold a secret and a key, a change to the rule that it "declares no binding of any kind", R27, and to "never stores a credential"); (iii) run the check and the install in one run (no gate between them, which Bob's ruling rules out). *Recommendation:* (i). The gate stays a gate (R90) and the stateless installer stays stateless. Whether Cloudflare actually shows the page twice is UNVERIFIED; it is measured on the rehearsal account (K4942) before the screen is worded.

**B3. Whether the check should also test that the founder's email is verified.** Step 2 of "Get ready" is "verify the email". K4943 records that email verification "waits on a measurement". A line for it would need a further permission on Cloudflare's Allow page (a user-details read; K4943 notes such a scope exists) and Bob registers scopes on the OAuth client himself (DEC-415 owed, K3815). *Recommendation:* no line; Workers Paid cannot be switched on by an account whose email is unverified (UNVERIFIED), so the plan line carries it. *Decision wanted:* confirm no, or add the scope (a Bob act).

**B4. The scope count (a fact to correct, not a choice).** `installer` R2 says the sign-in asks "exactly the five scopes"; `installer-steps` R45 and K4942 imply six or seven (`account-logs.read` and `connectivity-directory.bind` each handled by its own step). DEC-415 asks Bob to register the sixth (`account-logs.read`, K3815) "if the check is to cover request logging". The check drafted here does not need it (no line reads logs). *Needed from Bob:* whether it is registered, so R2's count and the consent page's wording can be made true.

## 2. Technical choices (BOB's)

1. **Check mode lives in the installer's own routes** (`POST /begin` with `mode: check`), reusing R70/R84's code through `installer-steps`; no new Worker.
2. **The gate is a convenience with a second line, not a security control.** The only party the gate protects is the founder from a failed install in her own account. An unsigned receipt cookie (slug and time only) is enough for the first line; the real enforcement is R84 at the start of the install itself (already built), which refuses again for any unmet condition. No secret is added.
3. **Lines are a closed list** `CHECK_LINES` in a fixed order; the pre-conditions R84 (5) (permission) and (6) (which account) are handled before the list as they are today (approve again; choose an account); R84 (4) (the workers.dev prefix, registered only on the founder's click) is not a check line, since a check registers nothing: it is shown as a note under the name line ("Your address is chosen during the install").
4. **Link checking is a release check plus a weekly run outside the product** (section 6, journey-check R33); the installer Worker has nowhere to keep a result (R27).
5. **Words by key** (`setup-words`): the design's 52 keys (DEC-416) are the only sentences; code holds none (installer R72, R79).
