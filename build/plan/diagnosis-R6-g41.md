## 1A. The 26 pages of BUDGET-2024-APP with no unit (asked by the coordinator)

**Question.** `g26.probe.mjs:17` prints "1328 of 1354 (every page once: false)" while the reading says `read_through 1354/1354`, whole (`diagnosis-R6-g40.md` section 2). Which 26 pages have no unit, and are they dropped silently?

**Measured** (`g41-budget.mjs`, the real `read` over the pinned 15,932,155 B file with `unitsBudget: Infinity`; `g41-range3.mjs`, `extractPdfRange` on each page). Page numbers are **0-based** (the reader's `text.pages[].page`, the unit's `extent.page`, `provenance.pages[].page`).
- 1,328 units for 1,354 pages; the 26 pages with no unit are exactly the 26 `provenance.pages` entries with `chars: 0, text_sha256: null` (`reading-pipeline/readingprov.mjs:225`): `0, 1, 2, 4, 5, 7, 11, 53, 65, 187, 229, 329, 413, 555, 609, 885, 1019, 1063, 1119, 1145, 1163, 1185, 1305, 1307, 1352, 1353`. Every page with `chars > 0` has a unit (0 exceptions). The units' text (13,597,036 characters) plus 1,327 joining newlines equals the reading's `text_chars` 13,598,363 exactly, so no text is lost between reader and units.
- **22 are honestly empty:** pages 1, 5, 7, 11, 53, 65, 187, 229, 329, 413, 555, 609, 885, 1019, 1063, 1119, 1145, 1163, 1185, 1305, 1307, 1352 show no text and draw no image: `extractPdfRange` returns `chars 0` and **no** `undetermined` marker for each. A blank page is by design unmarked (`pdfstructure.mjs:2596-2603`, the `no_text_layer` marker needs a drawn image, :2622).
- **4 are not blank, the reader could not decode their glyphs:** pages 0, 2, 4 and 1353 (1-based 1, 3, 5, 1354) show text whose codes map to nothing: unmapped / misaligned codes 47, 47, 2,447 and 48 occurrences, and `image_unread` on pages 0 and 1353 (a cover image not read). `chars` is 0, so no unit; the reading counts them in `text_undetermined` (4,181 in all; a count only).
- **Not silent.** Extraction's `#unreadOf` (`extraction/index.mjs:1417-1441`, R27) names every page without a glyph-bearing unit in `unread_pages` and the Document screen says it from `unread_says` (`document.unread.pages`; `screens-inquiry/document.mjs:231,292`). By that code the answer lists all 26. The `blank units dropped` rule (D-531, `indexUnits` :1207) is what keeps them unitless. I did not call `op=reading` on this file to see the list; it follows from the code (not measured).
- **Verdict: not a dropped page; the probe's check is wrong.** `g26.probe.mjs:17` compares units to pages. The honest check is units + `unread_pages` = pages (1,328 + 26 = 1,354). Two notes for BOB: (a) the screen says "unread" for 22 pages that are blank, a wording that over-claims a failure (K4571 forbids the opposite, a silent gap, so this is the safe side); (b) the 4 undecodable pages (cover, title and contents pages) carry real text the reader could not map, and are named only as unread pages, not as "text present but not decodable" (a requirement for reading-pipeline / docprofile if BOB wants the distinction; not G41). Fix to the probe: the harness reports `unread_pages` beside `units` (`plane/shape/harness.mjs`, `r.reading`).

## 2. Options for the over-limit values (rows 1 and 2; row 3 and 4 follow below)

**The size of the problem is wider than CSV.** Row 1 is every workbook and every table-bearing document above a modest size, not one format. Whatever is chosen for `reading.cells` is chosen for xlsx, ods, docx tables and csv together (reading-pipeline R28 passes them as the entry emitted them).

### Option A: spill large keys of the reading into side rows, read back through extraction's own read
In `extraction` (layer 4): at the write, a top-level key of the reading whose JSON is over `READING_KEY_BYTES` (262,144 B, the constant R94 already names for the answer; so the keys R94 omits from `readingFor` are the keys A spills) is written as rows of a new table `reading_parts (capture_sha, part_sha, seq, chunk)` in chunks of at most 256 Ki characters (at most 768 KB of UTF-8 in the worst BMP case; `calculations` `TEXT_CHUNK` is the pattern), and the key in the stored reading becomes a stub `{"$part": {sha, chunks, bytes}}`. `part_sha` is the digest of the key's JSON, so a re-read of the same cells, and the history row of the same reading, share the part rows (no copy per history entry). Everything else is as today: `reading_sha256` and the `composed_readings` digest stay over the whole unspilled JSON (R21/R23: digests of the reading as composed); `json_extract(reading, '$.provenance')` etc. (:931-935, :1013, :1134) still work, because the small keys stay in the row. `readingOf` (R30) reassembles the key, so `content` (R52, R46), `events` and `progressions` see the same reading as today; `readingFor` (R94) already names the key as omitted and needs only to take its size from the stub.
- **Member:** nothing changes. Every cell stays findable and citable at every size the entry reads today. A reading that could not be stored on the platform now is.
- **Other modules:** `retrieval-browse` (`findin.mjs:343`) must read its `cells` through extraction's `readingOf` instead of the raw `readings.reading` column, since a stub is not cells (its R8 and the tests that build the `readings` row by hand change with it). `content`, `events`, `progressions` use `readingOf` and do not change. No other module reads the `reading` column.
- **Cost:** storage is about 11x the file for a CSV and 8-13x for an xlsx (each cell 147-161 B of JSON), per capture (and once more per distinct changed reading only if the cells differ). A purge of the capture must delete its parts (extraction's purge arm). The write still builds the whole JSON string once (R95), so memory does not improve by A: it is the same ladder as `diagnosis-R6-g40.md` section 3.3 (1 MB CSV survives, 2 MB with the copy dropped, 4 MB with a compact grid, the stream path to 8 MB).
- **Owner:** extraction. Touches extraction R19 (the writer), R21 and R23 (digests kept over the unspilled text, stated), R30 (`readingOf` whole), R94 (the omitted key's size from the stub), R22's neighbour for purge; retrieval-browse R8 (read path); no change to reading-pipeline R28, csv-reader R8/R9, office-readers R30, content R52/R46.

### Option B: a compact cell grid, then A above what the grid holds
The csv entry (and, if wanted, the others) emits `cells` as rows of values with the constants once (about 16 B a cell; `diagnosis-R6-g40.md` section 3.3 `bgrid`): the reading of a CSV is 1.10 MB per MB of file and stores to about 1.7 MiB of CSV under the limit; above that it still needs A. It saves memory (a compact grid survives 4 MB of CSV at the real shape). For CSV every cell's `type` is `text`, `declared`, `cached`, `formula` null and `source` is computable from the position, so a grid loses nothing. For xlsx, ods and docx the cells carry real types, declared types, formulas and cached values, so a compact form needs per-cell columns for them.
- **Member:** nothing visible if readers expand the grid to the same cells.
- **Other modules:** every reader of the cell shape changes or gains an expander: `content` `typedCellsAt` (R52, R46: `content/index.mjs:1114,1258,1277,1299`, `notice.mjs:110,182`), `retrieval-browse` (R8: `findin.mjs:350-394,652`), reading-pipeline R28 (passes cells "as the entry emitted them... neither altered"), csv-reader R8 and `typed-cells.test.mjs`, office-readers R30 and odf-reader R46 if the others follow. This is the wide change K4164 warns of: many modules at several layers rebuilt for one storage limit.
- **Verdict:** B is a memory fix for G40 (Bob's question there), not a storage fix; it does not remove the need for A.

### Option C: no cells above a stated size (the csv entry's stream path)
Above a stated size an entry emits no `cells` (`cells: null`, as it already does over 20 MiB), and the answer says so to the member (K4571: a bound that must stay is stated, never a silent partial read). Smallest code change (a constant per entry), and it is the memory fix for CSV beyond 4 MB (`diagnosis-R6-g40.md` 3.3: the stream path holds 8 MB).
- **Member:** **this changes what a member can do.** Today a sheet's typed cells let find-in answer a cell with its row (retrieval-browse R8), let a passage cite a cell range as typed cells (content R52), and show `formula`/`cached` (office-readers R30). At the limit's size this takes those away: for a CSV at about 190 KB, for a workbook at about 90 KB zipped, which is most real budget workbooks. The words stay searchable (the sheet's text is in `capture_text` and FTS) but the typed cell, its position and its formula would be gone. That is a product decision, so it is Bob's (P17).
- **Other modules:** readers must already handle `cells: null` (they do for the over-guard case: `content/index.mjs:1277`, `findin.mjs:350`), but the Document and find-in screens would need to state "no cells above N" in words.

### Recommendation: A, owned by extraction, now; B and C stay with G40's memory question
**A**, for these reasons.
1. **It fixes the actual defect (storing) without choosing what a member can do.** Nothing in A removes a cell; B and C either rebuild the readers' shape or take cells away. K4571 (read whole, never a silent partial read) is kept by the option that drops nothing.
2. **It is one module's change plus one reader's move to the provided read.** Extraction owns `readings`; `retrieval-browse` stops reading another module's table directly, which is the K4164 direction (a small change in one place; no reader of `readingOf` rebuilt). B touches five modules at three layers.
3. **It is general.** Any key that outgrows the row, `cells` today, `provenance` for a 15,000-page file and whatever the unknowns of 1.2 turn out to be, is handled by one rule keyed on the constant R94 already owns, not by a per-format guard that the next format forgets.
4. **It reuses a measured pattern** already in the tree: spill to a chunked side table (`calculations` `TEXT_CHUNK`, `case-import` `BLOB_CHUNK`) and the 1 MB spill rule of `record-core` (`schema.mjs:33-35`).

A does not help memory, so the G40 question (compact grid or a stated size above which a CSV carries no cells) stays exactly as `diagnosis-R6-g40.md` section 3.4 put it, and **is Bob's**: it is the one place the choice changes what a member can do (C), or rebuilds the readers (B). With A in place the stored size is no longer a reason to choose either, which removes the pressure to choose C for storage reasons. I did not decide between B and C for memory.

**Rows 3 and 4 (estimated):** `calculations` (layer 5) stores `written_json`/`not_written_json` as rows of their own or bounds the lists: an ingest keeps its first N entries in the row and the rest as counted gaps, or one row per picked row in a child table (calculations R14); `following` (layer 10) stores `portal_snapshots.rows` in chunks as `calc_table_bytes` does or refuses a snapshot above a stated size in words (following R10). Both are their owners' details and neither changes what a member can do if chunked; a "stated size" version would be Bob's. Both are estimates; the shim (section 3 (2)) will name them if a test in their suites writes a large value.

**Owners and ids.** extraction: R19, R21, R23, R30, R94, new (G41 id) for `reading_parts`; retrieval-browse: R8 (and its read path); calculations: R14; following: R10; test-support: the preload (no requirement; its own tests). Not touched: csv-reader R8/R9, reading-pipeline R28, office-readers R30/R31, odf-reader R46, content R52/R46 (they read through `readingOf`).

## 3. G41, the four fields (plan style; for `fix-round-6-T51.md` after G40)

### G41 · The reading of a sheet is stored as one value the object's SQLite refuses (found by the in-workerd run of `diagnosis-R6-g40.md` section 2; the shim run of this report)

- **G41 · A document's whole reading is one SQL value; above about 2.1 MB it cannot be stored.** Owner **extraction (S)**; **retrieval-browse** (reads `readings.reading` directly); *prov* test-support (the platform's limit in the suite); **calculations** and **following** for rows 3 and 4 of `diagnosis-R6-g41.md` section 1.1 (estimates; each job measures its own first).
(1) **Cause, certain** (measured in Miniflare's real DO SQLite, `diagnosis-R6-g40.md` section 2): `writeReading` (`extraction/index.mjs:1006`) binds `ser.json`, the reading's whole JSON (`#serialOf` :674-681), into `readings.reading` at :1030 (`reading TEXT NOT NULL`, `extraction/schema.mjs:32`) and `#keepReading` (:1126) binds the same text into `reading_history.reading` at :1151 (and the prior row's text at :1140; `schema.mjs:334`). DO SQLite refuses a value over about 2.1 MB (`record-core/schema.mjs:33-35`: 2,098,176 B passed, 2,252,800 B failed). A reading's size is dominated by `reading.cells`, the typed cells of a sheet (`reading-pipeline/index.mjs:1716-1723`, R28): 147 B a cell for a CSV, 161 B for an xlsx (measured), so any CSV above about 190 KB (188,847 B ok, 209,811 B fails) and any workbook above about 13,000 cells (about 90 KB zipped, estimated from two measured points) throws `string or blob too big: SQLITE_TOOBIG` inside the write's transaction, the read does not finish and nothing is indexed (the CSV's text never reaches `capture_text`). Nothing bounds the stored row: R94's `READING_KEY_BYTES` (:52) bounds only the answer. The PDF case does not reach it: BUDGET-2024-APP's reading without its text units is 189,015 B (measured) because the text is in `capture_text` rows (:1206), each capped at 128 Ki characters. **Fix (extraction):** Option A of section 2: a top-level key over `READING_KEY_BYTES` is written as chunked, content-addressed rows of `reading_parts` (at most 256 Ki characters a row) and the stored key is a stub; the digests stay over the whole text; `readingOf` reassembles; `readingFor` names the key as it does; purge deletes the parts. **New reads only** (R-OLD): rows stored before are unchanged; a stored reading over the limit cannot exist. **Fix (retrieval-browse):** `findin.mjs:343` reads the reading through extraction's `readingOf`.
(2) **Missed** because no fixture emulates the value limit: node:sqlite has none, and `extraction/fixture.mjs:36-67` (a `sql.exec` that emulates only workerd's LIKE/GLOB pattern limit, `checkPatterns`) and `plane/fixture.mjs:33-39` (savepoints) never refuse a bound value. Seventy-four module fixtures each build their own `new DatabaseSync` (`bio-plane/test/m/*/fixture.mjs`; 122 files in `test/` call it), so a per-fixture shim would miss modules. **Gap fixed once:** a preload `bio-plane/test/m/test-support/platform-sqlite.mjs` that wraps `StatementSync.prototype.run/all/get/iterate` to throw `string or blob too big: SQLITE_TOOBIG` for any bound string or blob over 2,098,176 B, run by `npm test` as `node --import ./test/m/test-support/platform-sqlite.mjs --test ...` (node:test passes `--import` to each file's process) and added to the E3 harness child's `args` (`plane/shape/harness.mjs`, `shapeRun`).
