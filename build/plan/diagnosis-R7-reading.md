## What `last_ms` measures (R-CLOCK answered)
`pending.mjs:89` `ended()` = `now() - row.started_at`; `started_at` is set by `stamp(row, at)` (:133-137) where `at` is **the alarm's `now`, read once at the start of `onAlarm`** (`scheduler/index.mjs:573,589`, the same `at` for every consumer). So `last_ms` = (the clock when this row ended) minus (the instant the whole alarm began). It therefore (a) includes every consumer that ticked earlier in the same alarm and, in `pending.mjs:299-305`, up to 3 light rows (`subresources`, `unpack`) run before the one heavy row, all sharing one `at`; (b) includes awaited I/O: R2 `get` of the whole file, the OCR member's `fetch`, browser render (a `subresources` row ended 40,706 ms the same session); (c) includes synchronous compute only up to the last awaited call, because workerd freezes `Date.now()` between I/O (R-CLOCK); compute after the last await is not in it. It is NOT a CPU measure and not the row's own time. Whether the bar (10 s) is met per tick in CPU terms is **unknown from the ledger**; the harness (`g26.probe.mjs`, node wall in a heap-capped child) is the only CPU-shaped proof, and it drives `onAlarm(at)` itself (`g13.probe.mjs:283`), never the real alarm.
