# Design: the assistant in a Claude Code cloud session, started by a routine fire (BOB #192, read 2026-10-16)

Nothing in the product was changed. No routine was created, no fire sent, no credential used. Marks: **[doc]** documented (URL, read 2026-10-16), **[code]** read in the code on `origin/tranche/T49` @ 18e426aa56, **[inf]** inferred, **[reg]** register entry in `build/terms/anthropic.md`. API-key routes are not considered (K3347). Holding a member's token is ruled (K3061) and is not discussed. This builds on `study-remote-sessions.md` (the "remote study") and `study-assistant-link.md` (the "link study"); it corrects one thing in the remote study: the study called routine fire "start only, cannot return an answer". That is true of the fire call, and the design below gets the answer back a different way (section 2): the session writes to our own endpoint.

## 0. Answer in short

**The design holds up on paper, with one change to the brief: the table must stay on our side.** Do not let the session run the harness; let it be the *judge* inside a harness that our Worker still runs. The session asks our endpoint "what is the next row?", gives its judgement, and the Worker applies it (`applyJudgement`), does the plane calls, ticks, and returns the next row. The control table stays pure and server-side; the model cannot skip a row, because the only calls the session can make are the ones the Worker serves in order (section 2).

What it gives: one Opus context across the whole run (no re-rendered transcript per conversation, no closing turn per conversation), the four level sub-sessions as subagents (independent contexts, can run in parallel), no Cloudflare container for this path.

What it costs, in order of weight (section 3, 6):
1. Per member, a hand-built routine, environment and token, with no API for any of it; and a second setup (the group's host in the environment's allowlist). [doc]
2. A cloud session is a full Claude Code with a shell, on the member's account, with the member's records in a transcript Anthropic keeps, visible in the member's session list. Today's runner has `tools: []` and a temp dir that is removed. [doc, code]
3. Experimental API ("Routines are in research preview"; fire is under an experimental header). [doc]
4. No usage figure comes back; no idempotency; unknown start time (about 20 s plus setup observed by BOB, no published figure). [doc, observed]
5. The run's speed is not better by itself: model time dominates. The gain is context and parallelism, and parallelism could also be had locally on a bigger instance.

Five things can only be settled by a test, and the test in section 5 settles them: provisioning time, whether the VM can reach the group's `workers.dev` host and a repo-declared MCP server, whether an idle wait pauses the VM, whether the session's own transcript shows token use, and the session-list default visibility.

## 2. How the session gets the table's decisions, and how the plane learns of progress (Q2)

### What exists today [code]
- `agent-harness/src/harness.mjs` is pure: `CONTROL_FLOW` rows, `nextStep`, `advance`, `applyJudgement`, `stopBecause`. No I/O. The loop is in `agent-worker/src/index.mjs` (about lines 520-800): for each row, if it is judged it makes a model turn (`converse`, finalTool `judge_<step>`), applies the judgement (`applyJudgement` refuses overreach: `JUDGEABLE`, `NOT_JUDGEABLE`), then `performStep` does the plane calls, then `airuntick` logs, spends budget and renews the lease. The `collect` row's judgements are the four sub-sessions' reports (`subsession.mjs`, `spawnContracts`, `SUBSESSION_OPS = ["meaningrows"]`).
- The plane already mints a run-scoped credential for a dispatch (`#aiRunDispatch` carries `minted.token`; lease `AI_RUN_LEASE_MS = 3600000`, `ai-runs/index.mjs:363`; the remote study quotes 600000, which is the older figure); a segment that dies "lets the lease lapse to the reaper" and a resumed run reads its published state (harness `resumeFrom`, `resumeTargets`).

### Option A (recommended): the Worker serves the next row; the session is the judge
The session has three tools and nothing else:
- `claim(run, code)`: first call. The plane marks the run claimed by this session id (compare-and-set). A second session for the same run (a retried fire) gets "already claimed, stop".
- `next()` returns the row: `{step, prompt, facts, tools allowed, final_tool}`. The facts are record text, exactly what `openRow`/`rowFacts` give the model today (R61: facts reach the model only as a tool result). For the `collect` row it returns the four spawn contracts.
- `answer(judgement)` for a judged row. The Worker applies it with `applyJudgement`, performs the row (plane calls under the run credential, never from the session), ticks, and returns the next row in the same reply (so one call per row, not two).
- `read(op, args)`: only `meaningrows` for a level subagent (`SUBSESSION_OPS`), served by the Worker with the run credential, so the session never holds a plane credential.
- `report(level, report)`: a level subagent posts its own report (validated against `REPORT_KEYS`); the parent never carries it, so the parent cannot change a sub-session's finding.

How the session reaches these tools:
1. **Repo-declared MCP server** in a small public stub repo (`.mcp.json` pointing at the group's agent-worker). The session's tool surface is then these four tools; `.claude/settings.json` in the stub denies Bash, WebFetch and writes. This matches today's relay (`tools: []` plus in-process MCP) closely. Needs the test to show the VM can reach it (section 5, M3). [inf]
2. **Fallback: `curl` from Bash** to the same four endpoints. Works if the host is allowed, but the session then has a shell with the run credential in its context. Worse for record-text injection (section 3, item 7). Use only if (1) fails.

The run credential and the claim code go in the fire `text` (never a URL, K1874): `{"run":"...", "code":"...", "host":"..."}`, short-lived (the run's lease), scoped to these four endpoints. The routine's saved prompt is the pointer: "Do the check run named in the routine-fire-payload block, using only the tools of the civicos MCP server; follow CLAUDE.md in this repository." The text lands in the transcript, so the credential must be one-run and ends with the run (section 3, item 3).

How the plane learns progress: **it does not poll and the session pushes nothing separate.** Each `answer` is already the tick (Worker calls `airuntick` for the row, which renews the lease). A call that does not come for the lease lapses to the existing reaper. Nothing new needs a timer except one dead-man check (below).

### Option B (not recommended): the session runs the harness code
Possible only if the harness source is on the VM (the stub repo would hold a copy of `agent-harness/src`, with the drift that brings), and the session would call the plane's ops itself. Rejected: the session has a shell and could ignore or edit the table, which breaks "the model never decides when the loop stops" (harness header, TREC 2011 case); the plane credential would sit in the VM; the copy would age.

### Sub-sessions
At `collect` the parent starts four subagents (`.claude/agents/level-judge.md`, `model: sonnet`, `effort: low`), one per level, in one message so they run in parallel (cap 20). Each reads via `read`, reasons in its own context (independence kept, which the remote study's catch 2 asked for), and posts via `report`. The parent keeps context across the *parent* rows (the context Bob asked for), not across the levels. Subagents die with the VM if it is reclaimed (documented), so a reclaim during `collect` means the Worker re-serves `collect` to the new session.

## 3. What breaks or changes (Q3)

1. **Segments and leases (`ai-runs`, `agent-worker`).** The segment (a Durable Object alarm, 10 min wall bound, `tickAndContinue`) exists to stay under the alarm's 15-minute cap. In this path there is no alarm-held loop: each row is one HTTP request, so no segment break and no `DEFAULT_SEGMENT_WALL_MS`. The lease stays the failure detector. `ai-runs` gains a dispatch kind `routine` (fire instead of `AGENT_WORKER.fetch`), a claim (compare-and-set on the run) and a dead-man: no `claim` within a set time after the fire (suggest 3 minutes, from the test's measured fire-to-claim) means refire, counted against 30 an hour. [inf for the figure]
2. **Failure and retry.** (a) Fire `429`: wait `Retry-After`, no new run lost. (b) Fire `500/503`: retry with backoff, **but the call is not idempotent**, so the retry may create a second session; the claim makes the second one stop at once (it spends one empty session start of the member's usage). (c) Session dies mid-run (VM reclaim, usage limit, crash): lease lapses, reaper takes it, the run resumes from the last published state (existing R11 behaviour) by a **new fire = new session = parent context lost** (the same state, a fresh context, like today's segment resume). (d) The member's routine is paused, deleted, token regenerated (`400`, `404`, `401`) or the plan lost: the run ends with a plain reason ("your routine can't be started: <reason>") and the member must fix it by hand. (e) Subscription usage limit reached: the docs say additional runs are "rejected" without usage credits; how that shows to the fire caller is not documented (the fire returns once the session is created). The dead-man covers it. (f) "A green status ... does not mean the task ... succeeded": the plane's own run record, not Anthropic's status, is the truth. [doc, inf]
3. **Credential in the transcript.** The fire text, hence the run credential, is stored in the session. So the credential must be single-run and revoked at close or lease end; the plane already mints per-run tokens [code]. Alternative: an environment **network secret** for the Worker's host (the agent proxy attaches the bearer after the request leaves the VM, so the session never sees it) but it is long-lived and per environment, set by hand; keep as a hardening option only. [doc]
4. **Cost accounting (ai-runs R48 `usage`, per member).** Today each conversation reports `{mode, model, usage, calls}` from the SDK's `num_turns`. A cloud session reports nothing to us: fire returns no usage and the token has "no read access". Options: (i) `calls` = rows and subagent reports we served, `usage: null`, marked `source: "remote"`; approximate and honest; (ii) read the session's own transcript on the VM and send the sums (needs Bash/Read, so conflicts with the locked tool surface; whether the transcript file holds per-message usage is a test item M5); (iii) have the model report its own tokens: **not acceptable**, a model cannot see them. Recommend (i) now, (ii) only if the test shows the figures. The member's real consumption is at claude.ai/settings/usage (the routine "draws down subscription usage the same way interactive sessions do"). Note the budget bound `fetches/subsessions/wallclock` (BUDGET_BOUNDS) still works, since the Worker counts rows and sub-sessions itself; only a token budget is lost. [doc, code]
5. **Where the member's records go.** Today: record text goes to the Anthropic API from the container; `persistSession:false`; temp dir removed [link study]. Cloud: "Anthropic stores the session transcript so you can return to the session later"; retention by account type: Pro/Max 5 years if "allow data use for model improvement" is on and 30 days if off; Team/Enterprise 30 days; "We will train new models using data from Free, Pro, and Max accounts when this setting is on (including when you use Claude Code from these accounts)"; the member can delete a session, which "permanently removes the session's event data". The model path (API) is subject to the same retention locally [remote study section 3], so the new facts for Bob are: a **durable, viewable, shareable copy** of the records and of the model's findings sits in the member's claude.ai account, not in the group's copy; the group cannot delete it (no API); the member can read, share or keep it; the Pro/Max training toggle then governs it (their own setting). It is a policy and UX point for Bob, and it also means the group's record-text rules (what may leave the copy) now include "what the member's account holds". Mitigation we control: serve record text only through `next()` facts (as `read_facts` does today), never put it in the fire text, and put the "delete this session when finished" step in the member's setup guide. [doc, inf]
6. **The routine in the member's session list.** Every run is a session "alongside your other sessions". One run, one session (plus subagent transcripts inside it), not ten, so the list noise is lower than the remote study's per-conversation sessions. The member should name the routine so it is recognisable ("Civicsmith checks"), and may archive finished runs. Default sharing visibility is not stated (test M6). [doc]
7. **A larger attack surface than today's runner.** The session is a full Claude Code that "runs shell commands ... without stopping for approval" with "no permission-mode picker", and all the member's connectors are included by default. Record text is untrusted. Today `tools: []`, in-process relay only, no network but the model. Needed: a routine with **no connectors**, an environment with **Custom** network listing only the group's host and not the default list, a stub repo with `.claude/settings.json` denying every tool but the four MCP tools, no environment variables, no secrets. Even so, a prompt-injected session could call `answer` with a wrong judgement; the Worker's `applyJudgement` limits that to what a judgement may carry today (`JUDGEABLE`), the same as now. This is the one real security regression and must be tested (M4, M7). [doc, inf]
8. **Member setup, once.** (1) create the routine (name, short prompt, model, the stub repo, no connectors); (2) create an environment with Custom network, the group's agent-worker host; (3) add the API trigger and generate the token; (4) hand URL and token to the Civicsmith. All by hand, none scriptable (no token API; the CLI creates only scheduled routines). A token regenerated or a routine edited later breaks the link until step 4 is redone.
9. **Terms (Q4).** The register has no entry for routines, the fire endpoint, cloud sessions, or a routine token; **the register does not cover them.** Entries that bear on the adjacent facts, quoted from the register: AT-21 "OAuth authentication ... is designed to support ordinary use of Claude Code and other native Anthropic applications."; AT-4 Pro and Max limits assume "ordinary, individual usage of Claude Code and the Agent SDK", with unattended runs unresolved in **U-5** ("whether a member's standing question, re-run by the scheduler and calling the model on that member's token without their act each time, is ordinary individual use"); the routines page itself describes unattended use as the feature ("run unattended"), but that page is not in the register. AT-25: such questions go to Anthropic sales. AT-28: monthly API credits on Max and Team "don't cover interactive Claude Code sessions", and routines draw on the plan's limits, not the credits. AT-23/U-6 on the paused Agent SDK billing change do not apply to routines (the routine page says they use subscription usage like interactive sessions) [doc]. If Bob takes this forward, the register should get a new entry for the routines page (AT-n) and, if wanted, a question for Anthropic (U-n); BOB cannot answer it.

## 4. Per-conversation view: what the run looks like

Fire (plane, once) -> session starts (about 20 s plus setup, observed, no published figure) -> `claim` -> repeat: `next` / `answer` for each row (Worker does plane calls, tick) -> at `collect`, four subagents `read` then `report` in parallel -> more rows, passes -> `close` (the table, not the model, decides: `stopBecause`) -> Worker calls `airunclose` -> the session is told "done" and ends. The harness's stop rule, dedup-before-write ordering, F10 adjust rows and budget bounds are untouched because the table is still run by the Worker.

### Work to build (sizes S/M/L; each module is a tranche item for BOB to cut)
1. `ai-runs` (plane): dispatch kind `routine`, claim, dead-man refire, `usage` entry with `source`, a run credential class for the four step endpoints. **M**.
2. `agent-worker`: split the row loop (index.mjs about 520-800) into a steppable function with state held in the run's Durable Object, the `/mcp` endpoint with `claim/next/answer/read/report`, auth by run credential. **L** (the loop is the most tested code; both walks, pure and through `POST /run`, must still hold).
