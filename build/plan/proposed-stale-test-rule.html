The stale-test rule, as it would read

On 2026-10-21 you ruled that BOB fixes stale tests itself, with no job session, and that a red test never holds a deploy unless it shows a member's operation failing (K4297). That ruling governs now. Below is the exact text it would add to the principles and the mechanics. Nothing else in either document changes.

1. Principles, P7 (one paragraph added at its end)

PROCESS-DESIGN.md · after "A mechanical change is one pass"

A stale test is fixed without a job. A test that disagrees with correct code and with its requirement is stale. BOB, or a worker whose change BOB reviews, fixes it in BOB's own session: test files only, never a source file or a requirement line. The module's tests and the tests of every module the change reaches pass, and the checks read clean, before it is committed; one ruling names each module, file and commit. A change to product code stays a job's.

2. Mechanics, a new §6b

PROCESS-MECHANICS.md · after §6a "The cause job"

6b. A stale-test fix (P7).

  1. BOB confirms the test, not the code, is wrong: the code meets its requirement line as written.
  2. BOB, or one worker (haiku, low), edits only the module's tests paths, on the tranche branch.
  3. The module's suite and its impact set pass; ownership (only tests paths touched), coverage and words read clean.
  4. BOB reads the diff, commits, and records one ruling naming each module, file and commit.

3. Mechanics, §11 Release (one sentence added)

PROCESS-MECHANICS.md · end of §11

A deploy to a test copy is not held by a red test unless that test shows a member's operation failing; the suite runs beside the deploy and the walk, never before them as a gate (P1, P11).
