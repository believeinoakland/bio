Bringing the tests up to date

You asked for a way to bring the tests up to date without spending a week on it, and without opening jobs just to fix tests. This is that plan.

Where things stand

  • Many tests check the exact English a screen shows. When the design stream changes a word, those tests fail even though nothing is broken. A quick count finds at least 265 of the 3,069 test files doing this.
  • About 30 known failing tests were set aside until after the alpha. Some are stale tests, some may be real faults. Nobody can tell which yet, partly because a test that runs out of memory used to report nothing at all.
  • You already decided the direction: tests check the word's key, never the English (your words, 26 Oct). What's left to decide is how to get there quickly.

The two ways to do it

Recommended

A · One tooled sweep when T52 opens

  1. Turn on the new test runner first, so a test that crashes says why.
  2. A program finds every test that checks English and switches it to check the word key. This is one pass in my session, before T52's first jobs start.
  3. Where a screen doesn't give a key yet, that module's T52 job adds it alongside its real work. No job is opened only for tests.
  4. The word check is extended to refuse English in new tests, so the problem doesn't return.
  5. Each of the 30 failing tests is run once and sorted. A stale test gets fixed in the sweep. A real fault goes to its module's T52 job.

Cost: about a day before T52's first jobs start. After that, wording changes stop breaking tests, and a failing test means something is actually broken.

Alternative

B · Fix tests only as modules are touched

  1. Nothing is done up front. T52's jobs start right away.
  2. Each job switches its own module's tests to word keys as part of its work.
  3. Modules no job touches keep their English tests.

Cost: no delay at the start. But jobs spend part of their time on test cleanup, real failures stay mixed in with stale ones for weeks, and any wording change from the design stream keeps breaking the modules nobody has touched yet.

What I need from you

Choose A or B. I recommend A: it costs about a day once, it opens no jobs just for tests, and afterwards a red test means something is really broken. If the sweep runs past a day, I'll tell you why.

Not affected by this choice: the alpha's live walk on 0.87.0 is running now. Its findings become T52 work.
