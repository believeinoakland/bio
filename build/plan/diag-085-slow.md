# DIAG-085 slow: why a check run takes about half an hour (`tranche/R085` @ the deployed cut; a read-only worker in BOB #192)

Run observed: `RUN-d0faeebbefd9123a`, a `check` on `biosmoke8` (0.85.0), opened 13:51:45 UTC 2026-10-16. It finished at 14:21:18 (29 min 33 s), 37 ticks, `pass` 3, 12 sub-sessions, 96 plane subrequests, `wallclock` consumed 1,766,762 of the walk's 1,800,000 ms (the walk worker chose that bound). Sources: the walk worker's poll log `scratchpad/r1.log` (timings only), the run's own `airun` and `airunlog` answers it saved when the run ended (`r1-airun.json`, `r1-airunlog.json`; no sign-in was needed, nothing was written to the instance), and the code on `origin/tranche/R085`.

## Answer in one paragraph

The leading hypothesis (a fixed one-tick-a-minute schedule) is **refuted**. A tick is not a clock event: it is the heartbeat the run's own driver sends after each step of its control table. Nothing paces it. The run is slow because the work is a long, strictly serial chain of model conversations, each about one to two minutes, repeated for three passes: per pass one planning conversation, four level sub-sessions one after another, then collect, compose and dedup conversations; three passes of that is about 30 minutes. "Expires 14:01:45" was only the first ten-minute lease, pushed out by every tick; it never was a deadline.

## 1. What a tick is, and what drives the run

- A run is driven by `agent-worker`'s `driveHarness` loop (`agent-worker/src/index.mjs:552`, `while (steps < maxSteps)`): one iteration per row of the control table (`agent-harness/src/harness.mjs:271-358`: gate-mode, resume, plan, fanout, collect, compose, dedup, submit, adjust, next-pass, close). After each step it sends one `op=airuntick` (`index.mjs:679`; comment at `:643` "LOG-ALWAYS, AND IT IS A TICK"). A sub-session's report is also its own tick (`index.mjs:1566`). The plane counts it in `ai_runs.ticks` (`bio-plane/src/ai-runs/index.mjs:1660`).
- The loop runs inside a Durable Object alarm: `SegmentDriver.fetch` calls `setAlarm(Date.now())` once, to start the segment at once (`index.mjs:2052`), and `alarm()` runs the whole segment (`:2056`). There is no recurring alarm, no cron, no browser poll and no queue in the path. The browser only reads. The plane's own timer only reaps lapsed runs (`ai-runs/index.mjs:1838-1850`, `reapWake`).
- Evidence the cadence is not fixed: the poll log's tick counts rise irregularly, 3 ticks by 13:52:18, then none for two minutes (4 at 13:54:25), but 10 to 16 within one 30 s poll at 14:02:54 and 27 to 29 within two polls at 14:13-14:14. The count of ticks per minute depends on how many cheap steps follow each other (the gate, resume, fanout and next-pass steps tick in milliseconds; a model conversation ticks once per 1-2 minutes). The average of 37 ticks over 29.5 min (1.25 a minute) only looks like a schedule.

## 2. Where the time goes inside a tick

What the code does per model conversation (all serial):
- **Path.** `agent-model` `converse` -> `signinConverse` (`agent-model/src/signin.mjs:263-340`): opens a WebSocket to the member's own `agent-runner` container instance (`runner.idFromName(member)`, `:~180`), sends the whole rendered transcript as one prompt, and the container runs **one Claude Code (Agent SDK) `query` per conversation**: a fresh Node subprocess, a fresh temp home and config dir, no session kept (`agent-runner/src/runner.mjs:150-200`, `persistSession: false`, `mkdtemp` and `rm` per conversation). Every tool call is relayed back over the socket to the worker, which does the plane read and answers (`signin.mjs:300-330`).
- **Model and effort** (`agent-model/src/model.mjs:54-72, 208-211`; K3490): the four parent steps (plan, collect, compose, dedup) run `claude-opus-5-5` at effort `medium`; each level sub-session runs `claude-sonnet-5-5` at effort `low`.
- **No retry or backoff in this code.** `agent-model` adds none on the sign-in path. The Agent SDK has its own internal retry (`runner.mjs:192` reads `api_retry` messages); whether any occurred is not recorded in the run (see Unknown).
- **Container cold start.** `sleepAfter = '2m'` (`agent-runner/src/worker.mjs:65`). Inside a run the conversations follow each other well inside two minutes, so the instance stays awake; a cold start is probable only for the first conversation (the first plan step took about 2 min, 13:52:18 to 13:54:25, longer than any later parent step; not proven to be a cold start).
- **Container size.** `agent-runner/wrangler.jsonc:25-31` sets no `instance_type`. Wrangler 4.114.0 (the repository's own copy) applies `instance_type ?? "lite"` (`bio-plane/node_modules/wrangler/wrangler-dist/cli.js:206484`), and Cloudflare's `lite` is 1/16 vCPU and 256 MiB (Cloudflare Containers limits page, read 2026-10-16; the page itself does not say which is the default, wrangler's code does). Claude Code is a Node program that boots on every conversation; a sixteenth of a CPU is the most probable hidden cost per conversation, but it is **not measured**.
- **Measured per conversation** (from the run's own log timestamps, `r1-airunlog.json`): the three level reports of pass 1 arrive 85 s and 79 s apart (13:55:47, 13:57:12, 13:58:31); of pass 2, 80 s and 75 s (14:05:41, 14:07:01, 14:08:16); of pass 3, 86 s and 78 s (14:14:49, 14:16:15, 14:17:34). So a Sonnet-low sub-session is about 80 s, very regular. Parent steps (Opus, medium): collect plus compose plus the internet sub-session took 150 s in pass 3 (14:17:34 to 14:20:04); dedup and close 74 s (to 14:21:18). The model's own share versus container start versus plane reads inside those 80 s is not separable from what the run records.

## 3. Why the run passed `expires`

Expiry is a **lease, not a deadline**. `AI_RUN_LEASE_MS = 600000` (`ai-runs/index.mjs:362-369`); every tick sets `expires = now + lease` (`:1660-1663`); only a run whose ticks stop is reaped (`reap`, `:1850`, bound `lease`). The finished run's `expires` read 14:31:18, exactly its last tick (14:21:18) plus ten minutes. The open answer's `expires 14:01:45` is that first lease, shown to the member as if it were an end time; it is advisory text, true only of a run that stopped heartbeating. The risk it hides: any single step longer than ten minutes without a tick is reaped as dead.

## 4. How many conversations a check needs, and how long it should take

Per pass (`CONTROL_FLOW`, `harness.mjs:271-358`; `LEVELS` = 4 at `:154`; `DEFAULT_MAX_PASSES = 3` at `:556`): plan (Opus), then four sub-sessions in a serial `for` loop (`index.mjs:1508`), collect (Opus), compose (Opus), dedup (Opus), plus submit and adjust per candidate (adjust is judged), then next-pass. That is 8 or more serial model conversations a pass, up to 3 passes: 24 or more. The sub-session counter confirms it (12 consumed). At 75 to 90 s for the sub-sessions and roughly one to two minutes for the parent steps, one pass is about 9.5 to 10 minutes and three passes about 29 minutes; observed 29.5. **At the current design and container the run should take about 30 minutes; the observation is the design working as built.** A one-pass run would be about 10 minutes, which is the one thing "expires +10 minutes" happens to resemble.

Two further facts from the same log:
- **Passes 2 and 3 repeat pass 1.** Level reports 5-7 and 9-11 find the same single leg and the same two Marlowe passages as reports 1-3, and pass 3's targets again ask for "the full text of INFO-2026-0006 ¶2", the thing pass 1 and 2 left partial. About two thirds of the time bought no new finding. The harness stops only on the pass count (`harness.mjs:547-550`), never on "this pass added nothing".
- **Two forced segment breaks.** The segment wall bound is ten minutes (`DEFAULT_SEGMENT_WALL_MS`, `index.mjs:2037`). The log shows "the segment ended (by: its own segment bound)" at 14:02:27 and 14:13:29, each mid-work, and the plane re-dispatched (`tickAndContinue`, `ai-runs/index.mjs:1712`). Each re-dispatch re-reads the pack, the run, its whole log and resumes. Cost per break is not recorded; from the gaps between the segment end and the next level report (194 s and 80 s after the break, the latter including a sub-session) it is small, between seconds and about a minute and a half.

## 6. The priority question

- The record does not cover any way to get higher priority or faster service for Claude Code or the Agent SDK on a subscription sign-in: **the terms register (`build/terms/anthropic.md`) has no entry on subscription priority, speed or concurrency**, so nothing here claims one exists or does not.
- What the register does say bears only on the cost side of the options above: a sign-in's use draws on the plan's usage limits (AT-23); a Pro or Max plan's advertised limits assume ordinary individual usage (AT-4); whether a member's unattended or repeated runs count as that is unresolved (U-5). That is why option 3 (four conversations at once) is flagged, not rejected.
- So the speed we can get is ours to take: fewer conversations (2, 4), a faster container (1), overlap (3).

## 7. What stays unknown

- The split of each ~80 s sub-session between Claude Code process start on a 1/16 vCPU container, the model's own time, the SDK's internal retries and rate-limit waits, and the plane reads it relays. The plane records no per-conversation milliseconds. The runner logs `ms`, `cold` and `num_turns` per conversation (`runner.mjs:100-105`, `entry.mjs:84-88`) in Cloudflare observability, which this worker could not reach. One read of those lines would settle it.
- Whether the deployed `agent-runner` really has the `lite` size (Cloudflare's dashboard shows the app's instance type); wrangler's default is read from its code, not from the live account.
- Whether the first plan step's 2 minutes was a cold start.
- The cost of each segment re-dispatch.
- Whether the internet-level sub-session runs a full model conversation each pass (12 sub-sessions were counted, only 9 level reports were logged).
- What bounds the product's own screen opens a check with (the walk worker chose `wallclock` 1,800,000 ms and used 98% of it; a smaller default would end a three-pass run as `wallclock`).
