## 2. Root cause: the scheduler never re-sets a spent alarm (`bio-plane/src/scheduler/index.mjs:586-588`, `#reconcile`, non-exact)
```
const at = await this.#storage.getAlarm();
if (at === null || at === undefined || at > want) { await this.#storage.setAlarm(want); return want; }
return at;                                   // :588
```
`arm()` (:596, called by every `owe`, `pending.mjs:71,232`) and `start()` (:610, run in the constructor, `store.mjs:490`, so on every deploy and restart) only ever PULL the alarm EARLIER. The old wedge: the alarm was armed for the oldest row's due instant (0111, due_at 05:57:10.474, never rewritten because each run was killed before it wrote: `pending.mjs` before PLANE #50 wrote attempts only on return); the platform ran it, killed it 8 times and stopped. The platform still reports that spent alarm: its time `at` equals the oldest live row's `due_at`, which is the minimum wake. Every reconcile since computes `want` = that same `due_at` (new rows are due later, backoffs later), so `at > want` is false, nothing is set, and the platform runs no alarm that is not set afresh. The deploy's `start()` and the walker's registrations (06:21 on, 13:0x) all hit this line. The migration (`pending.mjs:204-218`) does not touch `due_at` (round-4 ledger already had `detail`), so the old row keeps the minimum. PLANE #50's wake choice (`pending.mjs:263-264`, wake = own due instant) is not the cause; R27's hold (:468-492) is not involved (a new instance, `#held` empty).
Evidence: (i) analytics above; (ii) offline, deployed code (suite-wt = 5ff8b5e01b for these files), live-shaped ledger (round-4 table, 0111 row attempts 0, last_try set, `NO_HOME`, due_at 7 h ago; five more rows due later; daily passes already done as on the live copy), storage whose `getAlarm` reports the spent alarm T = 0111's due_at: after construction, a fresh `pendingadd` and an `arm()`, **`setAlarm` is called 0 times, nothing runs: RED**. With the same storage and an empty alarm the real `onAlarm` path runs every row (control, my live-shape.test.mjs: rows run one heavy per tick). (iii) Live read: `op=owedwork` as administrator, 13:45: still 19/3/5, final 0.

## 3. Why PLANE #50's tests missed it
fix5-r77/fix4-r75 call `x.s.onAlarm(at)` themselves and the fixture's alarm is a plain variable that starts null, so they never start from a spent alarm; they never exhaust the platform's retries (one kill, then a clean restart). l77.test.mjs (Miniflare) kills the runtime once with `dispose()` and boots a second over the same storage, with a fresh ledger; Miniflare enforces no 128 MB limit and no retry cap. The rows' own accounting was tested; the arming under it was not.

## 4. Smallest fix and failing-first test
Fix: in `start()` only (every deploy and every restart of the object after a kill), when `getAlarm()` is older than a minute (`at < now - 60_000`) set `Math.max(want, now)` afresh (my 3-line change: a `fresh` flag on `#reconcile`, passed by `start()`). A spent alarm is not a pending one. Optionally the same in `arm()` outside a firing (heals a wedge without a restart), but that variant fails 2 further producer tests that seed fake past alarms; the start-only variant fails 3 scheduler tests (copies, files, plane R11-style "start keeps the alarm") that encode "only pulled earlier" with a past fake alarm: those tests need amending to seed the alarm near `now`, and scheduler R4/R11 need a line.
Test: `.../ledger/stale-alarm.test.mjs` (ROOT=<bio-plane dir>): fixture storage with a shared kv for the daily record, round-4 `keeps_pending` rows (0111 plus five later), `getAlarm` = 0111's due_at, `setAlarm` logged; construct, `pendingadd` a fresh digest, `schedulerOf().arm()`, assert `setAlarm` was called and, when the platform "fires" it (`onAlarm`), the fresh row's reading was asked. RED on 5ff8b5e01b (`setAlarm` 0 calls); GREEN with the fix (3 calls, the first at now; fresh row read). Also add a platform-check L: kill the alarm run more than 7 times (not once) and assert the object's next construction arms.
