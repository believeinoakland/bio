## Settled

**1. An interface to create, prompt and read a cloud session from Civicsmith's own code: none is documented.**
- Documented and callable from a Worker: only routine fire, `POST /v1/claude_code/routines/{trig_}/fire` (SRS §1a R2-R5; DRR §1 rows 3-7). It creates a session and returns id and url; it "does not stream session output or wait"; text at most 65,536 characters; a per-routine bearer token the member makes by hand on the web (no token API); 30 fires an hour per routine; experimental. It is a routine token, not the held sign-in, and has no read-back.
- Documented CLI: `claude --cloud` creates interactively only; `claude -p --cloud <id>` queues a message and exits (SRS R7). Both need a claude.ai login with scope `user:sessions:claude_code`, capped at 30 days; the held 1-year `setup-token` "doesn't cover it" and "can only make model requests" (SRS R8, R10). So the token agent-runner R27 mints cannot create or drive a session, and a CLI needs a process, i.e. the container N1197 disables. Read-back is documented only as a Stop hook on a Team/Enterprise self-hosted runner (SRS R9). No sessions REST API, SDK or third-party scope is documented (SRS §0 item 3; absence inferred from the docs index).
- What was done: every remote cell was created by the study lane's own session tools through claude.ai's sessions service (`/v1/code/sessions`, K3537; HAND S11-S17). It measured the platform (start 4.6-18 s, 3.0-3.2 s a tool call over 40, 6-7 sessions at once, 212 KB in and 62 KB out via git, a credentialed op call 0.7-2.6 s; TESTS parts 1-4). Civicsmith's own code never created or drove one (K3608).
- Unknown: whether a Worker or Durable Object may call the sessions service with that login; its request and event shapes; its prompt limit (HAND S17: unmeasured); model and effort per session; usage reporting; how a copy obtains and renews the login (Unknown 3). So agent-runner R38 makes the bottom-up proof the job's first step, each step logged by the copy (K3608), and the lines marked CONDITIONAL wait on it.

**2. Tool calls and logging.** A cloud session reaches the copy over HTTPS: `op=bootstrap` public, credentialed ops with `Authorization: Bearer` (TESTS "A cloud session that holds a credential"; HAND S15). The plane's log has no response sizes and missed 6 of 60 calls (HAND S9, S11), so the copy logs every request itself (R39). The answer comes back as the session's `finalTool` call at the door (write-back), not by reading its transcript; that leaves `agent-model` R6, R18 (`checkFinal`, N1188) and the table unchanged. The credential is only ever in the `Authorization` header (K1874).

Parts outside the six: Unknown 2.

**4. N1197.** agent-runner R35.

## Unknown / blockers

1. **The first step may block.** R38 is the only way to learn whether Civicsmith's code can call the sessions service. If it cannot (undocumented for third parties, the login not obtainable from a Worker), the documented fallback is routine fire: start only, a hand-built routine and token per member, the answer by write-back at the door (DRR §2; text 65,536 characters, the pack read at the door as facts). It needs a different held secret and Bob's decision on hand setup (DRR §7). Bob is told what blocked, with options (K3607).
2. **Parts outside the six.** `signin-door` (the `check` step, attaching the account), `op-declarations` (the step list), `bundler` (a second class, the door address), `instance-setup` (`part_signin`'s meaning). BOB adds them to N1196 or rules otherwise. Settings and installer lines above assume the door and class sit in the agent-runner Worker.
3. **How a member gets a remote-capable credential.** N1197 stops `/signin` (it needs the CLI in the container) and the held `setup-token` does not cover sessions. Nothing here settles the flow or who may perform it; a 30-day renewal returns up to the caller and no field for it exists yet.
4. **Home of the class and door.** Recommended: its own Worker with no container (no Containers scope, image or digest in the installer's R38 path), which needs a module cut by BOB; this draft keeps it in agent-runner per N1196. Alternative door: a plane op (control-plane, admission, credentials): no new public address, more owners.
5. **For Bob (P17).** Records now sit in a session list at Anthropic in the member's account, viewable and shareable, which the group cannot delete (DRR §3.5; SRS §3); the disclosure (`instance-setup` R54) changes and he decides it.
6. A cloud session is a full Claude Code with a shell; the brief and the credential's scope limit it, not the platform (DRR §3.7). A spend limit once cut every session (HAND S12). Unmeasured: model and effort per session, usage figures, ten at once, runs over ten minutes.
