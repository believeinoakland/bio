## P1 · C15 · the interface words are asked for without the release version, so the year-long cache never applies — fix is one line of ordering
- **Measured.** Home (`/app`) on a signed-in load: `op=interfacewords` is requested as `?op=interfacewords` (no `v`), answers 200, 1,016,962 bytes on the wire (zstd; about 6.2 MB decoded), `cache-control` absent, and the request waits 2.3 s, the last request of the page to finish. Two loads, two downloads.
- **Root cause.** R116 is in the source and is correct (`control-plane/words-cache.mjs:25`: caches only when the request names `v` equal to `env.VERSION`). The shell never names it: `interface-shell/browser.mjs:2450-2452` (`loadWords`) takes `v` from `BOOT.version`, but `BOOT` is set by `bootstrap`, which `start()` fires without waiting (`browser.mjs:2542-2547`) while `loadWords` is called from `whoami()` (`browser.mjs:1495`) about 1.5 s earlier than `bootstrap` answers (live: whoami at 0.18 s, bootstrap at 1.8-3.0 s). So `v` is always null on the first load. The sign-in page's copy of the op does carry the cache header because that page has the version in hand.
- **Owner.** `interface-shell` (the ordering); `control-plane` is correct as it stands.
- **Fix.** The page already knows its release when it is served (`appAsset(..., { version: env.VERSION })`, `control-plane/index.mjs:738`; the page is built in `interface-shell/index.mjs:449`): put the version in the page the shell is served in, and read it from there for `loadWords`, instead of from the `bootstrap` answer. (Alternative: `loadWords` awaits the `bootstrap` promise; it costs a round trip on every first load, so the first option is better.) Changes no requirement; R5 and R116 already state the intent.
- **Expected gain.** Second and every later load in the same browser: 1 MB and one 2.3 s request gone, and the words no longer wait on the plane (the first draw never waited for them, R5, but the redraw does). First load unchanged.
- **Risk.** None to a member; a test that pins the request without `v` (search `fixround2.test.mjs`) will need the new expectation.

## P4 · C12 · every capture waits 3.0 s for nothing, and a visitor-view capture also waits out the host governor (4-8 s)
- **Measured.** `acquire` of one public page, `timings` from the answer (the plane's own stage clock), 6 runs: plain: 4.0-4.7 s total = fetch 0.57-0.69 s, read 0.2, profile 0.23-0.28, **attest 3.000 s exactly** every time. With `render: true`: 13.9-16.9 s = **fetch 4.3 / 5.2 / 7.8 s**, read 0.13-0.18, render 5.5-6.3 s (the browser itself reports 4.0 s of it), profile 0.24-0.39, attest 3.000 s.
- **Root cause a (the 3.0 s).** `acquisition/index.mjs:364,1379`: `ATTEST_WAIT_MS = 3000`; the answer waits that long for the timestamp and co-archive, which on the copy never answer in time (the "had not answered when this capture was answered" sentence is drawn on every capture, A.md/B.md), so the wait is always spent in full and always ends pending. A fixed wait that always runs out is the cost of the request, not a bound on it.
- **Root cause b (the render's extra fetch time).** The render path asks the host governor to admit the host before the fetch (`acquisition/index.mjs:910-912`, `governorAdmit({ host })`, result discarded except for a refusal). The governor books every admit: it spends a token and records `last_grant_at = now + wait` (`host-governor/index.mjs:136-146`), the "human-shaped gap" of 60 s / 12 per minute × 0.6-1.5 = 3.0-7.5 s. The fetch that follows a few milliseconds later asks again (`governedFetch` → `admit`, `host-governor/index.mjs:304-313`) and sleeps out the remaining gap. 4.3-7.8 s fetch stage against 0.6 s plain fits that range exactly. The same happens in the capture screen's two calls (`heldat` with `check`, then `acquire`; screens-intake `capture.mjs:388-392`) for an address not yet held: the second fetch waits out a gap the first booked.
- **Root cause c (the render, 5.5-6.3 s against the browser's 4.0 s).** About 2 s outside the browser's own clock: session open (`Browser Rendering` acquire) and close. The renderer then collects every sub-resource's body one at a time after the page is taken (`browserrender.mjs:193-227`, `BODY_PHASE_MS` 10 s, awaited in a loop). Not yet measured separately (C13 below).
- **Owner.** `acquisition` (a, b), `host-governor` (offers the "admit without booking" b needs), `capture-sources` (c).
- **Fix.** (a) Do not wait: answer at once with the attempt pending, as the code already does past the wait (the late outcome is recorded by `recordLateAttestations`), or wait at most a few hundred ms; for the capture-request arm that already waits unbounded, no change. (b) The render admit must not spend the grant: either `governorAdmit` gains a peek (admission and refusal without booking), or the render path passes its admission to the fetch so there is one booking per host visit. (c) see P5.
- **Expected gain.** Every capture −3.0 s; a visitor-view capture a further −4 to −7 s. A plain page: 4.0-4.7 s → 1.0-1.7 s (under the bar of 2 s); a visitor-view page 14-17 s → about 7-9 s (the browser's own time remains, P5).
- **Risk.** (a) changes when the member learns the timestamp has landed, not whether; the sentence "asked for and had not answered" becomes the usual state, so the wording and the late-outcome recording (capture R68) are the review points. Whether to wait at all is a member-visible trade (time against seeing the timestamp in the first answer): **Bob's if BOB reads it so; recommendation: do not wait**, show the pending line, fill it when it lands.
