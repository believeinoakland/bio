## 1. For Bob, in plain words

The planning skill is the assistant's "Suggest options" button on a plan page. A member who has joined the project presses it for one plan; the assistant then reads what the group's record already holds about that plan's matters (the plan itself and the options and reasons already on it, the inquiries and published findings, the determinations and the standards' text, the consequences recorded, the project's declared kind of work, the jurisdiction profile's deadlines, venues and legal organisations, and the group's own earlier plans the member can see) and writes a few **proposals**, each with its reasons and the records it drew on. A proposal sits in a separate tray; it is not an option, not a decision, not an action and not a filing. Nothing enters the plan until a member adopts it, and every later step (choosing, scheduling, starting an action, preparing, approving, sending) stays a member's act as today. It may never: start by itself, change or remove anything on the plan, choose or decline an option, rank or score options, name a private person as an addressee, propose lobbying that does not enforce or restore an existing requirement, read the web, or send anything anywhere. Every proposal carries a fixed disclosure: *"Suggested by the assistant (machine work) in run RUN-…, under skill version …. It is not the group's decision; it becomes an option only when a member adopts it."* The adopted option keeps the record of where it came from.

### `agent-worker` (layer 6; last id R49)

- **R50** (`BIO_Action_v0_1.md` §4 rules 1, 3, 8) Mode `plan` walks its own control-flow table, `PLAN_FLOW`, pure and held beside `CONTROL_FLOW`: rows `gate-mode`, `resume`, `read`, `compose`, `dedup`, `submit`, `adjust`, `close`; one pass (R15's pass limit is 1 for this table); `stopBecause` asks `proposals` then `wallclock`. It has no `fanout`: it calls no `airunspawn`, `capturerequest` or `suggest`, and makes no fetch.
- **R51** `read` reads, under the run's credential and nothing else: the run's plan (`op=plan`), the plans of the same project the plane answers to `op=plans` (earlier plans), and, for each subject, the plane's reads of its inquiry's published findings, its determination and standards (`conformance.determinationRead`, `standards.standardRead`), its consequences, `filings.availableActions` and the profile's `deadlines`, venues and `legal_organisations` (`jurisdictions.combine`), each through the op `op-declarations` declares for it. A refused or silent read is carried as UNDETERMINED in the proposal's `why`, never as absence. It reads no person's attributes and no transcript.
- **R52** `compose` (judged) forms candidates with only `optionPropose`'s fields (`action-plans` R9's option fields, `why`, `sources`); a judgement naming any other key is `JUDGEMENT_OVERREACH` (R16). `dedup` drops a candidate whose canonical `{summary, category, subjects}` equals an option or proposal already on the plan, before any write. `submit` sends one candidate at a time through `op=optionpropose` with the run; `adjust` follows R25 unchanged. Candidates are submitted in the order formed; the table assigns no rank, order of merit or score.
- **R53** `PLANE_OPS` (R37) gains exactly `plan`, `plans`, the R51 reads and the write `optionpropose`; a plan-mode run calls no write but `optionpropose`, `airuntick` and `airunclose`. `MODES` gains `plan: {deployed: false}`; R44 reads "only the members Bob has deployed are deployed". Deploying `plan` is an edit to `MODES` under review (R42), made only after R40 and R48 are met.

### `action-plans` (layer 9; last id R29)

- **R30** (fills `ai-runs` R47) For mode `plan`: `NO_SUCH_PLAN` (R22's one answer) for an absent plan or one the actor may not see; `PLAN_NOT_OF_PROJECT` when the plan's project is not the run's context; `PLAN_CLOSED`; `membership.projectAuthority(project, actor, "joined")`'s refusal.
- **R31** (§4 rule 1; K590 D2) `optionPropose` (R11) by a machine credential names `run`: absent, or one `ai-runs.runFor` does not answer, `PROPOSAL_NO_RUN`; not `running`, `PROPOSAL_RUN_NOT_RUNNING`; not mode `plan`, or a run whose `plan` is another plan, `PROPOSAL_RUN_OTHER_PLAN`; the caller not the run's principal (`run-rules` R5), its refusal; the `proposals` bound reached, `PROPOSAL_BOUND_REACHED`. Then R9's field refusals (all but the author's), including `ADDRESSEE_REFUSED` (§4 rule 6), `LOBBYING_NO_REQUIREMENT` (§4 rule 9) and `OPTION_KEY_REFUSED` (§4 rule 8; R26); then `PROPOSAL_NO_SOURCE` for an empty `sources` or a source (a finding, determination, standard, consequence, plan or option id) the run's viewer may not see, answered alike. Otherwise, in one transaction, the proposal is stored as R11 stores it, with the run, the run's skill version and `sources`, and `proposals` is consumed by one (`ai-runs.consumeBound`). A member's proposal needs no run.
- **R32** (§4 rules 1, 3; DEC-24 rule 1) `planRead` answers each machine proposal with its `disclosure`, the fixed sentence of §1 filled with its run and skill version, its `why`, its `sources`, and the project's `work_kinds` as they stood when the run opened (R21); proposals are answered in id order, never ranked. A proposal's `why` is never copied into any member's reason (R4, R9, R13, R20): adopting, declining or closing takes the member's own words. An option adopted from a machine proposal answers `origin: {assistant: true, run, proposal, adopted_by}` for as long as the plan is read.
- **R33** (§4 rules 1, 2) A planning run's proposals never become options, dispositions, scenarios, checkpoint judgements, actions, filings or communications: every act but `optionPropose` refuses a machine credential by its existing code (R1, R9, R11's `optionAdopt`, R13, R14, R16, R18, R20; R24), and nothing here starts an action or prepares a filing from a proposal.

## 3. Bob's choices, each with a recommendation

1. **Who starts it.** Recommended: only a member who has joined the project, one plan at a time, by pressing "Suggest options" (`ai-runs` R46). No standing, scheduled or automatic run, not even when a plan opens or a determination lands (DEC-24 rule 2; the provisional NO on standing runs, AI Roles §7.3).
2. **How many options per run.** Recommended: at most 5 proposals per run, the member able to ask for fewer and to run it again; never ranked or scored (§4 rule 3).
3. **Communications text.** D2 already allows the assistant to draft communications as proposals (`filings` R23). Recommended: not in this run; the planning run proposes options only. Drafting a message for a started action is a separate run mode, drafted when you ask for it.
4. **What it reads.** Recommended: only the instance's own record that the starting member may see, including the group's earlier plans in the same project; not other projects' plans, never the web, never a person's attributes (§4 rules 8, 10). Alternative: earlier plans of every project the member has joined.
5. **When it is switched on.** Recommended: deploying mode `plan` is your act, taken after the fleet member runs model turns (`agent-worker` R40, R48); until then the requirement is built and tested, and every plan-mode run is refused as not deployed.
6. **The disclosure's wording** (§1's sentence). Recommended as written, on the tray and on the adopted option's origin; not repeated on the action or on outward filings, since a member's adoption makes the option the group's.
7. **Suspected matters.** Recommended: it may propose for a plan whose subjects are only suspected (your ruling 10), the plan's existing check (`action-plans` R19) flagging outward options that rest only on hypotheses.
