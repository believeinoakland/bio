## (1) §16 G137a and G136b (safe view pending 240 s)
Reproduced alone: G137a red (448 s), G136b S5 red ("classed": SAFE_VIEW_PENDING); G136b OVER_BOUND green originally.
Root cause (log + code, not a guess): TWO causes, both file-safety.
 A. `renderWake` (file-safety/index.mjs:2159-2175, R39). After any renderBatch has run, `kept.last` is set; a view queued later has `render_wait_at` NULL, so `views.t` is "" (:2171 `MIN(COALESCE(render_wait_at,''))`), `t` is NaN (:2172) and the wake is `poll` = last batch + FILE_SAFETY_POLL_MS (300 s) (:2163, :2173). The first file of the test is rendered by the first alarm (scanner /render at t0); the second file is queued 0.2 s later: alarm runs selection-sweep..pending-work but NO file-render; next_set_for = t0+300000 (log line `next_set_for 1792873573051` = batch 273051 + 300000). Test waits 240 s < 300 s.
 The ask does not arm anything and need not: `#ensureQueued` (:988) only INSERT OR IGNOREs a row the receipt (#onReceipt :259) already inserted and armed. The receipt's `#arm("render", renderWake)` answers last+300 s, which is "no sooner" so nothing wakes sooner. `heal` IS called on every request (plane/store.mjs:758, R102/G93) but only brings the alarm forward when some consumer's wake has already come (scheduler heal :781-788, oldestOverdue); renderWake says last+300 s, which has not come. So heal cannot help; the gap is the wake instant itself.
 Spec: R39 as written says "else the later of now and the last renderBatch plus FILE_SAFETY_POLL_MS (300,000)" and "`now` while the last renderBatch left a view queued (K4900)". So code follows R39's words; the words leave a NEW view (queued after a batch) up to 5 min late. Requirement defect plus code: owner file-safety (R39, R12; R40 for the arming). Not plane (R109 armJobs is for registered rows; render rows are not plane rows).
 Side note, same shape for scan: scanWake `since <= lastRun ? lastRun+POLL` (:2146-2149) with `queued_at` truncated to the second (`second(this.now())`, :251): a file queued in the same second after a scan batch also waits 300 s (second file's /scan not called in the unfixed log; called in the fixed run by luck of the second boundary). Not asserted by the seam; worth a test.
 B. (G136b S5, hidden by A in the original) `#renderCall` (:1108) treats only a rejected fetch / absent binding as `SCANNER_UNREACHABLE`. A service binding whose callee throws answers a 500 with a text body (Miniflare, log `status 500`), no class: falls to code `RENDER_FAILED` -> `#renderFinal` (:1114-1115). R12: "TIME_LIMIT and SCANNER_UNREACHABLE are transient ... retried". An unreachable renderer is not retried when it answers 5xx.
Why owners' tests missed it: wakes.test.mjs:77 and r39-render-wake.test.mjs queue the view BEFORE any renderBatch (kept.last absent => poll = now) or after a batch that left work (`left>0`); none queues a view after a batch that left nothing. r12-render-classes: unreachable is a rejected fetch in the fixture, never a 5xx.
Failing-first tests (written in scratch `d3/bio-plane/test/m/file-safety/r39-render-after-batch.test.mjs`): (i) capture, renderBatch, tick(1000), capture another: `renderWake(now) === now` (red unfixed, green fixed); (ii) renderer answering `{status:500}` no code: row stays `queued` (red/green).
Smallest fix (verified in scratch): index.mjs renderWake add before :2169 `if (views && views.t === "") return this.#answer("render", n);` (a queued view with no back-off is due now; a view in back-off keeps its instant); #renderCall :1108 `|| (r.status >= 500 && !(r.body && r.body.code))` -> retry as SCANNER_UNREACHABLE. Verified: seam G137a green (181 s), G136b both green (OVER_BOUND 187 s, S5 43 s); whole test/m/file-safety 136/136, scheduler/files 15/15. No requirement words change except R39's render clause ("a view queued with no back-off: now").
