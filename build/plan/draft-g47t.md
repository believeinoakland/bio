(3) **The design (BOB's, P17).** *Chosen: a nullable `capture_sha TEXT` on `published_shas`, written only for kind `attestation` and only for a `ref` that occurs on two or more entries of the `materials:` rows of the call (the very rule of G47 (b), counted over the same rows, so a one-capture-per-source document writes no value anywhere and stays byte for byte what it is).* **case-carriage:** `hold` learns the capture it is called for (a closure variable set per material in `holdMaterials`' loop, :253-:297; for an archive's tokens, the member material's sha, since they are shown under that material); its `files` entry gains `capture_sha` **only when kind is `attestation` and the `ref` is repeated** (otherwise the entry has no such key, so today's `files` deep-equal tests of one-capture documents stay unchanged); if a second capture of the same `ref` names the same token (`named`, :237, dedupes by `(sha, ref)`: a token or archive two members share), that entry's `capture_sha` becomes null, which says "shared": it belongs to both. **publication:** `ADDITIVE_COLUMNS` (`schema.mjs`, :539ff) and the `CREATE TABLE` (:96) gain `capture_sha TEXT` (nullable, never back-filled, as `delivered_by`); the INSERT at :1171 passes `f.capture_sha ?? null` in a seventh column; `ON CONFLICT(sha256,bundle_id,path) DO NOTHING` stays: **a stored row is never rewritten** (an old row keeps null); the other five writers are untouched; R40's column list names it (nullable; set only for kind `attestation` of a repeated `ref`; read by `public-read`). The public registry's `shas:` read (`public-read/index.mjs:653`) and every `path=('materials/'||sha256)` read stay as they are. **public-read:** for a row stating `sha`, the lookup adds `AND (capture_sha IS NULL OR capture_sha = ?)` with the row's `sha`; for a row stating none, the query is today's, unchanged. **R-OLD:** a token row with null `capture_sha` (registered before this, or shared) is read as the ref join reads it (shown under every capture of the `ref`), so a document written earlier reads exactly as before; no row is back-filled. *Why not the alternatives.* (a) **The token's own message imprint:** the tokens are RFC 3161 bytes, mostly blob-backed (`#holdTokens` :311-312, held in the evidence store, not in SQL), and public-read reads the projection only (`text(sha)`, inline texts); reading the imprint means ASN.1 parsing of bucket bytes in a read path and a new failure class, and it cannot attribute a co-archive record at all. (b) **A path `materials/<capture>/<token>`:** changes the path every `path=('materials/'||sha256)` read, `publishedbytes` and the manifest depend on, and the PK. (c) **A table of its own in case-carriage** (token, ref, capture): no publication change, but a second registry beside `published_shas` that can disagree with it, a new purge declaration and a new read contract; the column keeps the link in the row it describes. (d) **`DO UPDATE` to fill an old row:** would change stored rows, and a token an earlier case registered for another capture would be pinned wrongly; refused. **Purge/export class:** none new. `published_shas` is declared `purge: exempt`, `export: admin-only`, `expunge: none`, `derive: stored`, `sight: bundle` as a table (`publication/schema.mjs:498-519`, `PUBLICATION_DECLARATIONS`; a column inherits its table's classes) and `capture_sha` is a published digest of a capture the case already names, no member's data; the declaration's entry is asserted unchanged. **Census ops:** none changes its accepted keys or answers (public-read's `casefile` carries the same `held` items); the three jobs confirm and say so (K4208).
