## 3. Conclusion

### A2. CAUSE FOUND (mechanism); the browser's reason for dropping the request is the one thing left on the client side
1. The upload (42.7 s) read the scan inline: `extractread` ran 39.2 s `ok` (24 OCR calls, 18:50:55-18:51:32), leaving `ocr_left {cursor 24, pages 6}` and `tier3_candidate true`. At this point nothing is owed: `readUploaded` registers only `reading_pending`/`more` (R8-reading A(1)(b)).
2. The only hop that then registers the pages is the screen's `promote`: `unreadDocuments` (`control-plane/index.mjs:841-855`) marks the document `ocrOnly`, and `followEntries` (:2678, called at :3869 **after** `await`ing the object's promote answer, in the same request) writes the `ocr` row by `pendSha`. That request was **cancelled by the client 497 ms after it began** (`canceled`, wall 497 ms), and the object's promote, which needed 3.26 s of CPU for the 43 KB reading, was cancelled with it (`canceled`, 3,627 ms). The reading was kept (`kept_at 18:51:35`), so the promote's storing reached disk, but the awaited follow-up (`followEntries` -> `pendSha` -> `pendingadd`) did not run: **no `pendingadd` between 18:50:21 and 18:52:04**, `owedwork&sha=` `owed:[]`, `last:[]`, and no `ocr-worker` call from 18:51:35 to 20:55.
3. So the cause is a design dependency, shown live: the registration of an inline scan's remaining pages lives in a client-held request that the client can drop (a navigation, a closed tab, a headless walker moving on), at the moment of a long (42 s) upload. It was lost; nothing else registers it. R8-reading A(1)(c)'s "Cause unknown" is replaced by this. (Why the browser dropped that fetch 0.5 s in: the walker's page; for a member the same drop happens whenever the page is left within the promote's 0.5-4 s. Not visible server-side. The Add screen itself has no abort in its client (`interface-shell/browser.mjs` has none), so it is the page or the tab, not the shell's code.)
4. The best-reading fix of R8-reading A stands and is confirmed necessary, not just tidy: register at the source (`extraction.read` passes `owe`, or `readUploaded` writes the `ocr` row when `tier3_candidate`/`ocr_left` is in the reading it just made) so the debt is written **before the upload's answer leaves**, and take the OCR calls out of the request. A canceled promote then loses nothing. Old records: the walker's scan is exactly such a record (`tier3_candidate true`, `ocr_left`, no row); the repair of R8-reading A stands.

### B2. CAUSE FOUND for "never read"; "nothing owed" NARROWED (one line of logging left)
1. **Never read: the reading ran inline and killed the object's isolate.** The held ODS is only **1,031,890 bytes** (a heavily compressed zip with a 20.4 MB `content.xml`). The door gates inline-or-ledger by the stored bytes alone (`tooBigToReadInline`: a non-PDF defers only above `READING_DEFER_TEXT_BYTES` = 3 MiB, `control-plane/index.mjs:217, :733-747`), so it read it inline. `extractread` ran 37,973 ms with **7,462 ms of CPU** and ended **`exceededMemory`** at 19:52:53.530 ("Durable Object's isolate exceeded its memory limit and was reset"); the alarm run that shared the isolate (started 19:52:13) died with it. This is the R8-reading B(1)(a) mechanism (an ODS lists every cell: 172,302 cells, the reading JSON 29.7 MB, a 142 MB heap uncapped, dies at 112 MB), now observed live: **R8-reading B's "the live isolate's death is not observed, inferred" becomes observed.** The reproduction there used a 19.46 MiB stored package, which the door would have deferred to the ledger (and shown a stated "too large" reading); the live file is small stored and huge unpacked, so it goes the other way. **The gate must count the unpacked size of a container (zip/office), not the stored bytes**, besides the held-cells fix.
2. **Why the 42.9 s:** the upload's request waited for the extractread that ran 38 s to the kill (started 19:52:15.6, ended 19:52:53.5), then answered 200 at 19:52:54.0 (outer wall 42,899 ms). Not the capture (about 2-3 s), not the proxy. The equal 42.7 s of the scan is a coincidence of two different 39-38 s reads (24 OCR calls; an OOM).
3. **Nothing owed:** after the reset the door logged `extraction.acquire_read_unanswered` (NoAnswer, `STORE_REPLY_NOT_AN_ANSWER`) for the digest. By the code (`acquireReadingOp`, `extraction/ops.mjs:123-135`, then `readUploaded` :2749-2756) a no-answer read must come back `reading_pending: true`, and `pendSha` (:2658-2663) must write a `reading` row by `pendingadd`. **No `pendingadd` reached the object (none in 19:50:30-19:56:00), and `owedwork` has no row.** What is proven: the registration was attempted by no event the object saw; the `reading` is absent (`found:false`); the later `promote` (19:52:55) was itself cancelled at the outer Worker after 689 ms (it carried no reading, so its `followEntries` would have been the second chance, `readingWontFit` false -> `readHeld`, and would have asked the object to read it again; cancelled, it did not). What is **inferred, not shown**: that `pendSha`'s `stub.fetch` threw on the stub that had just seen the isolate reset (a Durable Object stub is "broken" after a reset until a new one is made) and `pendSha` swallowed it (`catch { /* the alarm is the reading's second chance */ }`). Nothing in the logs says so, because that catch writes nothing.
   **Logging still needed to close it** (K4428, rides the one deploy): in `pendSha`, a `console.error` line with `{event:"pendsha_failed", kind, sha, name, message}` in the catch, and one when the answer is not `ok`; in `readUploaded`, one line `{event:"upload_read", sha, pending, more, ocr_left, tier3_candidate}`. And the fix of B: `pendSha` takes a **fresh stub** (`env.STORE.get(id)` again) when the first call throws, so the debt survives the reset.
4. Neither walker's repair needs the ledger to have been registered: both documents can be re-registered by a migration (scan: re-register every stored reading with `tier3_candidate` true and no `ocr` row; ODS: documents held with no reading and no row, count by `heldcaptures` against `reading found:false` and `owedwork`).
