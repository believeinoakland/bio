## Item 4 · PLANE #56 "For BOB": the reading re-serves the whole file several times per tick

### 4.1 Where each tick reads the evidence. **Certain** (instrumented run)
Scratch copy of the merged harness with a log line in its counting `bucket.get` (`range`, object size, stack), `g41-shape` case "12 MiB CSV" (12,583,006 B). Unmodified counts, from /home/user/mx-plane (`g41-csv12.out`):

Instrumented reads (ranges, in order; object size 12,583,006 each time):
- Upload/profile: whole `get`, `null` options (`acquisition` `profileOf` :1941, capture upload :819).
- **Tick 1**: one whole `get` (`reading-pipeline/index.mjs:2283` `whole` ← `bytesOf` :2302 ← `readInner` :2377): by design, "the first piece still reads the whole" (R35's totals, R14 provenance, classification are over the whole text; comment `:1612-1619`); then 3 range reads of 1,048,576 B at offsets 0, 1 MiB, 2 MiB (`csvWindowCursorIn` :1765 ← `csvWindowCursorOf` :1746) to name where tick 2 begins.
- **Ticks 2-6** (`csvWindowTick`, G68): per tick one head read `{offset:0, length:1048588}` (`:1845`, the dialect/encoding head, CSV_HEAD_BYTES) and two or three window reads of 1,114,112 B (`:1832`, offsets 2108717, 3157294, 4205915; 4215066, 5263648, 6312258; ... ), i.e. about 4.4 MB requested per tick to advance ≈ 2.1 MB of the object (`read_through` 1,965,674 → 3,931,388 → ...). No tick after the first requests the whole object. The last `get` of the run is a whole read for `cellsOf` (`cellsInRange` :2769), which is the test's call.
- So the plane-1 note "4 evidence reads of 12 MiB each per tick" counts reads correctly (4) but their SIZE wrongly: the harness's bucket stand-in is `multipartBucket()` (`bio-plane/test/m/record-core/storage.mjs:78-89`), whose `get(k)` takes no second argument and returns the WHOLE object for a ranged request (`:83-88`); the harness then counts `o.arrayBuffer()` bytes (`harness.mjs:168`). R2 honours `range` (record-core R88; `rangeBytes` `:1630-1637` even tolerates a store that ignores it, "cut here"). On the platform each of those 4 gets is ≈1.1 MB, ≈4.4 MB a tick.
- For formats that cannot be windowed (HTML, a text that is not valid UTF-8, a CSV in UTF-16, any other format: comment `:1612-1619`) each tick reads the object whole, once. Measured: the 150,000-row xlsx, 3.49 MiB: tick 1 `gets 2`, ticks 2-3 `gets 1, bytesServed 3,661,384` (= the file, once). Bounded by the whole-read ceiling (`WHOLE_READ_MAX`), by design (G68 scope).

### 4.2 Is it a correctness issue, a memory issue at 128 MB, or efficiency only?
- **Correctness: no.** Every tick reads the same immutable object; the cursor kind `w` carries the offset and the totals; the run reaches `state: whole`, marks found, `cellsOf` equal to the generator's (g41-shape csv12 passes: `✔`, 6 ticks, 90 units).
- **Memory at 128 MB: not from this.** Real windows are ≈1.1 MB; the one whole read is tick 1's (12 MiB buffer + decode, by design). The harness's tick memory (peak heap+buffers 182-194 MB at cap 194, 95-107 MB above base) for ticks 2-5 is OVERSTATED by the stand-in, because it holds four 12 MiB buffers per tick where R2 would hold four 1.1 MB ones. The memory verdict of ticks 2+ on the platform is therefore not what the harness shows; tick 1's (a whole read) is. For non-windowable formats the per-tick whole read is a memory fact (file size + decode), already bounded by `WHOLE_READ_MAX` and covered by the cap convention.
- **Efficiency: ≈2× read amplification** on ticks 2+ in real R2 terms (4.4 MB asked for 2.1 MB advanced): the dialect head (1,048,588 B at offset 0) is re-read every tick (≈24 % of a tick's bytes) and the lookahead window that locates the next cursor re-reads the boundary region. Not a defect; could be kept in the cursor.
- **Test-quality issue the finding exposes:** `bars.mjs` states the bar as "a tick that reads the file whole eight times is the shape's limit" (`TICK_COUNT_BARS.bytesServedPerFileByte` 8). With a stand-in that serves whole for ranges, the working G68 shows 4× the file; with an honest range stand-in it would show ≈0.35×, and a G68 regression (each tick reading the whole object once = 1×) would pass an 8× bar either way. The bar does not see what G68 fixed.

### 4.3 Why the tests missed it; failing-first test; owner
- The harness's bucket ignores `range` (above). No test asserts that a later tick's bytes served is a window, not the file.
- Failing-first: module `record-core` owns the stand-in (`bio-plane/test/m/record-core/storage.mjs`): a test that `multipartBucket().get(k, {range: {offset, length}})` answers exactly the slice and `size` the object's (red today: answers the whole). Then `plane` (`shape/bars.mjs`, `harness.mjs`): a tick ≥ 2 of the 12 MiB CSV serves at most (windows + head) ≈ 4 × 1.2 MB, and tick 1 at most 1 whole read + the cursor's three windows; red the day a tick re-reads the object whole. Fix owner for the real reading: none needed for correctness; if BOB wants the head kept, `reading-pipeline` (`csvWindowTick`, cursor).

### 4.4 Live check after deploy: **No** for correctness (nothing changes in the product). Memory of tick 1 and of non-windowable formats at 128 MB is the existing P/L check of G41/G123a; the stand-in fix is test-only.
