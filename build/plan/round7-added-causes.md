## G83 · A team's room is created wherever its first `get()` runs (biosmoke8's in Frankfurt, its files in western North America; P19, K4746)

**Scope (coordinator, Bob's "B").** In the alpha: the room is created in the founder's region by a `locationHint` at its first creation; the installer learns the region by the simplest reliable route (below); biosmoke8's room is re-created in **western North America** (`wnam`) at the redeploy. **Not in the alpha:** the region shown on the install screen and the picker for a legal requirement (K4746's rest): they are a `next.md` entry (text at the end of this section), reason Bob's placement (K4747); no install-screen design work, no new word in T51.

### (1) Root cause, certain from code and the platform's page

- **Where the plane obtains the room.** Always `env.STORE.get(env.STORE.idFromName(<name>))` with no second argument; nothing in the tree passes a `locationHint` (grep of `bio-plane/src`, `newgroup`, `agent-worker`, `file-scanner`: no match in source; HANDOFF P11/P19 agree).   `store.mjs:759-766` and `ai-runs/index.mjs:2098-2106` only compare ids; they create nothing. `control-plane/phase-clock.mjs:90-98` wraps `STORE.get` as `(...a) => clockedStub(v.apply(target, a))`, so a second argument passes through (a control test below). `agent-worker`'s and `file-scanner`'s namespaces (`SEGMENTS`, `REMOTE`, `RUNNER`, `SCANNER`) are other objects, not the team's record; not in this cause (G83 answers K4746's "record object"; their placement is a later question, not planned here).
- **What Cloudflare does** (Durable Objects data-location page, read today): the object is created "in a data center close to where the initial `get()` request is made"; "To manually create Durable Objects in another location, provide an optional `locationHint` parameter to `get()`" (`NS.get(id, { locationHint: "enam" })`); "Only the first call to `get()` for a particular Object will respect the hint"; "Hints are a best effort and not a guarantee"; "Durable Objects do not currently change locations after they are created" (relocation "planned"). Valid hints on that page: `wnam`, `enam`, `sam` (spawns in `enam`), `weur`, `eeur`, `apac`, `apac-ne`, `apac-se`, `oc`, `afr` and `me` (the last two "spawn in a nearby supported location"); it says to prefer `apac` for general Asia-Pacific. The page documents the hint only for `get()` (not `getByName`). **Verified, not hearsay.**
- **Why Frankfurt.** The first `get()` came from a Cloudflare machine near Frankfurt. HANDOFF P19's hypothesis (the 5-minute cron runs "on underutilized machines", Cron Triggers page) is unconfirmed; with every site above passing the hint, whichever caller was first is covered, so the cause does not depend on it. Cause unknown in one respect only: *which* call first created biosmoke8's object; it is not needed for the fix (and the old object is wiped, below).
- **Jurisdiction is a different tool (for the later picker, not the alpha).** The same page: a **hint is best effort**; `eu`, `us` and `fedramp` are **jurisdictions** (`NS.jurisdiction("eu").idFromName(...)`), which "only run and store data within a region to comply with local regulations", but they make a *different id* for the same name (so `store.mjs:766`/`ai-runs:2106`, which compare `ctx.id.equals(ns.idFromName(name))`, would no longer recognise the object), and "Workers may still access" them from anywhere. Local workerd throws "Jurisdiction restrictions are not implemented in workerd". A legal requirement therefore cannot be met by a hint; this goes in the `next.md` entry so the later screen does not promise it.

### (2) Why the tests missed it

Every test hands the plane a Miniflare or fake namespace and asserts what the object *answers*, never the arguments of `get()`; a location is invisible to workerd locally (measured below), so no suite could see it; no install test asserts the plane's upload bindings for a region, since none existed; the measurement lane found it on the platform (P19) only after R2 and the object were seen in different places. Gap fixed by: (a) a census test that no source file calls `STORE.get(` except through the one helper (red today on 25 sites), (b) a recording namespace around the real plane that asserts the options of **every** `get()` across the real entry paths, (c) the installer's upload-metadata assertions, (d) the platform check P that reads where the object actually ran.

## G84 · The plane's global scope takes about 1.1 s in Node against Cloudflare's 1 s start-up limit (PERFORMANCE P16)

### (1) Root cause (certain in part; the rest named, with the measure that closes it)
