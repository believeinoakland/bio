## 2. Cloudflare facts (read live 2026-10-22)
- Cron Triggers (https://developers.cloudflare.com/workers/configuration/cron-triggers/, upd. Oct 17, 2026): five-field cron, `* * * * *` "At every minute" is listed (no minimum stated beyond that; I found none). "Cron Triggers execute on UTC time." "Changes such as adding... updating... or deleting a Cron Trigger may take several minutes (up to 15 minutes) to propagate". "Workers scheduled by Cron Triggers will run on underutilized machines" (so late fires are expected). Declared in wrangler `"triggers": {"crons": [...]}`; "When deploying a Worker with Wrangler any previous Cron Triggers are replaced... If the `triggers` or `crons` property are `undefined` then the currently deploy Cron Triggers are left in-place." That sentence is about wrangler; whether a raw API script PUT (deploy.mjs, installer) keeps schedules is NOT stated: UNCONFIRMED. The multipart upload metadata page (workers/configuration/multipart-upload-metadata) has no cron/trigger field, so crons are set only by the separate endpoint `PUT /accounts/{account_id}/workers/scripts/{script_name}/schedules`, body "array of object {cron...}" (https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/schedules/methods/update/; permission "Workers Scripts Write"; it does not say replace-vs-merge: UNCONFIRMED; a GET read-back is not on the page I read).
- Limits (https://developers.cloudflare.com/workers/platform/limits/, upd. Oct 12, 2026): "Number of Cron Triggers per account" 5 Free / 250 Paid (line 31); "CPU time per Cron Trigger" 10 ms Free, "30 seconds (< 1 hour interval)" Paid (line 72); "Scheduled Workers have a maximum wall time of 15 minutes per invocation" (line 429). Per Worker: "A Worker can have up to three Cron Triggers configured at once" (durable-objects/api/alarms/). Plane needs Paid anyway (wrangler.jsonc comment, DEC-42).
- Scheduled handler (https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/, upd. Oct 17): `scheduled(controller, env, ctx)`; `controller.scheduledTime` "the time the ScheduledEvent was scheduled to be executed"; "The first `ctx.waitUntil` to fail will be observed and recorded as the status in the Cron Trigger Past Events table"; the runtime waits for the returned promise "up to the 15-minute duration limit". Whether the platform auto-retries a failed scheduled run: NOT STATED; only a local `controller.noRetry()` flag is mentioned (cron-triggers page). Treat as no retry; the next cycle is the retry (K4566 (3)). Cron Events "stores the 100 most recent invocations"; Workers Logs keep longer. Local test: `wrangler dev` + `curl /cdn-cgi/local/scheduled?cron=...&time=...` (needs wrangler >= 4.139 for Local Explorer; repo has "^4.114.0", bio-plane/package.json:14).
- DO alarms (https://developers.cloudflare.com/durable-objects/api/alarms/, upd. Apr 21, 2026): "retried automatically when the alarm() handler throws... exponential backoff starting at a 2 second delay... up to 6 retries"; "This only applies to the most recent setAlarm() call"; "a sufficiently long outage... or a bug... can exhaust the limited number of retries, causing the alarm to not be re-run in the future until the next time you call setAlarm". `getAlarm()` "returns null unless setAlarm has also been called since the alarm handler started running" (so null is normal during a run). If the object is killed: "the alarm() handler may be re-instantiated on another machine... Following a short delay... run from the beginning". Not stated: how kills count toward the 6 (6 retries + first = 7 runs; diagnosis saw 8 kills, F5 diagnosis s1) and whether `getAlarm` keeps reporting a spent alarm: the page says nothing; that part is INFERRED from F5 (analytics + code), never read live. Constructor warning: check `getAlarm` before `setAlarm` in the constructor (same page).
- Worker -> DO from `scheduled`: same binding as `fetch`: `env.STORE.getByName(name)` / `get(idFromName(...))`, then RPC `await stub.method()` or `stub.fetch()` (https://developers.cloudflare.com/durable-objects/best-practices/create-durable-object-stubs-and-send-requests/, upd. Apr 21). The page shows it in `fetch`; nothing says `scheduled` differs (env bindings are passed, scheduled page); not separately demonstrated: UNCONFIRMED but expected. Errors (https://developers.cloudflare.com/durable-objects/best-practices/error-handling/): infra errors propagate to the caller; ".retryable" may be retried if idempotent; ".overloaded" "should not be retried"; a stub that threw is "broken": "create a new one" each attempt. RPC cannot be given a timeout by the platform: the Worker must bound it itself (race with a timer).

## 3. Smallest design meeting K4566 (1)-(5)
**Cron:** `triggers.crons: ["*/5 * * * *"]` in bio-plane/wrangler.jsonc (one of 3 allowed; 1 of 250 per account; file-scanner's is */10, so */5 is in precedent). Rationale: the 5-minute object monitor cadence is what the diagnosis saw; "stale" = owed work and no run for 2 cycles = 10 min; worst heal ~5 min + a late/queued fire. A `*/10` halves cost but doubles the worst case; the plan should pick (cost is 288 small fires/day/team, one DO request each; I did not read DO or Workers pricing for the figure).
**Worker `scheduled(controller, env, ctx)`** in plane/src/plane/index.mjs (new export beside `fetch`; update the "No other export" header): for each of `bio` and `scratch` (scratch has its own scheduler/alarm; if BOB rules scratch holds no owed work, `bio` only): fresh stub each call, `stub.watchdog(controller.scheduledTime)`, raced against a 10 s timer (the call keeps running; a long read queues the RPC behind it, so a timeout is "busy", not "dead"); the whole handler in try/catch; on any failure `console.error` structured line and then THROW after trying both objects, so Cron Events/GraphQL show a failed scheduled invocation (a failure path independent of the object); no `ctx.waitUntil` work, no other subrequest, no R2.
**Object method** `watchdog(at)` on Store (plane/store.mjs next to :705-708) delegating to `scheduler.watch(at)` (scheduler module). In one call, only: (a) `seen = at` write beside the heartbeat (single storage put, same key group as the heartbeat so one read shows both); (b) read `getAlarm()`, the heartbeat `{last_run, running_since}`; (c) decide: alarm null AND not running (running_since absent or older than a bound, e.g. 5 min, since a killed run leaves it set) OR alarm older than the spent bound (the job uses 60 s, J3 SPENT_ALARM_MS) OR owed work with `last_run` older than 2 cycles: then `arm(now)` (J3 behaviour: set to max(want, now)); never run `onAlarm`, never read rows or documents; "owed work" must come from a counter the scheduler keeps (e.g. wake instant), not a scan of ledger rows. Idempotent: setting the same near-future alarm twice is harmless; a late fire sees a fresh heartbeat and does nothing; a double fire is the same. Alarm replaced by `setAlarm` while the handler is running is safe (alarms never overlap, alarms page). Returns `{alarm_at, last_run, rearmed}`.
**Where last-seen lives (no shared failure):** two copies. (1) Object storage next to the heartbeat (what `owedwork`/`health()` shows: `watchdog_seen`); this shares the object's fate, so (2) the cron invocation's own status in Cloudflare (Cron Events, Workers Logs, GraphQL scheduled invocations) which exists even when the object is dead and is what the live smoke reads for "the object unreachable" case. Do not write R2/KV from the watchdog (adds a failure source and a subrequest).
**`owedwork` (plane, pending.mjs:292-296):** add `last_run`, `alarm_at`, `stale`, `oldest_overdue` (min `due_at` of owed rows `< now`, from the existing `holder.summary()`/`list` source, cheap, one MIN query), `watchdog_seen`; declared output in op-declarations and the words row; `health()` from the scheduler ({last_run, alarm_at, stale}) is the source (job B3). A read of owedwork must itself not re-arm (read-only op, declared.mjs:16 `mutating:false`).
