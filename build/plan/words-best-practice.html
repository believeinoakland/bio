Is a 15,000-row word table right?

BOB #213, 18 October 2026. Your question: is one hand-keyed word table of some 15,000 entries the best way to fix the fragility and meet the translation requirement? This page sets out what the established practice says, with sources, and where the evidence is thin. It ends with a decision for you.

What established practice says

  1. Text people read is kept out of the program logic, in message catalogs, one per language. That part we already do. GNU gettext extracts translatable strings into a .po catalog. FormatJS extracts into lang/en.json. Mozilla's Fluent keeps messages in .ftl files. GitLab syncs its catalog, gitlab.pot, to Crowdin for translators. (xgettext, FormatJS, Fluent, GitLab)
  2. The common workflow is not a table that people key by hand. In the mainstream tools, developers write the English message once, where it is used in the code, wrapped in a marker function. A tool then extracts every marked message into the catalog automatically. FormatJS: "We recommend against explicit IDs since it can cause collision", and its tooling generates an ID from each message's content. Lingui generates IDs by default, so "you don't need to come up with a name for each single phrase", and "searching for a user-facing string will lead to the place in code where it's used." Translators work only in the catalogs. (FormatJS, Lingui)
  3. Fragility comes from tests and stitched-together text, not from where the English sits.
    • One testing guide describes the classic failure: suites that "assert on literal copy, so every wording change breaks fifty tests". The standard fix is to assert the message's key or structure, and to test with a "pseudo-locale" (machine-garbled text) that proves every string goes through the translation layer. (Intlayer, Lingoport)
    • Never build a sentence from pieces. Use whole sentences with named placeholders, and handle plurals with ICU message syntax, because word order and plural forms differ by language (Arabic has six plural forms, Russian three). (Mozilla, GNOME, Locize)
  4. An English-only wording fix need not touch anything else. Mozilla: if a change is "relevant only for English", there is "generally no need to update the string ID"; a new ID is needed only when the meaning changes. With stable IDs, "if the message changes, the ID remains the same" (Lingui). (Mozilla, Lingui)
  5. Text only developers see is not translated. Google's error model keeps the developer message in English and localizes only what users see, through stable codes. (Google)
  6. Is 15,000 entries a lot? I could not find a published total for a large product's catalog, so I won't state one. The nearest figure: Mozilla's translation platform took in 13,002 new strings in 2025 alone, across its projects. Catalogs of this order are ordinary. Their size is not the problem; maintaining them by hand is. (Mozilla l10n 2025)

What that means for Civicsmith

  • Two of our rules match best practice: tests never copy a sentence, and nothing is stitched together. Most of the 1,463 tests that copy a sentence, and the 176 that copy another module's lists, are the real fragility. Both are fixed whatever else we choose.
  • Hand-keyed sentences are not the common practice. Our rule today, that no module may hold any English and that every sentence needs a hand-named key the design stream writes first, is what turns about 7,100 sentences into 7,100 round trips with the design stream. The mainstream tools avoid exactly that.
  • The word table also duplicates the code. 2,124 sentences sit both in a module and in the table. That is the worst case, because the two copies drift apart.

Your decision: how the words are kept

A. Keep today's rule and key all of it by hand

The design stream writes about 7,100 new rows and two passes switch the code. It works and matches our current doctrine, but it is the slowest, and every new sentence keeps needing a round trip.

B. Extract from the code (recommended)

Each sentence stays written once, where it is used, wrapped in one marker function with a stable ID. A build step extracts every marked sentence into the word table automatically, as gettext, FormatJS and Lingui do. The design stream still owns the wording: its English entry in the table overrides the code's, so a wording change is a table edit with no job. Translators work in one table per language.

The check then fails on three things: a sentence people read that isn't wrapped, a test that copies a sentence, and a hand-copied list. A pseudo-locale test proves nothing escapes the marker. The conversion is mechanical, a script wrapping literals in one pass, and needs no 7,100 design round trips. Developer-only messages stay plain English, as Google does.

C. A mix

Keep hand keys for the screens the design stream draws, and extract everything else. It is quicker than A, but it leaves two rules for developers to tell apart.

I recommend B. It is the established practice, it removes the bottleneck behind the fragility, and it keeps the design stream's control of every word through the English table. Either way, the test and list fixes, the check and the pseudo-locale test happen in T51.
