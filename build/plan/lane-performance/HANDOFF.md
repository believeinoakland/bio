## P1 · C15 · the interface words are asked for without the release version, so the year-long cache never applies — fix is one line of ordering
- **Measured.** Home (`/app`) on a signed-in load: `op=interfacewords` is requested as `?op=interfacewords` (no `v`), answers 200, 1,016,962 bytes on the wire (zstd; about 6.2 MB decoded), `cache-control` absent, and the request waits 2.3 s, the last request of the page to finish. Two loads, two downloads.
- **Root cause.** R116 is in the source and is correct (`control-plane/words-cache.mjs:25`: caches only when the request names `v` equal to `env.VERSION`). The shell never names it: `interface-shell/browser.mjs:2450-2452` (`loadWords`) takes `v` from `BOOT.version`, but `BOOT` is set by `bootstrap`, which `start()` fires without waiting (`browser.mjs:2542-2547`) while `loadWords` is called from `whoami()` (`browser.mjs:1495`) about 1.5 s earlier than `bootstrap` answers (live: whoami at 0.18 s, bootstrap at 1.8-3.0 s). So `v` is always null on the first load. The sign-in page's copy of the op does carry the cache header because that page has the version in hand.
- **Owner.** `interface-shell` (the ordering); `control-plane` is correct as it stands.
- **Fix.** The page already knows its release when it is served (`appAsset(..., { version: env.VERSION })`, `control-plane/index.mjs:738`; the page is built in `interface-shell/index.mjs:449`): put the version in the page the shell is served in, and read it from there for `loadWords`, instead of from the `bootstrap` answer. (Alternative: `loadWords` awaits the `bootstrap` promise; it costs a round trip on every first load, so the first option is better.) Changes no requirement; R5 and R116 already state the intent.
- **Expected gain.** Second and every later load in the same browser: 1 MB and one 2.3 s request gone, and the words no longer wait on the plane (the first draw never waited for them, R5, but the redraw does). First load unchanged.
- **Risk.** None to a member; a test that pins the request without `v` (search `fixround2.test.mjs`) will need the new expectation.

## P2 · C14 · why the screens take 6-13 s: five causes, ranked by what they cost on Home (7-8 s, 87 requests, 2.0 MB)
Home's own 81 API reads, in order of cost:
1. **The screen is read twice.** Every read of Home appears twice (`browse`, `lookedsince`, `projectlist`, `queue` 3×, `bootstrap` 3×, `groupidentity` 3×…), the second batch starting 1.3 s after the first, just when the assistant-reach read finishes. Cause: `loadReach()` (`browser.mjs:2492-2506`) ends with `if (MAIN) readAll(MAIN)` whenever `REACHABLE` changes, which on a first load it always does (false → true); `readAll` with no names re-reads every read of the screen and resets each to "loading". Nothing about the screen's reads depends on `REACHABLE`. Fix: re-read nothing there (redraw only; the dock's own reads are separate, `browser.mjs:1470`). Saves the whole second batch: about 40 reads and 1.5-2 s on Home. Owner `interface-shell`.
2. **One request per project, twice over.** Home reads `projectquestions` once per project (17 projects → 17 reads, to draw each row's question count: `screens-daily/project-rows.mjs:22-37`, paged to the end) and `casedrafts` once per project (17 more, to find drafts shared for review: `screens-daily/home-readings.mjs:62`). Each is 350-420 ms and they queue behind the frame's reads; 34 reads, 4 s of the load. Cause: the roster answer (`projectlist`, 7 KB) carries no counts or draft figures, so the screen asks per row. Fix: `project-roster` answers each project's question count and its drafts-shared-for-review summary in `projectlist` (one query inside the plane, not 34 round trips from the browser); the two screens (`screens-daily`) read them from there. Grows with the number of projects, so it is the cause that gets worse with use. Owner `project-roster` (new fields), `screens-daily` (use them); `basis-versions`/`publication` supply the counts as readers, not by edits across layers. Gain: Home −34 reads, about −3 s.
3. **`heldcaptures` is slow per row and Home asks it twice per load (four with cause 1).** Alone, one call takes 3.2-4.4 s for the 27 held captures of the copy (limit 500, full rows): 450 ms for 1 row, 950 ms for 10, 3.3 s for 27, about 110 ms per row; `fields=picker` takes 55 ms per row (1.9 s for 27). The full row runs, per row, R78's batch examination, the archive grouping (`archiveList`), R83's question reader, the grade, and an evidence-store `head` (`capture/index.mjs:1429-1468`, `#pageAnswers` 1669, `#wholeOf` 1431). Home asks it with `member` + `limit=500` and no `fields` (`screens-daily/todos.mjs:14`, which only needs source, collected_since and actor, which `picker` rows already carry, `capture/index.mjs:1436-1443`) and again with `picker` (`doors.mjs:16`): two reads of the same table at 1.8 s and 3.1 s. Fix: `todos.mjs` asks `fields=picker`; `doors.mjs` and `todos.mjs` share one read (the doors only need the count). In `capture`, the picker's per-row cost (55 ms) is still the evidence-store `head` per distinct digest: answer `whole` from what the register already holds (the size recorded at keeping), keeping `head` for the screens that act on a single document. Gain: Home −3 s of the slowest tail; the Held, Project and Inbox screens (13 s, 9.6 s, 8.9 s) read the same table. Owner `screens-daily` (the asks), `capture` (the per-row cost).
4. **The page itself is 4.3 MB of HTML, `cache-control: no-store`, on every load** (876 KB on the wire in zstd, 1.7 s before the first request starts; `curl -H 'accept-encoding: identity'` 4,336,426 bytes). The shell's whole program and every screen are inlined in a script element with a per-response nonce (`interface-shell/index.mjs:449`, `NONCE_SLOT`), so nothing can be kept. Not a fix for this round (it changes the page policy: an external, versioned script file served `immutable` with a hash in the CSP in place of the per-response nonce, `control-plane` page policy + `interface-shell`); proposed for the tranche after, and expected to take 1.7 s and 876 KB off every load after the first. Marked: **BOB's** to place.
5. **The frame's own reads are slow in themselves.** Measured alone: `queue` 0.7-1.2 s and 113 KB decoded (it is read 3 times on Home, with limit 200), `groupidentity` 0.54 s for 2.5 KB, `projectlist` 0.29 s, `browse` 0.28 s, `whoami` 0.16 s; a 40 ms round trip means `groupidentity` and `queue` spend 0.5-1 s inside the plane. Not yet traced to a line (next, with the plane's per-op timing); `queue` at least can be read once per load (cause 1 removes two of the three).
- **What the member would see after 1 and 2 and 3:** Home from about 7.5 s to about 2.5-3 s. The bar is 2 s; with 4 and 5 it is reachable.

## P4 · C12 · every capture waits 3.0 s for nothing, and a visitor-view capture also waits out the host governor (4-8 s)
- **Measured.** `acquire` of one public page, `timings` from the answer (the plane's own stage clock), 6 runs: plain: 4.0-4.7 s total = fetch 0.57-0.69 s, read 0.2, profile 0.23-0.28, **attest 3.000 s exactly** every time. With `render: true`: 13.9-16.9 s = **fetch 4.3 / 5.2 / 7.8 s**, read 0.13-0.18, render 5.5-6.3 s (the browser itself reports 4.0 s of it), profile 0.24-0.39, attest 3.000 s.
- **Root cause a (the 3.0 s).** `acquisition/index.mjs:364,1379`: `ATTEST_WAIT_MS = 3000`; the answer waits that long for the timestamp and co-archive, which on the copy never answer in time (the "had not answered when this capture was answered" sentence is drawn on every capture, A.md/B.md), so the wait is always spent in full and always ends pending. A fixed wait that always runs out is the cost of the request, not a bound on it.
- **Root cause b (the render's extra fetch time).** The render path asks the host governor to admit the host before the fetch (`acquisition/index.mjs:910-912`, `governorAdmit({ host })`, result discarded except for a refusal). The governor books every admit: it spends a token and records `last_grant_at = now + wait` (`host-governor/index.mjs:136-146`), the "human-shaped gap" of 60 s / 12 per minute × 0.6-1.5 = 3.0-7.5 s. The fetch that follows a few milliseconds later asks again (`governedFetch` → `admit`, `host-governor/index.mjs:304-313`) and sleeps out the remaining gap. 4.3-7.8 s fetch stage against 0.6 s plain fits that range exactly. The same happens in the capture screen's two calls (`heldat` with `check`, then `acquire`; screens-intake `capture.mjs:388-392`) for an address not yet held: the second fetch waits out a gap the first booked.
- **Root cause c (the render, 5.5-6.3 s against the browser's 4.0 s).** About 2 s outside the browser's own clock: session open (`Browser Rendering` acquire) and close. The renderer then collects every sub-resource's body one at a time after the page is taken (`browserrender.mjs:193-227`, `BODY_PHASE_MS` 10 s, awaited in a loop). Not yet measured separately (C13 below).
- **Owner.** `acquisition` (a, b), `host-governor` (offers the "admit without booking" b needs), `capture-sources` (c).
- **Fix.** (a) Do not wait: answer at once with the attempt pending, as the code already does past the wait (the late outcome is recorded by `recordLateAttestations`), or wait at most a few hundred ms; for the capture-request arm that already waits unbounded, no change. (b) The render admit must not spend the grant: either `governorAdmit` gains a peek (admission and refusal without booking), or the render path passes its admission to the fetch so there is one booking per host visit. (c) see P5.
- **Expected gain.** Every capture −3.0 s; a visitor-view capture a further −4 to −7 s. A plain page: 4.0-4.7 s → 1.0-1.7 s (under the bar of 2 s); a visitor-view page 14-17 s → about 7-9 s (the browser's own time remains, P5).
- **Risk.** (a) changes when the member learns the timestamp has landed, not whether; the sentence "asked for and had not answered" becomes the usual state, so the wording and the late-outcome recording (capture R68) are the review points. Whether to wait at all is a member-visible trade (time against seeing the timestamp in the first answer): **Bob's if BOB reads it so; recommendation: do not wait**, show the pending line, fill it when it lands.

## P6 · acts that take 5-7 s (C12's acts: Share for review 7.5 s, reply 6.6 s, Prepare the draft 7.4 s, Confirm ties 5.1-5.9 s)
- **Root cause.** After every act the shell re-reads the whole screen unless the act names which reads to repeat: `browser.mjs:2052`: `readAll(inst, d.spec.rereads || null)` (`null` = all, and it resets each to "loading", so the screen blanks while it re-reads). Acts that name `rereads` take 1.3-1.5 s on the walk (vouch 1.3 s, cite 1.5 s); acts that do not take the act's own time plus the screen's full read set (the document page's 50-124 reads, the case editor's, the plan's). By a count of the act declarations in `screens-*`: about 120 of about 300 name `rereads` (counted by pattern, so approximate).
- **Owner.** Each screen module declares its acts; the shell's default is what makes the omission expensive.
- **Fix.** Change the default: an act re-reads the reads its screen marks as depending on that act's op (a declared dependency), or only the reads whose request changed (`redrawAfter` already does that comparison, `browser.mjs:327`), and keep "all" for an act that says so. One edit in `interface-shell` instead of 180 act declarations; a test that every act's repeat set equals what it needs is the proof.
- **Expected gain.** Those acts to about 1.5 s. Not measured here: the act's own server time (one POST, to be done on a `PERF` project in the baseline).
- **Risk.** An act whose result shows in a read it does not declare would leave the screen stale: the default must be per-screen dependency, with the all-reads fallback kept for acts with no declared dependency until each screen is converted.
